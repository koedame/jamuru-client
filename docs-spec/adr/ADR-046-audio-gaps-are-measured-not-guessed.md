# ADR-046: 受信した音の欠けを数え、時刻と一緒に記録する。自動調整と帯域の警告は、その欠けを見る

## Status

Accepted

## Context

Mac（M4 Max・AG06・バッファ 64・`ultra-low-latency`）で、LAN 内の相手から 700Hz を受けた出力に、64 サンプル（1 パケット分）の無音が 3 秒に 33〜40 か所入った。多くは 100.0ms ちょうどの間隔で、耳には 1 秒に 10 回ほどのプチッという音になる。相手側の送信は途切れておらず（相手のホストでパケットを取ると間隔は最大 1.84ms）、`streaming_status` の `underrun_count` は 1546 回だったのに、`delay_adjustments` は 0 のままだった。調べると、次の 4 つが別々に見つかった。

1. **自動調整が空読みを見ていない。** `adapt()` の入力は補間（`Concealed`）だけで、来るはずのフレームが来ておらず後続も無い読み出し（`Starved`。無音を出し、再生位置を進めずに待つ）を数えなかった。フレームが遅れて届く回線では欠けの大半が空読みなので、1 秒に 10 回欠けていても段数は動かない。増やす閾値も 5% で、64 サンプルのフレームでは 1 秒に 37 回欠けるまで増えなかった。
2. **`debug.audio_record` の途切れの数え方が、1 パケットの欠けを数えない。** 2ms 以上の無音だけを途切れとしていたので、64 サンプル（1.33ms）の欠けが 32 か所あっても「途切れ 1 回」と出た。
3. **帯域の警告が、健全な回線を不足と呼ぶ。** 受信したレートを、自分のプリセットの必要帯域と比べていた。相手は自分の必要量ちょうどしか送らないので、健全でも受信レートは必要帯域に届くだけで超えられず、常に境界線上に載る。そのうえ受信側の数え方は UDP と IP のヘッダ（1 パケット 28 バイト）を含まず、必要帯域は含むので、5% 足りない側に外れ、3 秒続けて「不足」になる。相手がミュートして音声を送らなくなっても keepalive のバイトは届くので、これも「不足」になる。
4. **途切れの原因が測れない。** 100ms ごとの処理は 2 つある（受信ループの統計処理と、画面の 100ms ごとの状態読み出し）。どちらが受信を止めているのか、そもそも受信が遅れているのか、デバイスの読み出しが遅れているのかを、Mac の上で区別する手段が無かった。

## Decision

### 1. 自動調整は空読みも欠けとして数え、閾値を下げ、往復を抑える

[ADR-031](./ADR-031-live-playout-delay.md) の表を、区間の欠け率（補間 + 空読み）で判定する形に改めた。増やす閾値は 1%、きれいな区間は 0.1% 未満。減らして 3 区間以内に増やした（減らしが早すぎた）ときは、次に減らすまでのきれいな区間を 2 倍にする（80 区間が上限）。閾値だけ下げると、減らして欠けて増やす往復が 11 秒ごとに起きるため。

### 2. 帯域の警告は、相手が送った音声パケットの欠けの割合で判定する

相手の連番は、相手が送った音声パケットの数を教える。区間ごとに「届かなかった割合」を出し、1% 以上を marginal、5% 以上を insufficient とする（接続品質の良好／普通／悪いと同じ線。`quality.rs`）。相手が音声を送っていない区間（ミュート）は、運ぶものが無いので sufficient。バイトが 1 つも届かない区間だけが無通信（REQ-LAT-127）。表示する受信レートは、UDP と IP のヘッダを含めて数えるようにした（`ConnectionStats::wire_bytes_received`）ので、必要帯域と同じ基準で読める。REQ-LAT-124・125・NET-023 の文言は、この判定に合わせて直した（ID は変えない。警告を出す意図は同じで、測る量が変わった）。

**選ばなかった案**: 受信レートを相手のプリセットの必要量と比べ続け、許容を足す。相手の FEC の有無がプロトコルで分からず（必要量が 25% 変わる）、ミュートは判別できず、「余裕 20% 未満」は送るレートが必要量ちょうどの相手からは原理的に測れない。

### 3. 録音の途切れは、最小のフレーム（32 サンプル）より短い無音から数える

`DROPOUT_SECONDS` を 2ms から 0.5ms にした。1 パケットの欠けは、32・64・128 サンプルのどのフレームでも 1 回として数える。純音のゼロ交差は、50Hz でも 4kHz でも数えない（テストで固定）。

### 4. 受信した音の欠けを、種類と時刻つきで記録する（飛行記録）

`src/audio/flight.rs` の `FlightRecorder` が、次の種類の欠けの回数と、直近 512 件の時刻（起動からのマイクロ秒）と値を持つ。書き込みは出力のコールバックからも呼ばれるので、ロックも確保も無い（1 件は 64 ビット 1 語のリング、回数は relaxed の加算）。

| 種類 | 意味 | 書く場所 |
|------|------|----------|
| `starved` / `concealed` / `padded` | 読み出しの結果 | 出力コールバック |
| `primed` | 再生中に、バッファが起動し直して出した無音（再同期のあと） | 出力コールバック |
| `busy` | 読み出しが、ネットワーク側の持つバッファに当たって 1 フレーム無音にした | 出力コールバック |
| `late_frame` / `resynced` | 書き込みが、遅すぎて捨てられた・ストリームが飛んで作り直した（値: 飛んだ距離） | ネットワーク側 |
| `late_arrival` | 受け取ったフレームの間隔が 2 フレームを超えた（値: 間隔） | ネットワーク側 |
| `thread_stall` | 受信のタスクを運ぶスレッドが、自分のループの 1 周に 2 フレーム超かかった（値: 長さ） | 統計のループ |
| `read_gap` / `read_burst` | デバイスの読み出しが 2 フレーム超遅れた・4 分の 1 フレーム以内にまた来た（コールバックがフレームより大きい） | 出力コールバック |
| `trimmed` | 再生バッファが目標より深く溜め込み続けたので、余分を 1 回の飛びで捨てた（値: 捨てたフレーム数。[ADR-048](./ADR-048-playout-gives-back-piled-up-frames.md)） | ネットワーク側のフレームを読む出力コールバック |

`debug.audio_timing`（デバッグの口だけ）が、回数・直近の時刻・読み出しと書き込みの数を返す。読み方: `starved` の時刻が `late_arrival` の直前にあり、それが `thread_stall` と同時なら、スレッドが止まって受信が遅れている（受信ループの統計処理・ログ・ロックが疑わしい）。`late_arrival` だけなら回線。`late_arrival` も `thread_stall` も無いのに `starved` が出るなら、デバイス側（`read_gap` / `read_burst`）か、読み出しが書き込みより多い（`reads` / `writes`）。

## Consequences

### 良い影響

- 遅れて届くフレームのある回線で、段数が上がって欠けが止まる（`playout.rs` のシミュレーションテスト）。
- 健全な回線に帯域の警告が出ない。受信レートと必要帯域が 1% 以内で一致する（Linux の 2 台で実測: 受信 3.324 Mbps・必要 3.312 Mbps・判定 sufficient。旧判定は同じ構成で insufficient）。
- 途切れの原因を、Mac の実機で 1 回の呼び出しで切り分けられる。

### 悪い影響・残る作業

- **100ms の途切れの原因は、この ADR の時点で確定していない。** 記録の仕組みは入れたが、Mac に新しい版を入れて測るまで、どの種類が 100ms に揃うかは分からない。
- **再生バッファの深さは、増える一方で、上限（リング 38 フレーム = 約 51ms）で再同期して初めて減る。** 空読みは再生位置を進めずに待つので、1 回ごとに保持量が 1 フレーム増え、デバイスの読み出しが遅れた分も同じ。目標の段数より深くなっても、自動調整の縮める操作は目標を下げるだけで、余分な分を捨てない。Linux の 2 台では、再同期の距離が毎回 38（リングの大きさ）で、そのたびに `primed` の無音が出た。目標を超えて溜まった分を捨てる仕組みは [ADR-048](./ADR-048-playout-gives-back-piled-up-frames.md) で入れた。
- 帯域の判定は、回線が運べる量の**余裕**は測らない（相手が必要量ちょうどしか送らないので、受動的には測れない）。「余裕が少ない」は、すでに欠けが出ている状態を指す。
