# ADR-130: ルームチェックで、各ランナーとサーバー側の常駐の参加者との往復を測る

## Status

Accepted

## Context

ルームチェック（[ADR-117](./ADR-117-check-many-peers-on-hosted-runners.md)）の往復は、GitHub がランナーを置いたデータセンターどうしの間のものだけで、
アプリを使う人の側の置き場所（日本など）と、データセンターの間の往復は測っていない。ランナーは自分がどのクラウドのリージョンにいるかを
毎回記録しているので、決まった場所にいる 1 人の参加者との往復を測れば、リージョンごとの往復が溜まる。

## Decision

- ステージングのサーバーに、ルームチェックの部屋とは別の常設の部屋を 1 つ持ち、そこに常駐の参加者（相手）を 1 人置く。
  部屋は一覧に載せず、招待コードは Actions の secret `ROOM_CHECK_LATENCY_ROOM` で渡す（ソース・ログに書かない。[ADR-117](./ADR-117-check-many-peers-on-hosted-runners.md) の接続先と同じ扱い）。
  テストの部屋とも別にする。ベータの利用者がそこで試している間に、ランナーが参加者として見えたり、その音が届いたりしないため
- 各ランナーは、自分の部屋の計測が終わったあとに、この部屋に **1 台ずつ順番に** 入る。音は出さず（`/mute`）、入ってから 30 秒いて出る。
  アプリが 1 秒ごとに相手へ送る往復の測定（`LatencyPing`）の返事の時間が、リンクの往復（`rtt_spread_ms`）になる
- 順番はルームの開始時刻から各ランナーが自分で出す。ランナー i の番は「ルームの run の終わり + 60 秒 + 45 秒 × i」。
  同時に入らないのは、ランナーが一緒に入ると、ランナーどうしの鍵交換・穴あけ・ping と、まだ残っている自分の部屋の参加者の CPU が往復の揺らぎに混ざるため。
  台ごとに部屋と相手を分けるやり方は、相手の数だけサーバーの設定が増え、相手のいる回線と機器が共有のままで、同時に測る負荷が消えないので採らない
- 順番が守れたかは記録で確かめる。入っている間に部屋に見えた、相手以外の参加者の数を残し、1 人でも見えた台（`shared`）の数字は集計から外して数を出す。
  自分の番に遅れた台は、次の台の番に重ならないよう測らない（`skipped`）。相手に往復が届かなかった台は `unreached` として別に数える
- ルームチェックの合否には混ぜない。ログに出すのは台ごとの OS・リージョン・往復の数字だけで、アドレスは出さない

## Consequences

- 毎晩・毎時の回で、ランナーのリージョンごとの往復が溜まる。ランナーが出るのは北米のリージョンが中心で、欧州・アジアは出ていないので、この仕組みで分かるのは北米との数字
- ランナーの台数に応じて、ジョブが長くなる（台 1 つあたり 45 秒）。45 分の上限には余裕がある
- ランナーの外から UDP が通らない台は `unreached` になる。環境のせいで測れなかった台として数え、アプリの欠陥には数えない
