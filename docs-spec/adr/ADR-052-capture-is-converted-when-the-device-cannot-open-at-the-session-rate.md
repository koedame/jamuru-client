# ADR-052: 入力デバイスがセッションのレートで開けないときは、デバイスのレートで開いて変換し、それでも開けなくてもセッションは続ける

## Status

Accepted

## Context

Windows 11（beta.24）で、USB のオーディオインターフェース（Windows 上の名前は「USB AUDIO CODEC」、入出力 2ch）を入出力にしてルームに入ると、取り込みを開くのが `AUDCLNT_E_UNSUPPORTED_FORMAT`（0x88890008）で失敗し、音声の送受信が丸ごと止まった。相手の音も聞こえなかった。

1. WASAPI の共有モードは、サウンド設定の「既定の形式」でしか開けない。安いインターフェースは録音側の既定が 44100 Hz のことが多く、jamjam の既定 48000 Hz で開こうとすると拒まれる。デバイスは対応レートを入力 44100 だけ・出力 44100/48000/96000/192000 と申告していた。
2. cpal 0.18 の WASAPI は、出力にだけ `AUTOCONVERTPCM`（OS が変換する）を付け、取り込みには付けない。OS に変換させる道は cpal を改造しない限り無い。
3. 入力が開けないと、セッション全体が失敗して再生も始まらない。画面に出るのは OS のエラー番号だけだった。

## Decision

1. **デバイスがセッションのレートを申告しないときは、申告するレートのうち最も近いもの（同じ近さなら高い方）で開き、アプリ側でセッションのレートに変換する。** レートは開く前に、デバイスが申告する構成（チャンネル数が足りるもの）から選ぶ（`input_open_rate`）。セッションのレートで開けるデバイスは変換しない。
2. **変換は取り込みのコールバックの中で、メモリを確保せずに行う**（`CaptureResampler`）。rubato の 7 次多項式補間を 8 フレームずつ処理する。
   - 遅延: 補間の遅延 4 フレーム（実測: インパルスのピークが 3 フレーム = 0.06 ms 遅れる）に、8 フレームの区切りに満たない端数がコールバックをまたいで待つ分（最大 7 フレーム = 0.16 ms）。合わせて 0.3 ms 未満で、片道 2 ms の目標に収まる。
   - 音質（44100 → 48000 Hz の正弦波。0 dB = 入力と同じ音量）: 1 kHz・5 kHz は 0.01 dB 以内、10 kHz は -0.06 dB、15 kHz は -0.84 dB、18 kHz は -2.2 dB。3 次補間（既存の受信側の変換）は 10 kHz で -0.46 dB、15 kHz で -1.9 dB。
   - 採らなかったもの: 窓付き sinc 補間。通過域は 15 kHz まで平らだが、遅延が 0.35〜0.7 ms（16〜34 フレーム）になり、15〜17 kHz から上が切れる（sinc 長 32・64 で実測）。低遅延を最優先にするため採らなかった。
   - **変換なしが最良。** Windows のサウンド設定でデバイスの形式を 48000 Hz にすれば、変換は入らない。
3. **入力がどの方法でも開けなくても、セッションは続ける。** 出力は開いたままで相手の音は聞こえ、送信は何も出ない（閉じた入力の空のリング）。デバイスを選び直すと、開き直す。
4. **開けなかった理由を画面に出す。** デバイスが形式を拒んだ（`cpal::ErrorKind::UnsupportedConfig`）ときは、`device_problems` に `unsupported_format` とセッションのレートを入れ、画面が「入力デバイス（名前）を 48000Hz で開けません。サウンド設定で、このデバイスの形式を 48000Hz にしてください」と知らせる。それ以外の失敗は、これまでどおり「開けませんでした」。

## Consequences

- REQ-AUD-124（デバイスのレートで開いて変換する）と REQ-AUD-125（開けなくてもセッションが続き、直し方が出る）の検証は、変換・レート選びの単体テストと、開けなかったときのセッションの扱いの単体テスト、画面のテスト、Windows 実機（44100 Hz が既定の USB インターフェース）での動作確認で行う。
- 出力は WASAPI が変換するので、この決定の対象外。macOS・Linux で取り込みのレートが合わないデバイスも、同じ変換を通る。
- 変換を入れた取り込みは、セッションのレートより 8 フレーム分の区切りを持つので、取り込みのコールバックが 1 回に渡すフレーム数は一定でなくなる。送信側は受け取ったフレームを 1 フレームぶんずつ切り出すので影響しない。
