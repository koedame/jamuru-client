# ADR-111: 音声パケットを損失なく詰めて送る

## Status

Accepted。[ADR-096](./ADR-096-send-pcm-as-24-bit-integers.md) が決めた「24-bit 符号付き整数を 3 バイトずつ並べる」ワイヤ上の形を置き換える（サンプルの値は変えない）。

## Context

ADR-096 で 1 本あたりの必要帯域は約 22 % 減ったが、16 人のルームでは 1 人あたり 40〜47 Mbps のままで、家庭の回線の上りでは足りない相手が多い。

一方、音は隣のサンプルと近い値になる。直前のサンプルから予測した残りは小さな数で、小さな数は少ないビットで表せる。しかも jamuru の音質の最優先要件は「音を変えない」ことなので、ロスのある圧縮（Opus 等）は使わず、復号した値が 1 ビットも違わない方法に限る。

方式は FLAC（[RFC 9639](https://www.rfc-editor.org/rfc/rfc9639)）の考え方を使う: 固定多項式の予測（次数 0〜4、9.2.5 節）と、残りの Rice 符号（9.2.7 節）。ステレオは左右・左と差・差と右・中央と差（9.1.3 節）から選ぶ。

## Decision

1. **1 パケットのサンプルを、パケットごとに損失なく詰めて送る。** 復号した 24-bit 整数は元と完全に一致する（±1.0 を超える値の切り詰めと NaN の扱いは ADR-096 のまま。詰める前に行う）。
2. **FLAC のフレームは持ち込まない。** 1 パケットは 64〜256 サンプルで、フレームヘッダ（同期符号・CRC など）が大きな割合を占めてしまう。パケットに入れるのは、形式 1 バイト、チャンネルごとの予測の次数（3 bit）・分割の次数（2 bit）・Rice パラメータ（5 bit）・残りだけ。パケットの完全性は AEAD の認証タグが守るので、CRC は要らない。
3. **どのパケットも単独で復号できる。** 各チャンネルの最初の `次数` 個のサンプルは予測せずそのまま入れる。パケットが失われても後ろのパケットには影響しない（FEC・ジッタバッファの前提と同じ）。
4. **詰めても小さくならないパケットは「そのまま」の目印を付けて 24-bit のまま送る。** 形式バイト 0 に 3 バイトずつのサンプルが続くだけで、元より 1 バイトしか増えない。
5. **ステレオの左右が同じ（モノのマイクを中央に置いたときアプリが送る形）なら、差がほぼ 0 になるので 1 チャンネル分に近づく。** 左右・左と差・差と右・中央と差のうち、パケットごとに一番短いものを選ぶ。
6. **パケットの大きさは、音の中身が読み取られにくいよう、24-bit のままの大きさの 8 分の 1 刻みに切り上げる。** 余りは復号側が読み飛ばす。
7. **復号は固定の領域（スタック）で行い、確保しない。** 名乗るサンプル数が 2048 を超える、データに載り切らない、残りの符号が範囲外のパケットは、panic せずエラーにする（偽造・破損パケットで確保量や時間が膨らまない）。
8. **プロトコル版を 2 から 3 に上げる。** ワイヤ上に目印を付けず、ADR-096 と同じく版で切り分ける。鍵の交換の AAD にヘッダが入るので、既知の暗号文のテストの値も替わる。
9. **必要帯域の見積もり（`required_bps`）は上限のままにする**（詰めない場合の 24-bit + 形式 1 バイト）。実際の帯域は音で変わるので見積もりに使えず、足りないと見積もるのは安全側。UI の文言は「最大で約」にした。
10. **1 パケットに載るサンプル数は、そのまま送った場合（24-bit + 形式 1 バイト）が収まる数で数える。** 詰めた結果は常にこれ以下なので、MTU を超えない。上限は形式バイトの分だけ 1 サンプル減る（`samples_per_audio_packet`）。

却下した案:

- 毎回同じ大きさへの詰め物（固定長）: 大きさから音の中身が漏れなくなるが、詰めた分がすべて消えて意味が無い。
- 前のパケットを予測に使う: 小さくなるが、パケットが 1 つ失われると後ろが復号できない。FEC を前提にしたこの設計に合わない。
- 適応予測（LPC）や、より大きな Rice の分割: 64〜256 サンプルのパケットでは、予測の係数を送るコストが利得を上回る。
- ロスのある圧縮: 音を変えない方針に反する。

## 測定

条件: 48 kHz・ステレオ・24-bit。弦（Karplus-Strong）と声（フォルマントを通した声帯パルス）は合成した音で、オーディオインターフェースの雑音はガウス雑音を足して作った。数字はある機材の実測ではなく、音の種類ごとの目安。再現は `cargo test --release --test packed_measure -- --ignored --nocapture`。

24-bit のままのサンプルに対するパケットの大きさ（128 フレーム／パケットの場合。64 フレームもほぼ同じ）:

| 音 | 正確な大きさ | 8 分の 1 刻みに切り上げ後 |
|---|---|---|
| 声・モノのマイクを中央（雑音 −110 dBFS） | 21.3 % | 25.3 % |
| 声・モノのマイクを中央（−100 dBFS） | 23.9 % | 28.2 % |
| 弦・モノのマイクを中央（−110 / −100 dBFS） | 36.0 / 36.1 % | 41.9 % |
| 声・2 入力（−110 / −100 dBFS） | 38.5 / 43.6 % | 47.3 / 48.0 % |
| 弦・2 入力（−110 / −100 dBFS） | 62.8 / 63.9 % | 70.0 / 70.8 % |
| 無音（インターフェースの雑音のみ・2 入力） | 29.4〜36.2 % | 37.9 % |
| デジタルの無音 | 4.9 % | 12.6 % |
| 大きな雑音（ガウス、RMS 0.25） | 88.1 % | 90.9 % |

- 大きな雑音でも元より小さくなる（予測の残りの方がサンプルより小さい）。詰められなかったパケットは決定 4 の「そのまま」になり、元に +1 バイト。
- 弦のようにインターフェースの雑音が下位ビットを占める音は、雑音の分が詰められず、詰めた結果は声より大きい。24-bit のうち上の桁の分だけ得る。

1 パケット（128 フレーム）の処理時間（リリースビルド、開発機）:

| | 詰める | 戻す |
|---|---|---|
| 典型 | 約 14〜26 µs | 約 2〜5 µs |
| 最大（観測） | 約 60 µs | 約 11 µs |

128 フレームは 2.67 ms なので、詰める時間は周期の約 1 %、最大でも約 2 %。

遅延（`tests/wire_latency_measure.rs`、実際の UDP を loopback で往復）:

| | 詰める前 | 詰めた後 |
|---|---|---|
| 1 パケットの往復 p50 | 58 µs | 76 µs |
| 往復 p99 | 174 µs | 180 µs |
| 最初の音が届くまで | 12 ms | 13 ms |

増えるのは詰める・戻すの数十 µs で、フレーム 1 つ（1.3〜2.7 ms）の 2 % 以下。ジッタバッファの深さはパケット数で決まり、パケットの大きさには依存しない。

## サイズの漏れ

パケットは暗号化されるが、暗号文の長さは平文に比例する。詰めると、長さが音の複雑さ（無音か、声か、雑音か）に従って変わるので、通信を見ている者に「話している・黙っている」が読み取れる。

- もともと、非圧縮の PCM でも音声パケットは常に同じ長さで、ネットワークから見て無音と発話の区別はつかなかった。詰めると、この性質を失う。
- ただし読み取れるのは大きさの大まかな分類で、**内容（何を言ったか・何の曲か）は読み取れない**。8 分の 1 刻みに切り上げているので、パケットごとの情報量は測定で約 0〜1.5 bit（上の表で bits/pkt の列）に抑えられる。
- 固定長への詰め物は、帯域の節約を全部打ち消すので採らない。
- 参加者はもともと自分の音声を相手に渡している（ルームの相手には聞こえる）ので、「話している」ことは相手に隠さない。隠す対象は、経路上の第三者。

方針: **刻みの切り上げで十分とし、固定長にはしない。** プライバシーの説明（`docs/getting-started/privacy.md`）にその旨を書く。経路上の第三者に対して発話の有無までは隠したい利用者向けの選択肢は、必要になれば別の ADR で扱う。

## Consequences

- 1 本あたりの帯域は音で変わる。声（モノのマイクを中央）で約 25〜28 %、2 入力の声で約 48 %、弦で約 42〜71 %、大きな雑音で約 91 %。ADR-077 の表の「最悪」は上限として残る。
- 古い版のアプリとは繋がらない。ステージングのサーバー側の音質チェックのボットとエコーは、同じタグで出し直す。
- ワイヤ上の目印が無いので、将来さらに形式を変えるときもプロトコル版を上げる。
- FEC の冗長パケット・分割フレーム（ADR-070）は、詰めた後の可変長のまま扱える。
- 詰める処理はリアルタイムの音声スレッドで確保をしない。
