# ADR-093: 音声ソケットは IPv4 と IPv6 の両方を受ける 1 本にする

## Status

Accepted。[ADR-026](./ADR-026-gui-audio-path.md) の「候補は IPv4 のみ」と、[ADR-035](./ADR-035-stun-through-the-audio-socket.md) の決定 2（IPv4 専用のソケット）を改める。

## Context

音声ソケットは `0.0.0.0` に bind した IPv4 専用で、候補も IPv4 のアドレスだけだった（ADR-026・ADR-035）。一方 `architecture.md` と `api/signaling.md` は「デュアルスタック対応」と書いていて、実装と食い違っていた。

IPv6 どうしなら NAT がなく、ルーターのポートを開ける必要も UPnP も要らない。IPv4 over IPv6（MAP-E・DS-Lite・v6プラスなど）の回線は、使えるポートが限られて UPnP も使えず、IPv4 の相手と繋がらないことがある。ヤマハが公開しているフレッツ光ネクストの 2 回線のあいだの実測では、遅延は IPv6 が 1.06〜2.02 ms、IPv4 が 7.56〜13.25 ms で、揺れ（最大と最小の差）も IPv6 は約 1 ms、IPv4 は約 5.7 ms だった（[IPv6 サミットの発表資料](https://www.jp.ipv6forum.com/2020/timetable/program/20201202_2_IPv6summit_yamaha_hara_1130.pdf) 24 枚目。片道か往復かは資料に書かれていない）。zero-latency の遅延予算は 2 ms なので、この差は大きい。

## Decision

1. **音声ソケットは `[::]` に bind した 1 本のデュアルスタックにする**（`IPV6_V6ONLY` を切る。Windows は既定で切れていないので明示する）。ルームの全員が同じ 1 つのポートに送る作り（REQ-CON-033）は変わらず、IPv4 の相手にも IPv6 の相手にも同じソケットで送受信する。IPv6 が無い・デュアルスタックにできないシステムでは、これまでどおり `0.0.0.0` の IPv4 ソケットに戻る。ソケットを 2 本に分ける案は採らない: ルームに公開するポートが 2 つになり、相手ごとの接続（鍵・再接続・統計）が 2 本のソケットをまたぐ作りになるため。
2. **アドレスの綴りを 1 つにする。** デュアルスタックのソケットは IPv4 の相手を `::ffff:192.0.2.1`（IPv4-mapped）で報告し、IPv4 の宛先を渡すにも mapped にする必要がある（Windows・macOS は IPv4 の宛先をそのままでは受け付けない）。送るときは `UdpTransport::send_to` と STUN が mapped に直し、受けるときは `UdpTransport`・`UdpMux` が送り元を IPv4 に戻す。相手の候補も同じく正規化する（`usable_candidates`）。比較・表示・ルーティングに出るアドレスは、IPv4 は IPv4 の綴りだけになる。
3. **候補にはソケットが使える族のアドレスを入れる。** ホスト候補は IPv4 のインターフェースのアドレスと、IPv6 のグローバルユニキャスト（`2000::/3`）。リンクローカル（`fe80::`）は宛先にインターフェースの番号（`fe80::1%en0`）が要り、ワイヤ形式に載らないので入れない（受け取った側も送らない）。ユニークローカル（`fc00::/7`）は同じネットワーク内でしか使えず、そこでは IPv4 のアドレスでも届くので入れない。
4. **STUN は IPv4 と IPv6 の両方に、1 つのソケットから同じ周回で問い合わせる。** IPv6 は、ホストにグローバルな IPv6 アドレスがあるときだけ問い合わせる。片方が答えたら、もう片方を待つのは 1 秒まで（IPv6 のアドレスはあるが経路が無いホストが、ルームに入るのを遅らせない）。
5. **STUN が見た IPv6 のアドレスがあるときは、それ以外の IPv6 のホスト候補を出さない。** IPv6 のインターフェースにはグローバルなアドレスが複数付く（固定のものと、システムが入れ替える一時的なもの）が、システムが送るときに使うのは 1 つで、STUN が見たのがそれ。送ったことのあるところからの通信しか通さないファイアウォールは、そのアドレスにだけ穴が開く。ほかのアドレスは繋がらない経路で、確認の送信を 1 つずつ増やし、ルームに知らせるアドレスも増やす。STUN が答えなければ全部残す。
6. **経路の選び方は変えない。** 候補は IPv4 も IPv6 も同じ確認で測り、往復時間の中央値が最も短いものを選ぶ（[ADR-054](./ADR-054-route-is-the-nearest-that-answers.md)）。IPv6 を優先する規則は足さない。遅い方を選ぶ理由は無く、測って選ぶ。ホスト候補の優先度の中の IPv6 の +1 は、往復時間が並んだときの決め手になる。
7. **サーバーの変更は要らない。** 候補の型 `SocketAddr` はもともと `[ホスト]:ポート` の IPv6 の形を許し（`api/asyncapi.yaml`）、1 人 32 個までの上限も変わらない。シグナリングの Worker は Cloudflare の背後にあり、IPv6 だけの回線からも AAAA レコードで届く。

## Consequences

- IPv6 を使える回線どうしは、NAT を通らない IPv6 の経路でも測られ、IPv4 より短ければそちらで繋がる。IPv4 だけの相手とは今までどおり IPv4 で繋がる。1 つのルームに IPv4 の相手と IPv6 の相手がいても、1 つのソケットで両方に送る。
- **IPv6 だけの相手と IPv4 だけの相手は繋がらない**（族が合わない）。IPv4 だけの端末に IPv6 の候補は届くが、送れず、確認の返事も来ない。これを利用者に知らせる画面は、まだ無い。
- 相手と運営者に、端末の IPv6 のグローバルアドレスが見えるようになる（IPv4 では公開アドレスと LAN のアドレス）。IPv6 は NAT を通らないので、端末自身のアドレスが見える。利用者向けの説明（`docs/getting-started/privacy.md`）と Wiki「法務チェック」を同じ作業で直した。
- IPv6 には NAT の保護が無いので、受信を止めるファイアウォールが無い回線では、音声のポートに知らない相手からデータグラムが直接届きうる。届いたものは相手の確認と暗号化を通らなければ音にならず（ADR-090）、IPv4 でポートを開けた場合と同じ扱いになる。この ADR では足していない対策として、未知の送り元を `UdpMux` が全 lane に渡す前に数で絞ることが考えられる。
- 固定のインターフェース ID（MAC 由来）を持つ IPv6 アドレスは、端末を長く追える識別子になる。STUN が IPv6 で答えたときは一時アドレスだけを出すが、STUN が答えないときは全てのグローバルアドレスを出す。多くの OS は既定で一時アドレスを使う。
- アドレスの正規化をしない経路が残ると、同じ相手が別の相手に見える。送り元を受ける 3 つの口（`recv_from`・`recv_raw`・`try_recv_raw`）と `UdpMux` の読み取りでそろえ、`tests/ipv6_audio_test.rs` が IPv4 の相手との接続のアドレスで確かめる。
- 検証は `::1` と `127.0.0.1` のループバックと、STUN の模擬サーバー。IPv6 の回線どうしの実測の往復は、実機（ベータ版）で別に取る。
- UPnP でルーターのポートを開ける機能と、入室前の回線の確認は別のチケット。IPv4/IPv6 の不一致の警告も、この ADR では足していない。
