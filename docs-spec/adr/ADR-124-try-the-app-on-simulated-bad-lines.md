# ADR-124: 悪い回線を模擬して、アプリの途切れへの強さを変更の前後で並べて測る

## Status

Accepted

## Context

受信バッファ・欠けた音の補い・再生の速さの調整など、途切れに効く変更が続いている。その効き目は「同じ悪い回線で、変更の前後を並べて」でないと分からない。ところが次の手段しか無かった。

- 結合テスト（`tests/conceal_test.rs`、`tests/e2e/src/scenarios/loopback.rs`）は決めたフレームを抜くだけで、欠けが続けて起きる・遅れが揺れる・順番が入れ替わる・帯域が足りない、を実際の送受信に通して試すものが無い。8 人の劣化試験（`tests/e2e/src/scenarios/eight_node.rs`）は空のまま
- 実機の端末と相手役の間に OS の機能（`tc netem`）で品質をかける方法は、管理者権限と共有の機器と実機の端末が要り、毎回の検査や PR ごとの前後比べには使えない

リポジトリの中だけで、権限も実機も要らず、何度でも同じ悪い回線を作れれば、途切れの変更を数字で比べてから取り込める。

## Decision

アプリの中は変えず、**テストの側で相手との間に「悪い回線」を挟む**。

```mermaid
flowchart LR
    CLI["jamuru join-room<br/>--input-bursts --report-json"] -->|"相手の候補 = 中継の口"| L["BadLine<br/>上りの回線 / 下りの回線"]
    L --> E["EchoPeer<br/>受けた音を返す"]
    E --> L
    L --> CLI
    S["FakeSignaling"] -.->|"中継の口を相手のアドレスとして知らせる"| CLI
```

### 1. 方式: テストの中の UDP 中継（`tests/common/line.rs`）

`BadLine` は 1 つのソケットで両端のデータグラムを受け、上り（近い側→遠い側）と下り（その逆）に別々の回線をかけて送り直す。
カーネルの `netem` を使わない理由は、権限（`NET_ADMIN`）も docker も要らず、毎回の検査（`jamjam-check.sh`）で回せることである。
`tests/nat/run.sh`（docker のルーター）に `netem` をかける案は、実際のカーネルの振る舞いに近い代わりに docker と権限が要るので、毎回の検査には入れられない。
そのため中継を主とする。中継と実際のカーネルの `netem` が同じ数字を出すかの突き合わせは、ここではしていない（未検証。`docs/development/testing.md` に記す）。

- 乱数は固定のアルゴリズム（splitmix64）で、**種が同じなら同じデータグラムを同じように落とし、遅らせる**。ライブラリの版で列が変わらない
- 遅らせ方は、データグラムごとに「出す時刻」を決めて時刻順に並べ、時刻が来たものから送る。受信の処理ごと眠らせない。短い遅れのデータグラムは、先に送られた長い遅れのデータグラムの後ろで待たない
- 回線の判断は `Direction::offer(到着の時刻, 大きさ)` という時刻と大きさだけの計算で、ソケットなしに検査できる

### 2. 模擬できること（向きごとに別々）

| 項目 | 設定 |
|---|---|
| 遅延・揺れ | 遅延と揺れ（ms）。分布は一様（±揺れ）・正規（標準偏差が揺れ。`netem` の `distribution normal`）・Pareto |
| ランダムな欠け | 確率 |
| 続けて起きる欠け | Gilbert-Elliott のモデル（良い状態から悪い状態への確率 p、戻る確率 r、悪い状態・良い状態での欠ける確率。`netem` の `loss gemodel`）。悪い状態の長さの平均は 1/r、悪い状態にいる時間の割合は p/(p+r) |
| 順番の入れ替わり | 確率で遅延を飛ばして先に出す（`netem` の `reorder`）。揺れによる追い越しも起きる |
| 重複 | 確率で 2 回送る |
| 帯域の上限 | ビット毎秒と待ち行列の深さ（ms）。待ち時間が深さを超えるデータグラムは捨てる（末尾の切り捨て） |
| 全断 | 線の開始からの時刻と長さ、または `black_out(長さ)` |

Pareto の揺れは、遅延を最短とし、揺れ × (X − 1)（X は形 3・尺度 1 の Pareto 分布）を足す。多くは遅れがわずかで、まれに揺れの何倍も遅れる。平均は遅延 + 揺れ / 2。
`netem` の表とは分布の形が同じではない（遅延 0.1 ms・揺れ 3.0 ms の Wi-Fi 風は、この定義での値である）。

### 3. 名前付きの条件

片道の値で、往復は 2 倍になる。最初の 6 つは実機の測定と数字をそろえてある。

| 名前 | 片道の遅延 | 揺れ | 欠け | 帯域 |
|---|---|---|---|---|
| `fiber`（光） | 3 ms | 1 ms | なし | 制限なし |
| `4g-good`（4G 良好） | 35 ms | 8 ms | 0.2 % | 20 Mbit/s |
| `4g-busy`（4G 混雑） | 90 ms | 25 ms | 1 % | 5 Mbit/s |
| `burst-loss`（突発の途切れ） | 40 ms | 10 ms | 平均 20 パケット続く欠けが全体の約 2 %（0.1 %・5 %・100 %・0 %） | 制限なし |
| `narrow`（帯域不足） | 40 ms | 10 ms | なし | 1 Mbit/s |
| `queue-bloat`（往復が伸びる） | 30 ms | 10 ms | なし | 4 Mbit/s（待ち行列 600 ms） |
| `loss-5` / `loss-20` | 20 ms | 2 ms | 5 % / 20 %（ランダム） | 制限なし |
| `wifi`（Wi-Fi 風） | 0.1 ms | 3.0 ms（Pareto） | なし | 制限なし |
| `wired`（有線風） | 0.2 ms | 0.3 ms | なし | 制限なし |

既定の揺れの分布は正規（実機の測定と同じ）。待ち行列の深さの既定は 500 ms。

### 4. 測る道具: `cargo test --test line_trial -- <条件の名前>...`

CLI を、受けた音を返す相手（`EchoPeer`）のいるルームに入れ、相手の手前に回線を置いて、`--input-bursts --report-json`（ADR-039）で測る。
条件ごとに 1 行の表（往復の最小・中央値・95 パーセンタイル・最大、返ってきたバースト数、受信バッファの段数、再生・補った・遅れたフレーム数、経路の移動数、上りと下りで落ちた割合）を出す。
`--quality` を付けると、1 kHz の音を同じ回線に通して、音が消えた窓と、音らしくない窓の割合を足す（10 ms の窓ごとに正弦波を最小二乗で当てはめ、消えた窓は振幅が普通の 1/10 未満、音らしくない窓は音以外のエネルギーが 0.1 % 以上）。

- `--app <jamuru のバイナリ>` で別の版のアプリを測れる。変更の前後の版で同じ条件・同じ種・同じ秒数で回して表を並べる
- 引数なしは、毎回の検査の短い組（`fiber`・`4g-busy` を 6 秒ずつ）
- 終了コード: 0 = 全条件を測れた、1 = 測れない条件があった（アプリがレポートまで走らなかった・回線を何も通らなかった・往復が回線の最短より短く回線が効いていない）、2 = 引数が分からない。**数字の良し悪しでは終了コードを変えない**（比べるのは人）
- `--json <path>` で全項目を残す

### 5. アプリは変えない

回線はアプリの外にあり、アプリには設定も最適化も足さない。アプリが見るのは、相手の候補のアドレスだけが中継の口に変わった、いつもの接続である。

## Consequences

### 良い影響

- 途切れの変更を、同じ悪い回線の前後の表で比べられる。管理者権限も実機も要らず、毎回の検査と PR で同じ表が出せる
- 模擬そのものを `tests/bad_line_test.rs` で検査する。設定した欠けの割合・遅延の分布・帯域・欠けの続く長さが実際の出力で設定どおりであること、種が同じなら同じ結果になること、短い遅れが長い遅れの後ろで待たないこと

### 悪い影響・残る制約

- 回線は時間と共に変わる実際の回線と違い、条件の数字は一定。長い間に変わる回線は、全断（`black_out`）を重ねて作る
- 帯域の上限と待ち行列は 1 本の FIFO で、揺れによる追い越しは帯域の後ろで起きる。実際のルーターの複数の待ち行列は模擬しない
- 測るのは CLI の経路で、実デバイスの取り込み・再生は含まない（ADR-039）。台の負荷が高いと、回線と関係なく遅れる。表には測った台の負荷を添える
- 近い側のアプリが中継の口宛てに送るので、アプリの経路の選び方（近い経路から選ぶ、アドレスの移動の確認）は直接の接続とは違う入り方を通る
- 2 台のアプリを同時に回線の両側に置くには、偽のシグナリングが両方の候補を中継の口に向ける必要がある。今は相手が `Connection`（`BadLine::start(Some(a), b, ..)`）か、受けた音を返す相手

### 検証

| 内容 | 検証 |
|------|------|
| 欠けの割合・欠けの続く長さ・遅延の分布・帯域と待ち行列・順番・重複・全断・同じ種で同じ結果・名前付きの条件の数字 | `tests/bad_line_test.rs`（計算そのもの） |
| ソケットを通した遅延・短い遅れが長い遅れの後ろで待たないこと・向きごとの独立・全断・同じ種で同じ欠け方 | `tests/bad_line_test.rs`（中継） |
| CLI が回線越しに測れ、回線の最短より短い往復が出ないこと | `tests/line_trial.rs`（引数なし。`cargo test` が回す） |
