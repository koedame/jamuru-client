# ADR-118: 多人数の部屋の確認に、Windows と macOS の runner を混ぜ、記録を足す

## Status

Accepted

## Context

[ADR-117](./ADR-117-check-many-peers-on-hosted-runners.md) の部屋の確認は Linux の runner だけで回していた。
公開リポジトリでは Windows と macOS の runner も無料で、参加者を system ごとの runner に分けて 1 つの部屋に入れれば、
全員が全員を聞くので、聞く側の system × 話す側の system の組み合わせが 1 回で全部測れる。

2026-11-07 の 4 回を同じ台の中と台をまたぐものに分けると、往復の時間は同じ台の中で 0.06〜0.08 ms、台をまたぐと組ごとに 15〜65 ms で、
またぐ側は runner が置かれたデータセンターの距離で決まっていた。アプリの品質として追うのは「アプリが足した遅れ」
（端から端の往復 − 回線の往復）なので、それを測れる形で記録を残す。

## Decision

- 参加者を Linux・Windows・macOS の runner に分ける（既定は Linux と Windows が 2 台 × 2 人、macOS が 2 台 × 1 人。macOS の runner は 3 CPU で、2 人載せると返事が 0.6〜1.4 秒遅れ、1 台で 11 人と話すと 1 コア近くを使い切る。合計は上限の 16 人まで。台ごとの人数は `--layout` で渡す）。
  部屋を作る台は常に Linux（Windows の runner では、別の step に残る子プロセスの扱いが確かめられていないため）。
  macOS の runner は同時に 5 本まで（同時実行の上限）
- 番の始まりは、部屋を作った時に決めた時刻にしない。runner がマシンの割り当てを待つ時間は読めず（macOS は同時 5 本まで）、遅れて起動した runner が
  始まりのあとに着くと、すぐ終わって空の測定を「成功」として返していた。部屋を作った runner が、全員が部屋に入った（自分のログの
  「joined the room」を数える）40 秒後を始まりとして成果物で配る。全員を待つのは最長 20 分で、それでも来なかった参加者は
  始まりのあとに着いて失敗する（空のまま合格にはならない）
- 参加者は `r<run の番号>a<試行>-p<番号>` の名前で部屋に入る。サーバー側の記録とは IP ではなくこの名前で結び付ける
  （NAT で同じ台の参加者が 1 つのアドレスにまとまり、同じ台が接続ごとに違うアドレスに見えることもあるため）
- `jamuru --report-json` は相手ごとに、経路の種類（同じ機械 / 内側のネットワーク / 公開アドレス）、IPv4 / IPv6、つながるまでの時間、
  経路が切り替わった回数、受信バッファの量、回線の往復と端から端の往復の最小・中央値・p95・最大・標準偏差を書く（REQ-CLI-013）。
  往復は 1 秒に 1 回測って持つ
- 結果には参加者ごとに system・アプリの版・コミット、runner ごとに CPU 数・クラウドのメタデータ（Azure のインスタンスのメタデータ。
  取れなければ入れない。第三者の IP の位置を引くサービスは使わない）・IPv6 の可否・NAT の癖（2 つの STUN サーバーに同じソケットで
  問い合わせ、ポートやアドレスが変わるか）を足す
- **アドレスそのものは入れない。** 同じかどうかを比べるものは、接続先（secret）と run の番号を鍵にしたハッシュにする。
  鍵は run ごとに変わる
- 終了は標準入力の `/quit` で、全 system で同じにする（Windows には SIGINT を送れない）
- 設定の置き場所は `JAMJAM_CONFIG_DIR` で指せる（REQ-CLI-014）。Windows では `HOME` を変えても設定の場所が変わらず、同じ台の参加者が 1 つの端末の識別を共有して互いを入れ替えてしまうため。
  参加者ごとに別の場所を渡す
- **番の前に、台どうしが直接 UDP で届き合うかを、アプリを使わずに確かめる。** 各台が 1 本の UDP ソケットを開き、STUN で見える自分のアドレスを
  接続先で暗号化した成果物で配り、全員のアドレスがそろってから（待つのは最長 10 分）25 秒間、全員が全員へ送り合って受けた数を数える。
  ある 2 台は、**両方向とも届いたとき「通る」、どちらかが 0 のとき「通らない」**。片方でも確認できなかった組（アドレスが取れない・来なかった台）は「確認なし」。
  この 3 つの step は失敗してもジョブを落とさない
- **結果の読み方を分ける。** 確認で「通らない」台どうしの組のうち、アプリでも聞こえなかったものは、不合格にせず、まとめ（Verdict）に
  「環境のせいで測れなかった」として組の数と台の組を出す（聞こえた割合の統計にも入れない）。確認で「通る」のにアプリで聞こえなかった組は、これまでどおり不合格。
  確認で「通らない」のにアプリでは聞こえた組は、測れた組として数える（確認の取りこぼし）。確認と食い違った組（通らないのに聞こえた・通るのに聞こえない）は、まとめに記録する。異なる台の組が 1 つも測れなかったときは不合格にする
- 再生を速度の制約なしにファイルへ書く確認では、バッファの不足（underrun）を数えても意味が無いので、報告には入れない

## Consequences

- 組み合わせの表（聞く側 × 話す側）が毎晩 1 回で取れる。runner の CPU は共有なので、性能の結論にはしない（ADR-117 のまま）
- 回線の往復が大きく変わる台の組は、アプリの品質と分けて読む（端から端 − 回線の往復で、アプリが足した遅れを出す）
- 1 回あたりのサーバーへの要求は、人数と台数で変わる。変えたら測り直す
- 2026-11-08 の手動の回では、macOS の台の一部（15 台中 6 台）が、外との直接 UDP が通らない状態になった（アプリのソケットを何本作り直しても、
  全相手と送受信とも 0）。アプリでは直せず、中継（TURN 相当）は作らない方針なので、この確認で「環境のせいで測れなかった」と分けて出す。
  アプリの欠陥を、この分類に入れない（確認で通った組の失敗は不合格のまま）
- 確認の 25 秒のあとで状態が変わる可能性は消えていない。確認と食い違う組が出たらまとめに残るので、そこから見直す
