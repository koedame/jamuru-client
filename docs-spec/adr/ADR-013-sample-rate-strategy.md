# ADR-013: サンプリングレート戦略

## Context

P2P音声通信において、サンプリングレートの扱いを決定する必要がある。

### 検討事項

1. **固定 vs ユーザー選択**: サンプリングレートを固定にするか、ユーザーが選択できるようにするか
2. **通信相手との整合性**: 送信者と受信者のサンプリングレートが異なる場合の対応
3. **リサンプリングの実行箇所**: 送信側と受信側のどちらで変換するか

### 選択肢ごとの特性

| サンプリングレート | 音質 | 負荷 | 遅延（128samples時） | 帯域（PCM 16bit mono） |
|------------------|------|------|---------------------|----------------------|
| 44.1 kHz | CD品質。可聴域十分 | 最軽量 | 2.9ms | 705 kbps |
| 48 kHz | プロオーディオ標準 | 軽量 | 2.67ms | 768 kbps |
| 96 kHz | 超高周波対応 | 2倍 | 1.33ms | 1.54 Mbps |

**補足**: 96kHzと48kHzの可聴域での音質差は科学的に証明されていない。96kHzの利点は主に編集時のヘッドルームとエイリアシング軽減。

### リサンプリング実行箇所の比較

| 観点 | 送信側で変換 | 受信側で変換 |
|------|------------|------------|
| 送信遅延 | 変換分増加 | なし |
| 受信遅延 | なし | 変換分増加 |
| 送信側CPU負荷 | 高 | 低 |
| 受信側CPU負荷 | 低 | 高（参加者数に比例） |
| プロトコル複雑度 | 低（統一レート） | 中（レート情報必要） |

**重要**: 送信側でリサンプリングすると、その遅延が全ての受信者に影響する。受信側でリサンプリングすれば、変換が必要な受信者のみが遅延を負担する。

## Decision

### 1. サンプリングレートはユーザー選択可能

選択肢: 44100 / 48000 / 96000 Hz

理由:
- オーディオインターフェースによって対応レートが異なる
- DAWとの連携時、プロジェクト設定に合わせる必要がある

### 2. デフォルト・推奨値は 48 kHz

理由:
- プロオーディオ/映像業界の標準
- ほぼ全ての現代のオーディオ機材がネイティブ対応
- 44.1kHzより高品質、96kHzより実用的

### 3. 異なるサンプリングレート間の通信を許可

各参加者は自分の機材に最適なサンプリングレートで動作できる。

### 4. リサンプリングは受信側で実行

```
送信: キャプチャ(ネイティブレート) → パケット化 → 送信
受信: 受信 → 必要に応じてリサンプリング → 再生
```

理由:
- **低遅延優先**: 送信パスに余計な処理を入れない（ADR-008の方針に合致）
- **遅延の局所化**: 変換が必要なユーザーのみが遅延を負担
- **柔軟性**: 受信側が品質と遅延のトレードオフを選択可能

### 5. 同一サンプリングレート時はパススルー

送信者と受信者が同じサンプリングレート（推奨: 48kHz）の場合、リサンプリングをスキップして遅延ゼロを実現。

```rust
// 受信時の処理（擬似コード）
fn process_received_audio(packet: AudioPacket, my_sample_rate: u32) -> AudioBuffer {
    if packet.sample_rate == my_sample_rate {
        // パススルー（変換なし、遅延ゼロ）
        packet.audio_data
    } else {
        // リサンプリング（このユーザーのみ遅延追加）
        resample(packet.audio_data, packet.sample_rate, my_sample_rate)
    }
}
```

### 6. パケットヘッダにサンプリングレートを含める

受信側がリサンプリングの要否を判断するため、送信側のサンプリングレートをパケットに含める。

## Consequences

### メリット

- **最低遅延の実現**: 推奨設定（48kHz）同士ならリサンプリング不要
- **機材互換性**: 各自が最適なサンプリングレートを使用可能
- **送信パス最適化**: zero-latencyモードでも送信側に余計な処理が入らない

### デメリット

- **受信側負荷**: 参加者が増えると、異なるレートの音源ごとにリサンプラーが必要
- **プロトコル複雑化**: パケットにサンプリングレート情報が必要
- **ユーザー教育**: 最低遅延には48kHz推奨であることを伝える必要

### 想定されるケース

| 送信側 | 受信側 | 処理 | 遅延影響 |
|--------|--------|------|---------|
| 48kHz | 48kHz | パススルー | なし |
| 48kHz | 96kHz | 受信側で変換 | 受信者のみ |
| 96kHz | 48kHz | 受信側で変換 | 受信者のみ |
| 44.1kHz | 48kHz | 受信側で変換 | 受信者のみ |

### UI/UX への反映

- 設定画面で48kHzに「（推奨）」を表示
- 異なるサンプリングレートの参加者がいる場合、接続情報画面で通知
- zero-latencyプリセット使用時、48kHz以外を選択していたら警告
