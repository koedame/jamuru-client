# ADR-088: Windows の WASAPI のデバイスを、排他モードと低遅延の共有モードでも開けるようにし、設定で選ばせる

## Status

Accepted

## Context

Windows で ASIO ではないデバイスは、cpal の WASAPI 共有モードで開いていた。共有モードでは、アプリの音は Windows のオーディオエンジン（ミキサー）を通り、
ミキサーが動く周期（多くのドライバで 10 ms 固定）ごとに受け渡される。バッファサイズをいくら小さくしても、片道に周期ぶんの遅延が乗る。
Windows の実機で入力から出力までの往復を測ると、WASAPI の共有モードは 36〜46 ms、同じ端末の ASIO は 9〜11 ms だった。ASIO のドライバが無いデバイス（内蔵のオーディオ・
多くの USB のヘッドセット）を使う人は、遅延を縮める手段を持っていなかった。

WASAPI には、ミキサーを通さない開き方がほかに 2 つある。

- **排他モード**（`IAudioClient::Initialize` に `AUDCLNT_SHAREMODE_EXCLUSIVE`）: デバイスをアプリだけで使い、デバイスが許す最小の周期（多くは 3 ms 前後）で受け渡す。
  そのあいだ、ほかのアプリはそのデバイスで音を出せない。デバイスはミキサーの形式ではなく、自分が受け付ける形式（ビット数・レート）で開く必要がある。
- **低遅延の共有モード**（Windows 10 から。`IAudioClient3::InitializeSharedAudioStream`）: ミキサーを通したまま、ドライバが許す周期のうち短いものを選ぶ。
  ほかのアプリも鳴らせるが、短い周期を許すドライバでしか速くならない（標準の周期しか許さないドライバでは、標準と同じ遅延になる）。

どちらが効くかはデバイスとドライバで決まり、排他モードにはほかのアプリの音を止めるという代わりがある。1 つに決めて全員に当てることはできない。

## Decision

設定に「WASAPI のモード」を足し、**標準の共有モード・低遅延の共有モード・排他モード**の 3 つから選ばせる。既定は標準の共有モード（これまでと同じ挙動）。
設定は、いま使っているデバイスについて、それぞれのモードが**推奨・非推奨・使えない**のどれかと、その理由と周期を出す。

### 開き方

- **標準の共有モード**は cpal のまま開く（これまでと同じ経路）。
- **排他モードと低遅延の共有モード**は、cpal がこの 2 つを提供しないので、アプリが WASAPI を直接呼んで開く（`src/audio/wasapi.rs`）。ストリームごとにスレッドを 1 つ持ち、
  そのスレッドで COM（マルチスレッドのアパートメント）に入ってデバイスを開き、周期ごとのデバイスのイベントで起きて、cpal と同じ形（インターリーブの `f32`）で
  エンジンのコールバックに渡す。コールバックのスレッドは ADR-087 と同じく MMCSS に登録する。エンジンから見ると、どちらの経路でも同じコールバックが呼ばれる。
- **排他モード**の周期は、セッションの 1 フレーム（バッファサイズ）とデバイスの最小の周期の長い方（デバイスの単位の 100 ns で切り上げて求める。最小の周期をわずかでも下回る値は断られる）。デバイスが周期をそのまま受けない
  （`AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED`）ときは、デバイスが返した大きさで開き直す。形式は、セッションのレート → ミキサーのレート → ほかに使えるレートの順に、
  `f32` → 24 bit（32 bit の入れ物）→ 32 bit → 24 bit → 16 bit の順で、デバイスが受ける最初のものを使う。セッションと違うレートで開いたら、cpal の経路と同じくアプリが変換する。
  - 排他モードにしても音質は落ちない。共有モードでも、デバイス自体は Windows の設定にある形式（排他モードで受ける形式のどれか）で動いており、16 bit しか受けないデバイスは
    共有モードでも 16 bit で鳴っている。
- **低遅延の共有モード**の周期は、ドライバが許す周期（`GetSharedModeEnginePeriod` の最小値から基本単位刻み）のうち、セッションの 1 フレームが収まる最小のもの。
  ほかのアプリがミキサーを別の周期で動かしている（`AUDCLNT_E_ENGINE_PERIODICITY_LOCKED`）ときは、その周期で、新しいクライアントで開き直す（一度失敗したクライアントは使わない）。
- **デバイスを選んでいない側（Windows の既定のデバイス）**も同じモードで開き、Windows が既定のデバイスを切り替えたらストリームを止めて開き直す（cpal が既定のデバイスで開いたストリームと同じ。`IMMNotificationClient`）。
- **ASIO のデバイスには効かない。** ASIO のデバイスは ASIO のドライバで開く。入力か出力の片方だけが ASIO なら、WASAPI の側にだけ効く。

### 選んだ方式で開けなかったとき

Windows のサウンドの設定でアプリによる排他的な制御が許されていない・ほかのアプリがそのデバイスを共有モードで鳴らしていて、Windows の設定が排他モードのアプリを優先しない・デバイスが受ける形式が無い、などで開けなかったときは、
**同じコールバックで標準の共有モードで開き直し、セッションは止めない。** 開き直すのは開けなかった側だけで、開けた側はそのモードのまま動く。
どちらで開いたか（と開けなかった理由）はセッションの状態（`streaming_status` の `wasapi_opened`）に出し、メイン画面がその理由を数秒知らせる。
ほかのアプリがそのデバイスを排他モードで使っているときは、標準の共有モードでも開けない（Windows がそのデバイスをほかのアプリに渡さない）。そのときは、これまでと同じくデバイスを開けなかったと知らせる。
Windows の既定の設定（アプリによる排他的な制御を許し、排他モードのアプリを優先する）では、ほかのアプリがそのデバイスを共有モードで鳴らしていても排他モードで開け（Windows の実機で確かめた）、そのあいだミキサーはデバイスに音を渡さないので、そのアプリの音は止まる。
排他モードの形式を尋ねて、形式の答え（`AUDCLNT_E_UNSUPPORTED_FORMAT`）でない失敗が返ったとき（ほかのアプリが使っている・排他的な制御が許されていない）は、
形式が無いとは扱わず、その失敗を理由にする。
開いたあとにデバイスが無くなった（`AUDCLNT_E_DEVICE_INVALIDATED`）ときは、cpal の経路と同じ「デバイスを失った」扱いにする。デバイスのイベントが止まったときも、
デバイスにまだあるかを尋ねて気づく（抜かれた機器はイベントを出さなくなる）。
開くのが時間の上限を過ぎて、あとから開いたストリームは、その間に開き直したストリームの記録を上書きしない（記録はストリームを頼んだ順に番号を付ける）。

### 推奨と非推奨

設定は、使っている入力と出力のデバイスが何に対応しているかを、**ストリームを開かずに**読む（`IAudioClient::GetDevicePeriod`・`IAudioClient3::GetSharedModeEnginePeriod`・
`IsFormatSupported` の排他モード）。読むのは使っているデバイス（と、切り替え先のデバイス）だけで、デバイスの一覧と同じ時間の上限で諦める。
答えないデバイス（このアプリが排他モードで開いている・ドライバが固まっている）は、最後に読めた値を使う。読み出しが戻らない間は次の読み出しを重ねず、
最後に読めた値を出す（デバイスの一覧と同じ。ADR-050）。Windows が排他的な制御を許していないデバイスは、排他モードの形式を尋ねると
許されていないとだけ返す（`AUDCLNT_E_EXCLUSIVE_MODE_NOT_ALLOWED`）。これは答えないのではなく「排他モードでは開けない」という答えなので、
最後に読めた値には戻らず、排他モードを使えないとする。判定は次のとおり（`wasapi_mode::advise`）。
片道の遅延は、周期と 1 フレームの長い方として比べる。

| モード | 推奨 | 非推奨 | 使えない |
|---|---|---|---|
| 排他モード | WASAPI の側すべてに排他モードで開ける形式があり、標準より遅延が短くなる側がある | 1 フレームが標準の周期より長く、遅延が変わらない・読めない側がある（選べば試す） | Windows が排他的な制御を許していない側（理由に、デバイスのプロパティで許す方法を添える）・排他モードで開ける形式が無い側がある |
| 低遅延の共有モード | 標準より遅延が短くなる側がある | 標準と同じ周期になる・1 フレームが標準の周期より長く、遅延が変わらない・読めない側がある | Windows に低遅延の共有モードが無い |
| 標準の共有モード | ほかに推奨のモードが無い | ほかに推奨のモードがある | （無い） |

使えないモードは選べない。保存してあるモードが、切り替えたデバイスで使えなくなったときは、選んだまま表示し、開けない側は標準の共有モードに戻る（上の「開けなかったとき」）。
画面の遅延の表示は、バッファの長さと、選んだモードでその側が動く周期の長い方を片道として出す（選んだモードで開けない側は標準の周期）。
排他モードの注意書きは、選べるときと、選んだまま一部の側だけ排他モードで開くときに出す。

メイン画面の遅延（参加者の行の↑↓と内訳）と、相手に伝える自分の取り込み・再生のバッファも同じ数え方にする（REQ-AUD-043）。
各側は、セッションのバッファの長さと、その側が実際に開いた方式の周期（開いたときにアプリが選んだ・読んだ値）の長い方。
相手が受け取る値も同じなので、相手の画面の「相手の取り込み・再生」もモードに応じて変わる。
ドライバが報告する遅延（CoreAudio の latency・ASIO の入出力遅延・WASAPI のストリームの遅延）までは数えない。OS ごとの読み方が要るので、必要になってから別に決める。

### 設定として

- 設定ファイルの `wasapi_mode`（`shared` / `low_latency` / `exclusive`）。この項目の無い古い設定ファイルは `shared` として読む。
- 変えると、部屋にいれば部屋を出ずに音声のセッションだけをやり直す（バッファサイズと同じ）。設定の手伝い（ADR-044）からも同じ変更（`{"setting": "wasapi_mode"}`）で変えられ、
  手伝いの終わりに元に戻す設定にも入る。
- Windows 以外と、WASAPI のデバイスが 1 つも無いときは、設定にこの項目を出さない（設定の応答の `wasapi` が無い）。

## Consequences

- ASIO のドライバが無いデバイスでも、排他モードで往復の遅延を ASIO に近いところまで縮められる。ドライバが短い周期を許すデバイスなら、共有のまま縮められる。
- 既定は変えないので、選ばない人の挙動は変わらない。排他モードを選んだ人は、そのあいだほかのアプリの音がそのデバイスから出ない。Windows の既定の設定では、先に鳴らしていたアプリの音も止まる（設定の注意書きで先に知らせる）。
- アプリが自分で持つ WASAPI のコード（`src/audio/wasapi.rs`）を保守する。cpal の WASAPI の実装と同じ役目を、2 つの開き方の分だけ持つ。
- 依存は増えない（`windows` クレートの機能を足しただけ）。

## Verification

- Windows の実機で、同じデバイス・同じバッファサイズのまま、3 つのモードで入力から出力までの往復の遅延を測って並べる。
- 排他モードを選んだうえで、ほかのアプリに同じデバイスを共有モードで鳴らさせたまま排他モードで開けること、ほかのアプリに排他モードで使わせると、これまでと同じくデバイスを開けなかったと知らせることを確かめる。
  開けなかった側を標準の共有モードで開き直すこと（排他的な制御が許されていない・形式が無い）は、開き直しの単体テストで確かめる。
- Windows の設定で出力のデバイスの排他的な制御を許さないようにして、排他モードを選んだまま入ると出力だけ標準の共有モードで開き直してメイン画面がそう知らせること、
  設定がそのデバイスでは排他モードを使えないと出し、許す方法を添えることを確かめる。許し直すと、排他モードが推奨に戻ることも確かめる。
- 設定の画面で、使っているデバイスに対する推奨・非推奨・使えないと周期が、測った結果と食い違わないことを確かめる。
