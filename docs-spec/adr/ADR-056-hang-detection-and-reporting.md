# ADR-056: 主スレッドの見張りと、正常終了しなかった前回の起動の報告

## Status

Accepted. [ADR-037](./ADR-037-usage-reporting-opt-in.md) / [ADR-042](./ADR-042-usage-reporting-includes-investigation-data.md) の送る/送らないの原則はそのまま、`hang` という新しい種類のイベントを 1 つ足す。[ADR-055](./ADR-055-restart-does-not-wait-for-the-main-thread.md) が個別に直した「再起動が主スレッドの停止で進まない」不具合を、今後同じことが一般の利用者の環境で起きたときに気づける仕組みに一般化する。

## Context

ある版で、終了処理の中で利用状況の送信を待つ呼び出し（`UsageState::app_exiting` の `block_on`）が返らなくなり、アプリが固まって
再起動もできない不具合が開発中に 2 度起きた（[ADR-055](./ADR-055-restart-does-not-wait-for-the-main-thread.md) はそのうち
1 つ、再起動の経路を直したもの）。今回は手元で気づけたが、正式にリリースした後に一般の利用者の環境で同じ種類の不具合が起きても、
今の仕組みでは何も届かない。

- 利用状況の送信（REQ-TEL）はエラーとセッションの集計を送るが、固まりは記録しない
- パニックの記録（REQ-TEL-008）は、固まりがパニックでない以上残らない
- 遠隔デバッグはベータ版限定で、正式版には無い

## Decision

### 1. アプリの中で気づく（`usage_reporting` の設定に関わらず動く）

1. **区間の種類は 4 つ用意する**（`HangStage`: `app_exit` / `restart` / `update_apply` / `device_open`）。
   実際にガードを差し込んだのは終了処理（`lib.rs` の `RunEvent::Exit`）と再起動（`restart.rs`。ADR-055 が単独で持っていた
   「10 秒待って新しいプロセスを起こす」仕組みに、その瞬間の記録を 1 行足しただけ）の 2 つ。**更新の適用と音声デバイスを開く
   処理は、どちらも呼び出し元がすでに詰まらない作り**（更新は `tokio::time::timeout`（REQ-UPD-016）、デバイスは
   [ADR-050](./ADR-050-device-calls-are-bounded.md) の `bounded()`。上限を過ぎたら呼び出し元へ即座にエラーが返り、
   詰まったスレッドは置き去りにして続行する）で、失敗はすでに `error` イベント（`device_open_failed` 等）で届く。
   そのため今回はガードを差し込まず、区間名は将来同じ形の不具合が見つかったときのために予約するだけにした。
2. **区間ごとに自分の上限時間**（終了処理 5 秒・再起動 8 秒・更新の適用 20 秒・デバイスを開く処理 3 秒。デバイス呼び出しは
   [ADR-050](./ADR-050-device-calls-are-bounded.md) が別に上限を持つので、この値はそれより外側）を持ち、見張りの
   スレッド（`tokio` のタスクではなく素の OS スレッド。詰まっているのが `tokio` 自身のこともあるため）が 1 秒おきに確かめる。
   上限を超えたら、どの区間で・何ミリ秒たっていたかを 1 回だけローカルに書く（`hang.json`。既存の `crash.json` と同じ置き場）。
   上限に達する前に区間が終われば何も残らない。
3. **見張っている区間が無いまま前回の起動が正常終了しなかったとき**（強制終了・電源断など）も同じ形で拾う。起動のたびに
   「動いている」印（`running.json`）を書き、`RunEvent::Exit` の最後で消す。次の起動時にこの印が残っていれば、
   区間名は「不明」（`unknown`）、経過時間は無しとして記録する。区間の記録（2）があれば、より詳しい情報としてそちらを優先する。
4. **ローカルの記録は `usage_reporting` の設定を見ない。** 固まりに気づくこと自体は同意の要らない診断機能とし、
   何を・いつ送るかだけを次の 2 で同意にかける。診断ログ（`jamjam.log`、ADR-036）とは別の経路のまま
   （ADR-037 決定 7 を踏襲）。

### 2. 同意を取って送る

5. **`usage_reporting` が既にオンなら、次の起動でパニックの記録と同じように自動で送る**（利用者に確認しない。
   既にオンにした人は、この種類の記録も届くことに同意済みという扱い）。
6. **`usage_reporting` がオフのときは、その場で聞いて 1 件だけ送れるようにする。** 設定の Diagnostics タブに
   前回の記録が残っていれば専用の案内を出し、「送る」を選ぶとその 1 件だけを送る。送信は、送るためだけに作って
   送信後に捨てるインストール ID を使う（既存の `usage_reporting` の切り替えを一時的に借りて、送信後に必ずオフへ戻す。
   REQ-TEL-020）。**これは `usage_reporting` 自体をオンにしない**。「送らない」を選べば記録は捨てる。
   起動のたびに繰り返し聞かない（1 回読んだ記録はディスクから消え、次に何かが起きるまで再び聞かれない）。
7. **送る内容は、`hang` イベント（区間名・経過時間）だけ**。ADR-036 が診断ログ (`jamjam.log`) に書いている、
   サーバー URL・デバイス名・ルーム ID を含みうる**生のログを添えて送る機能は今回は作らない**（§4 の「決めたいこと」）。

### 3. こちらで気づいて直しに向かう（サーバー側。閾値・受け口は非公開側）

8. `hang` は既存の利用状況の送信の経路（`POST /api/v1/usage-logs`）にそのまま乗る。**受け口（jamjam-server）が
   新しい `schema.json` に追いつくまでは、この行を捨てる**（ADR-042 決定 5 と同じ扱い）。
9. 版ごとに固まり・パニック・強制終了の件数を数え、増えたら起票する仕組みと、悪い版の配布を止める仕組みは、
   サーバー側の閾値・受け口の認証を伴うため**非公開側で設計・実装する**（このリポジトリには何も書かない。
   `.claude/rules/public-repo-private-info.md`）。

## Reasons

- **区間ごとの上限時間を主スレッドの「脈」ではなく経過時間で測る**方式にした。案として、見張りスレッドが定期的に
  `AppHandle::run_on_main_thread` で主スレッドに小さな仕事を頼み、それが返るかで生死を測る方式も検討したが、
  今回見張る 2 区間（終了処理・再起動）はどちらも「アプリが終わろうとしている最中」そのものであり、区間の外側で
  主スレッドが別の理由で詰まっているのを拾う需要が今は無い。経過時間だけの方式は依存が少なく、テストも本物の
  待ち時間なしに書ける（開始時刻を過去にずらすだけで上限超えを再現できる）。将来、区間の外側の詰まりを拾う要求が
  出たら見直す。
- **`hang.json` を `usage_reporting` の切り替えの対象外にした。** 既存の `discard()`（オフにしたときに消すファイルの一覧）に
  `hang.json` を加えなかったのは、既定オフの利用者が起動するたびに記録が消えてしまうと、2 の「オフのときに聞く」が
  機能しなくなるため。

## Consequences

- 一般の利用者の環境で終了処理・再起動が詰まっても、次の起動でローカルに記録が残り、`usage_reporting` がオンの
  利用者からは既存の経路で自動的に届く。オフの利用者にも、その場で 1 回だけ送るかどうかを聞ける。
- 更新の適用・デバイスを開く処理は、呼び出し元が詰まらない作りである前提のまま区間のガードを持たない。
  その前提が崩れる不具合（`tokio::time::timeout` 自体が効かないほどランタイムが詰まる等）が見つかったら、
  終了処理・再起動と同じ形でガードを差し込む。
- 生ログを添える「問題を報告」ボタン（提案の原文にあった機能）は、この ADR の範囲では作っていない
  ([ADR-058](./ADR-058-report-a-problem.md) で作った)。1.0.0 より前は、本 ADR の確認自体にもそのログを
  添えて送る ([ADR-059](./ADR-059-hang-report-attaches-the-log-before-1-0-0.md))。
