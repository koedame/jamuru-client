# ADR-043: アプリの操作はすべて名前付きのコマンド（RPC）にする。E2E は全部を、相手の設定の手伝いはその一部を呼ぶ

## Status

Accepted

## Context

jamjam を独力で使い始めるには、オーディオインターフェースの入出力・チャンネル・バッファサイズといった専門的な設定が要る。
使い慣れた人が、同じルームにいる相手の設定を**遠隔でしてあげられる**機能が欲しい。求められていることは次のとおり。

- 安全性と誤操作を考え、設定する側は**設定変更を申請**し、設定される側が**許可を押して**初めて変わる
- 設定する側も設定される側も、**いつでも遠隔設定を止められる**
- 変更のたびに、チャット欄に「A さんが B さんの ○○ 設定を変更しました」と出る

あわせて、**E2E テストからアプリを遠隔操作しやすい**設計にしたい。全機能を呼び出せる遠隔操作の口を用意し、
利用者向けの遠隔設定はその一部を使う形にする。

作り始める前の状態には、これを阻むものが 3 つあった。

1. **E2E は画面（DOM）経由でしかアプリに触れなかった**（[ADR-025](./ADR-025-gui-e2e-control-channel.md)）。
   状態を整えるだけでも画面を 1 段ずつたどる必要があった
2. **設定の変更が画面の中で組み立てられていた。** 設定ウィンドウの Adapter が「デバイスを選ぶ」「設定を保存する」
   「接続中のセッションに伝える」を別々のコマンドで順に呼び、検査もそれぞれにあった。遠隔から同じ変更を
   するには同じ手順をもう 1 つ書くことになる。実際に食い違いも起きていた（下記「直した欠陥」）
3. **シグナリングで知らない種類のメッセージが届くと、接続が切れた扱いになっていた。**
   相手とメッセージをやり取りするためにサーバーへ種類を足すと、配布済みのアプリはルームから落ちる

## Decision

### 1. アプリの操作は名前付きのコマンドで、それが RPC の一覧になる

アプリの操作はバックエンドのコマンド（`src-tauri/src/lib.rs` の `generate_handler!` に並ぶもの）として持つ。
**この一覧がそのまま RPC の一覧**であり、呼び出し口ごとに「どこまで呼べるか」だけが違う。

| 呼び出し口 | 呼べる範囲 | 経路 | 誰が |
|-----------|-----------|------|------|
| 画面 | 全部 | webview の IPC | アプリ自身の UI |
| E2E の制御チャネル | **全部** | `POST /e2e/invoke` → webview の IPC | テスト（`e2e-control` feature のビルドだけ。ループバックのみ。認証は無いので、このビルドは配らない） |
| 相手の設定の手伝い | **音声の設定の取得と変更だけ**（`settings_get` / `settings_change`） | シグナリングサーバーの中継 | 同じルームの、許可された相手 |

- E2E は画面と同じ IPC を通す。引数名の変換や公開ビルドの権限まで、画面と同じ道を検証の中に残すためである。
  コマンドを足せば、制御チャネルを直さずにそのまま呼べる
- **1 つの操作は 1 つのコマンドで完結させる。** 画面が複数のコマンドを順に呼んで状態を持つ操作は、呼び出し口に
  よって結果が変わる（E2E から個々のコマンドを呼んでも画面の状態が追従しない）。画面で組み立てている操作は、
  遠隔から呼ぶ必要が出た時点でバックエンドの 1 コマンドに寄せる。今回は音声の設定を寄せた（次節）。
  ルームへの参加など他の操作は、E2E からは画面のページオブジェクトで行う

### 2. 音声の設定は `settings_change` の 1 か所で適用する

`src-tauri/src/settings.rs` が音声の設定の変更をすべて持つ。

- `settings_change(change)` は 1 件の `SettingChange`（`{"setting": "buffer_size", "samples": 128}` のように、
  設定の名前で区別する）を受け、**提供されている値かを検査し、保存し、接続中のセッションが即座に追従できる
  ものは伝え、変更後の設定を返す**。同時に全ウィンドウへ `audio:config-changed`（ペイロードは変更後の設定）を送る
- 対象は入力・出力デバイス、入力・出力チャンネル、送信チャンネル数、バッファサイズ、サンプルレート、プリセット
- 何をするかの判断（`plan`）は、現在の設定と提供されているデバイスだけから決まる純粋な関数にし、単体テストで検証する
- **設定の置き場所は `config.toml` の 1 か所にする。** これまでの `AudioState`（選んでいるデバイスとバッファサイズの控え）は廃止し、
  ストリーミングの開始も保存済みの設定を読む（画面から値を渡さない）
  （[ADR-026](./ADR-026-gui-audio-path.md) で入れた「起動時に保存した選択を効かせる」は、設定を直接読むことで引き続き満たす）
- **設定の書き込みは、読み・変更・保存を 1 つのロックの中で行う**（`ConfigState::update_with`）。同時に来た 2 つの変更の
  片方がもう片方を黙って戻すことをなくす。保存に失敗した変更は、メモリ上でも効かせない。
  設定全体を上書きするコマンド（`config_save`）は廃止し、利用状況の送信のスイッチは専用のコマンドにした
- チャンネルは**片側ずつ**変える（`{"setting": "input_channel", "side": "right", "channel": null}`。R の `null` はモノラル）。
  もう片方は保存済みの値を使うので、素早い 2 回の変更が前の変更を戻さない
- 変更には通し番号（`revision`）を付ける。設定ウィンドウは、変更の答え・通知・読み込みが前後して届いても、古いもので上書きしない
- デバイスのチャンネル数は、その向き（入力なら入力）の申告だけから取る。申告が無いデバイスは「不明」とし、2ch とみなさない
  （使用中で申告できないデバイスで、選んであったチャンネルを推測で拒まないため）
- バッファサイズとサンプルレートは**次の接続から**効く。フレームサイズは接続中の音声エンジンの寿命のあいだ固定だからである
  （プリセットの切り替えと同じ扱い。REQ-LAT-106）
- 設定ウィンドウは値を持たず、返ってきた「変更後の設定」と `audio:config-changed` をそのまま表示する。
  選択肢（デバイス・チャンネル数・バッファサイズ・サンプルレート）もバックエンドが返したものを出す

#### 直した欠陥（画面で組み立てていたことによるもの）

| 欠陥 | 原因 |
|------|------|
| バッファサイズに 8・16 サンプルを選べたが保存されず、次の起動で元に戻っていた | 画面の選択肢と、設定の検査（32・64・128・256）が別々に定義されていた |
| 診断の「推奨プリセットを適用」が、プリセットの定義と違うバッファサイズを入れていた | 画面がプリセットとバッファサイズの対応表を独自に持っていた |
| プリセットを変えても、次の接続のバッファサイズが変わらなかった | 選択が `AudioState` と設定の 2 か所にあり、プリセットは設定だけを変えていた |
| 接続中にバッファサイズを変えると音声が途切れた | 画面がストリーミングを止めて開き直しており、新しいソケットの番号を相手が知らなかった（サンプルレートも既定値に戻っていた） |
| サンプルレートを変えても、セッションは常に 48 kHz で動いていた（ミキサーの表示だけが変わっていた） | 画面がストリーミングの開始にサンプルレートを渡しておらず、既定値が使われていた |
| 入力デバイスのチャンネルの選択肢に、出力側にしか無いチャンネル数が混ざっていた | デバイスの能力を、入力と出力の申告を合わせて数えていた |
| 利用状況のスイッチを切り替えると、その間に別の場所でした設定の変更が戻ることがあった | 画面が設定全体を読んで 1 項目を変えて書き戻していた |

### 3. 相手の設定の手伝いは、許可された間だけ、変更は 1 件ずつ申請して許可をもらう

**同意の単位は 2 段にする。**

1. **手伝いの開始**: 設定する側（手伝う人）が相手を選んで「設定を手伝う」を申請する。設定される側に
   「A さんがあなたの設定を手伝おうとしています」と出て、**許可**すると手伝いが始まる。許可すると、手伝う人は
   相手の音声の設定（`settings_get` の内容。デバイス名を含む）を見られるようになる。
   **デバイス ID は渡さない。** ID には機器のシリアル番号が入りうる（`jamjam.log` でも伏せている。REQ-GUI-022）ので、
   手伝われる側が手伝いのあいだだけ使う仮の名前に置き換えて渡し、変更の申請に付いてきた仮の名前を自分で ID に戻す
2. **変更 1 件ごと**: 手伝う人が相手の設定を変えると、その変更が**申請**として届く。設定される側に
   「A さんが入力デバイスを ○○ に変更しようとしています」と出て、**許可**したものだけが `settings_change` で適用される。
   拒否したもの・答えないまま手伝いが終わったものは適用されない

- 変更 1 件ごとに許可を求めるのは、要求にある「誤操作を想定して」に応えるためである。開始の許可だけでは、
  手伝う人の選び間違いがそのまま相手の設定になる。
  - 却下: 開始の許可だけで、以後の変更は即座に適用する。手伝う人の誤操作を止める手段が「停止」しか無くなる
  - 却下: 開始の許可を省き、変更ごとの許可だけにする。相手の設定（デバイス名）を、許可の前に読めてしまう
- **どちらの側からもいつでも止められる。** 止めると、未回答の申請は捨てられ、以後の申請は受け付けない。
  相手が退室した・自分が退室した・シグナリングの接続が切れたときも終わる。手伝いの状態はメモリにだけ持ち、
  アプリを起動し直すと残らない
- 手伝いは同時に 1 本ずつ（設定される側としても、手伝う側としても）。手伝われている最中に別の人から来た開始の申請は、
  自動で断る
- **変更が適用されるたびに、ルームのチャットに記録が出る。** 「A さんが B さんの入力デバイス設定を変更しました」。
  文は受け取った各アプリが自分の言語で組み立てる（送るのは「誰が・誰の・どの設定を」だけ）。手伝いの開始と終了も同じ形で出る
- 手伝う人が呼べるのは `settings_get` と `settings_change` だけである。受け取る側は、呼び出しの名前ではなく
  **型で受ける**（知らないものは読めずに捨てる）ので、一覧に無い操作はそもそも表現できない。
  チャンネルやデバイスの検査は、手元で変えるときと同じ `plan` が行う

### 4. 相手とのやり取りはシグナリングサーバーが中継し、送り主はサーバーが付ける

- 相手に宛てたメッセージを、シグナリングサーバーが**同じルームの宛先にだけ**届ける。送り主は、メッセージに
  書かれた名前ではなく**サーバーがその接続の参加者として付ける**（チャットと同じ。なりすましを防ぐ）
- 中身はアプリ同士の取り決めで、サーバーは解釈しない。遠隔設定の手順を変えても、サーバーは変えずに済む
- 中継を受け取れるアプリは、ルームに入るときにそのことを知らせる。**受け取れない相手（古い版）には、
  手伝いの申請を出さない**（画面に出さない）。サーバーも、受け取れると知らせていない相手には届けない
  - 却下: 音声の UDP で送る。相手の証明が無く（IP アドレスは偽れる）、届いたかどうかも保証されない。
    申請と許可は取りこぼすと意味が変わる
  - 却下: チャットのメッセージに埋め込む。誰でも同じ文面を打てるうえ、利用者の言語に訳せず、チャット欄を汚す

### 5. 知らない種類のシグナリングメッセージは読み飛ばす

`SignalingConnection::recv()` は、`type` を知らないメッセージを捨てて次を待つ（REQ-CON-030）。
これが、サーバーにメッセージの種類を足す前提である。知っている種類なのに読めないメッセージは、非互換として従来どおり失敗にする。

## Consequences

### メリット

- E2E から全機能に届く。状態を整えるのに画面をたどらずに済み、ページオブジェクトの無い機能も試せる
- 音声の設定は、画面・E2E・遠隔設定のどこから変えても同じ処理を通る。遠隔設定のために手順をもう 1 つ書かない
- 設定を変えた人が誰でも、開いている全ウィンドウに変更後の設定が届く
- 画面で組み立てていたことによる 4 つの欠陥が消えた

### デメリット

- 画面が組み立てている操作（ルームへの参加など）は、まだ E2E から 1 コマンドでは呼べない
- 変更 1 件ごとに許可を押すので、設定される側の操作は増える（開始の許可 + 変更の数）
- 遠隔設定は、中継を受け取れる版どうしでしか使えない

### 実装の順序

1. RPC の一覧化・`/e2e/invoke`・`settings_change` への集約・知らないメッセージの読み飛ばし
2. シグナリングサーバーの中継と、受け取れることの知らせ
3. 手伝いの申請・許可・停止、チャットへの記録、画面
