# ADR-060: 送信オンの端末の自動の固まり報告にも `jamjam.log` を添える

## Status

Superseded by [ADR-065](./ADR-065-personal-information-before-1-0-0.md)

## Context

[ADR-056](./ADR-056-hang-detection-and-reporting.md) 決定 5 は、`usage_reporting` が既にオンの端末では、前回の起動が
正常終了しなかったことを次の起動が見つけたとき、確認を挟まずクラッシュと同じように自動で構造化された `hang` イベント
（区間名・経過時間）を送る。[ADR-059](./ADR-059-hang-report-attaches-the-log-before-1-0-0.md) はその後、`usage_reporting`
がオフの端末が確認画面で「送る」を選んだときに限り、`jamjam.log` も追加で送るようにしたが、**オンの端末の自動送信は
対象にしなかった**。

実機での確認で、この抜けが実際に影響した: 検知した固まりはすべて `usage_reporting` がオンの端末（検証ユーザーは
ほぼこちらを使う）で起きており、利用ログには構造化された `hang` イベント（区間名が「不明」）は届いたが、
`jamjam.log` は付かず、どの区間で何が起きていたかを追う材料が無かった。1.0.0 より前は検証ユーザーだけがアプリを
使うという ADR-059 の前提はオンの端末にも変わらず当てはまるのに、確認画面を経由するかどうかで送る内容が
変わってしまっていた。

## Decision

1. **`usage_reporting` が既にオンの端末でも、アプリの版が 1.0.0 未満の間は、前回の起動が正常終了しなかったことを見つけて
   自動で送る `hang` イベントに、`jamjam.log` を追加で送る。** 版の判定は ADR-059 と同じ `attaches_log`
   （`src-tauri/src/usage.rs`）を再利用する。1.0.0 以上ではこの追加送信をしない。
2. **送信は ADR-059 と同じ経路を再利用する**（`report_problem::send_log_report`。ADR-058「問題を報告」の送り先・
   本文の作り方・マスク・切り詰めをそのまま使う）。新しい受け口は作らない。
3. **コメントには区間名と今回の起動 ID を機械的に埋める**（`hang_report_comment`、ADR-059 と共通）。利用ログ側の
   構造化された `hang` イベントは既に `launch_id` を持つので、同じ値がサーバー側で両者を突き合わせる印になる。
4. **確認は挟まない。** ADR-056 決定 5 のとおり、既にオンにした時点で利用者は記録が送られることに同意済みという扱いを、
   ログの添付にもそのまま広げる。オフの端末（ADR-059 の確認画面の対象）とは異なり、聞き直さない。
5. **ログの送信は失敗しても構造化イベントの送信を失敗にしない。** ADR-059 と同じく `tracing::warn!` に残すだけで、
   利用者には何も見せない（この経路には見せる画面自体が無い）。
6. **1.0.0 を出すときに ADR-059 と一緒に見直す。** 判定が同じ `attaches_log` にまとまっているので、直す場所は 1 つ。

## Reasons

- **ADR-059 が新しい受け口を作らない判断をしたのと同じ理由で、ここでも経路を増やさない。** 確認を挟む・挟まないは
  「いつ送るか」の違いでしかなく、「何を・どこへ」は変わらない。
- **既にオンの端末を確認画面のオフ端末より軽く扱う理由が無い。** むしろ検証ユーザーの大半はオンにしているため、
  実際に固まりが起きたときの材料はオンの端末からの方が多く要る。

## Consequences

- 1.0.0 より前の検証ユーザーは、`usage_reporting` をオンにしている限り、固まりに気づいた次の起動で構造化イベントと
  `jamjam.log` の両方が確認なしで届く。
- 1.0.0 以上では、オンの端末の自動送信は ADR-056 のときと同じ、構造化イベントだけに戻る。
- ログの送信が失敗しても、構造化イベント（既存の経路）は届く。
