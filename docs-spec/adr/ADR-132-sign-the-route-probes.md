# ADR-132: 経路の確認とその返事に、部屋で受け取った相手の鍵で確かめられる署名を付ける

## Status

Accepted

## Context

リンクは、鍵交換より前に、相手の候補へ「返事を求める keep-alive」（経路の確認。`Packet::route_probe`）を送り、返事が戻るまでの時間で使う経路を決める（REQ-CON-115）。鍵交換はこの確認のあと（つながった経路の上）で行うので、確認とその返事は平文で行き来する。これまでの確認は、送り手が選んだ番号（何回目の・どの候補への確認か）だけを載せていて、誰が送ったかを確かめる手段が無かった。

UDP の送り元のアドレスは偽れる。相手の候補のアドレスを送り元に偽ったパケット 1 つで、次のことが起きた。

- 確認に答えさせ、こちらからの折り返しの確認（REQ-CON-132）を出させる（`Probing::hear`）
- 番号は推測できる（何回目かと候補の順番）ので、偽の返事で、ある候補の往復を短く見せ、使う経路を選ばせる
- 最初の確認の前の待ち（[ADR-131](./ADR-131-open-our-own-nat-before-the-first-probe.md)・REQ-CON-181）を早く終わらせ、相手の NAT が開く前にこちらの確認を送らせる。待ちが守っている NAT（こちらの最初の送出より前に相手のパケットが届くと壊れるもの）で、つながらなくなる

被害は「つながらない・つながりにくくなる」ことに限られ、音声の中身（鍵交換のあとで暗号化され、鍵交換は `link_key` の署名で守られている。[ADR-090](./ADR-090-refuse-peers-that-cannot-be-checked.md)）は読めない・変えられない。鍵交換のあとの確認（新しいアドレスの確かめ。[ADR-121](./ADR-121-confirm-the-new-address-before-moving-the-route.md)）は、リンクの鍵で暗号化されているので当たらない。

鍵交換の前に両端が共有しているものを、コードで確かめた。

- 部屋に入るときに作る、参加者ごとの Ed25519 の鍵（`LinkIdentity`）。公開鍵（`link_key`）はサーバーが部屋のほかの参加者に渡す。`SecureLink::for_peer` は自分の鍵と相手の `link_key` を持ち、鍵交換の署名に使っている
- 鍵交換の一時鍵（X25519）は、鍵交換のパケットで初めて相手に届く。確認の時点では相手は知らない

## Decision

- **経路の確認とその返事に、自分の `LinkIdentity` で署名を付ける**（REQ-SEC-010）。署名するのは、確認か返事かの種類・番号・送り手の `link_key`・受け手の `link_key`（と、ほかの署名と混ざらないための固定の前置き `jamjam-route-probe-v1:`）。
  パケットの形は keep-alive のまま、中身を「種類 1 バイト・番号 4 バイト・署名 64 バイト」にする（これまでは署名の無い 5 バイト）
- **受け取った側は、相手の `link_key` で確かめられる確認と返事だけを扱う**（`SecureLink::read_route_probe`）。確かめられないものには返事をせず、往復の時間に数えず、最初の確認の前の待ちを終えず、推測した相手のポート（[ADR-115](./ADR-115-predict-the-port-behind-a-symmetric-nat.md)）への経路の移動にも使わない。鍵交換のあとの暗号化された確認・返事も、同じ署名を付けて同じように確かめる（経路の上で同じ作りにする）
- 受け手の `link_key` を署名に入れるので、同じ参加者が部屋のほかの人へ送った確認を、こちらあてとして使い回せない。送り手の `link_key` を入れるので、こちらが送った確認を相手の住所から送り返されても、相手のものとして受け取らない
- 相手を知らないリンク（まだ相手が決まっていないもの・echo や音質チェックのボットの `answering`）は、確認に署名も返事もしない。ボットはこれまでも確認に答えていない
- **プロトコルの版（`PROTOCOL_VERSION`）は上げない。** 前の版のアプリは、新しい確認を「中身の付いた keep-alive」として読み、何もしない（これまでと同じ）。新しい版は、前の版の署名の無い確認・返事を扱わない。前の版とは確認が通らず、つながるときは確認が何も返らなかったときの経路（最初の公開アドレス。REQ-CON-114）になる。1.0.0 までは前の版のための読み替えを残さない方針なので、前の版を受け付ける道は作らない
- 検討して採らなかったもの
  - 両端の `LinkIdentity` を X25519 に変換して静的な DH から共有鍵を作り、短い MAC を付ける: パケットは小さく確かめるのも速いが、署名の鍵を鍵交換にも使うことになる。署名なら、鍵交換と同じ鍵を同じ使い方（署名）で使うだけで済む
  - 番号を乱数にするだけ: 経路の上でパケットを見られない攻撃者には推測されにくくなるが、確認（返事を求める側）には効かない。だれの確認でも答え、待ちを終えてしまう
  - プロトコルの版を上げる: 前の版のアプリとは音声も通らなくなる。前の版と混ざったときに起きるのは「確認が通らない」ことだけで、取り違えて音が壊れるような害は無いので、上げるほどではない

## Consequences

- 相手の住所を偽った UDP パケットでは、確認に答えさせることも、経路を選ばせることも、最初の確認の前の待ちを終えさせることもできない。経路の上でパケットを見られる者は、見た確認・返事を、両端が同じ部屋にいて同じ `LinkIdentity` を使っているあいだ送り直せる（署名は送った時刻を含まない）。ただ、その位置にいる者は、パケットを捨てるだけでつながりを妨げられるので、これを防ぐ手立ては加えない
- 確認と返事は 64 バイト大きくなる（12 + 69 バイト）。確認は 1 つのリンクの始まりに候補の数 × 5 回と折り返しの 3 回まで、ポートの予測（ADR-115）で毎秒 250 回まで出る。署名と確かめはそれぞれ数十マイクロ秒で、音声の送受信には入らない
- 署名を確かめるのは、鍵交換の前は候補のアドレスから届いたものだけ、鍵交換のあとはリンクの鍵で開けたものだけ。それ以外のパケットは、署名を確かめる前に捨てる
- この版の前のアプリとは、確認が通らない（前の段落）。つながったときも、往復で選んだ経路ではなく、確認が何も返らなかったときの経路になる
