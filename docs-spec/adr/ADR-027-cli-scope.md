# ADR-027: CLI の位置づけと GUI との機能差

## Status

Accepted

## Context

`architecture.md` §8.2 は「全機能をCLIから利用可能とする。E2Eテストの自動化に対応する。」と述べ、
コマンド一覧まで載せていた。**実装はこれを満たしていなかった。**

| 仕様に載っていたコマンド | 実装 |
|---|---|
| `jamjam devices set --input <ID> --output <ID>` | 無い（`devices list` のみ） |
| `jamjam preset list` / `preset use` / `preset save` | 無い（プリセットの概念が CLI に無い） |
| `jamjam host --password PASS` | `--password` が無い |
| `jamjam join <ROOM_URL｜IP:PORT>` | `IP:PORT` のみ |

さらに GUI にあって CLI に無い操作が広範にあった: ルーム作成（招待コードの発行）、ミュート、
音量・パン、プリセット選択、チャンネル数、診断、セッション中のデバイス切替、設定の永続化、
チャットのリアクション、接続履歴、手動再接続。

**実務上いちばん効いたのはルーム作成の欠落である。** CLI は既存のルームに参加することしかできず、
CLI だけではセッションを開始できなかった。

## Decision

### 1. CLI はデバッグ効率のために存在する

E2E テストの自動化は GUI E2E（[ADR-025](./ADR-025-gui-e2e-control-channel.md)）が担う。
実アプリを起動して DOM を読み・操作する層が既にあり、そちらが利用者の見る状態を検証する。
CLI に同じ役割を負わせると、同じ振る舞いを 2 か所で検証することになり、
どちらが正なのかが曖昧になる。

CLI の役割は**GUI を立ち上げずにセッションを再現・観察すること**である。
ウィンドウ・オーディオデバイス・webview を伴わずに、接続とチャットと音声経路を試せる。

### 2. 同等性は GUI → CLI の一方向のみ

GUI で操作できるコア機能は CLI からも操作できるようにする。逆は求めない。
`host` / `join` によるシグナリングサーバー抜きの IP 直指定は CLI にのみ存在し、
GUI に足す予定はない（利用者はルームで繋ぐ）。

### 3. 追加するコア操作

| コマンド | GUI の対応物 |
|---------|-------------|
| `create-room --server <URL>` | 接続画面の「ルームを作成」 |
| `/mute` `/unmute`（セッション中） | ミキサーのミュートボタン |
| `/stats`（セッション中） | 接続品質・遅延表示 |
| `preset list` / `preset use <NAME>` | 設定のプリセット選択 |
| `devices set --input/--output` | 設定の Devices タブ |
| `--preset` フラグ | 同上（一時適用） |

セッション中の操作をスラッシュコマンドにしたのは、チャット入力と同じ 1 本の stdin を
共有するためである。`/` で始まる行はコマンドとして解釈し、認識できないものはチャットとして
送らずに警告する（打ち間違いが相手に飛ぶより良い）。

### 4. 設定ファイルは GUI と共有する

`AppConfig` とその読み書きをコアライブラリ（`src/config.rs`）へ移し、
`src-tauri/src/config.rs` は Tauri コマンドの薄い層として残す。

CLI で `preset use` / `devices set` を実行すると、GUI が次に起動したときその設定で動く。
逆に GUI で選んだデバイスは CLI のセッションでも使われる。**同じアプリの設定は 1 つである**という
利用者の期待に沿う。CLI 専用の設定ファイルを別に持つと、どちらが効いているのか分からなくなる。

設定の解決順序は GUI と同じである:

```
コマンドラインのフラグ > --preset の値 > 保存された設定 > 既定値
```

### 5. 対象外とするもの

| 機能 | 理由 |
|------|------|
| 音量・パン | GUI の可視化（フェーダー・メーター）が本質。CLI で数値を打つ操作に価値が薄い |
| 診断（ネットワーク・オーディオ・CPU） | 結果の解釈に GUI の表示が要る。CLI からは `/stats` で実測値を見る |
| チャットのリアクション | 絵文字の選択が GUI 前提 |
| 接続履歴 | GUI の利便機能。CLI は招待コードを引数で受け取る |
| `preset save`（カスタムプリセットの保存） | カスタムプリセットの可否自体が未決（Plans.md「判断待ち」） |
| `--password` | ルームパスワードはプロトコルにあるが GUI も CLI も使っていない。片方だけ実装しない |

## Consequences

### 良い影響

- CLI だけでセッションを開始できる。GUI を起動せずに接続・音声・チャットを確認できる
- `create-room` の実装により、CLI にも「後から来たピアのアドレスで接続する」経路
  （[ADR-026](./ADR-026-gui-audio-path.md) が GUI で直した欠陥と同じもの）が入った。
  ルーム作成者は自分ひとりで待つため、この経路が無いと音声が流れない
- 設定が 1 か所になったので、「GUI では動くが CLI では動かない」の原因からデバイスとプリセットが消える
- `architecture.md` §8.2 が実態と一致する

### 悪い影響・残る制約

- **CLI の受信経路にはジッタバッファ・PLC・FEC が無い**。受信したフレームをそのまま再生する。
  GUI（`run_audio_streaming`）とは音の出方が異なるため、ジッタや損失に関わる問題の再現には
  CLI を使えない。この差は Plans.md に既知の負債として記録する
- `--sample-rate` / `--frame-size` の既定値が「48000 / 128 固定」から「保存値」に変わった。
  フラグを明示していたスクリプトの挙動は変わらない
- コアライブラリが `toml` / `directories` / `chrono` に依存するようになった
  （いずれも MIT / Apache-2.0）

### 検証

| 要求 | 検証 |
|------|------|
| REQ-CLI-001 | CLI で作ったルームに招待コードで参加するテスト（シグナリングサーバーを立てて回すため、このリポジトリの外で回す） |
| REQ-CLI-002 | `src/main.rs` のコマンド解釈テスト 3 本 |
| REQ-CLI-003 | `tests/cli_test.rs` のプリセット保存・拒否テスト |
| REQ-CLI-004 | `tests/cli_test.rs::devices_set_refuses_a_device_this_machine_does_not_have` |

CLI テストは `$HOME` を一時ディレクトリに差し替える。CLI が書くのは利用者の実設定ファイルであり、
テストがそれを書き換えてはならないためである。実音声を伴う CLI 同士の接続は手動で確認する
（`--chat-only` でない `create-room` と `join-room`）。
