# ADR-035: 公開アドレスは音声ソケット自身から STUN に問い合わせて公開する

## Status

Accepted

## Context

jamjam はルーターのポート開放なしで繋がる設計である。双方が相手のアドレスへ同時に UDP を送り、NAT に穴を開ける。そのために、各端末は「自分の音声ソケットが外からどう見えるか」を STUN で調べ、シグナリングで相手に伝える。

実装は STUN の問い合わせを音声とは**別のソケット**（`bind("0.0.0.0:0")`）で行い、返ってきた外向きポートを捨てて、**音声ソケットのローカルポート**を付けたアドレスを公開していた。

NAT の対応表は送信元ソケットごとに作られる。別のソケットは別の対応を持つので、STUN が見たポートは音声ソケットのものではない。ローカルポートをそのまま使えるのは、ルーターが内側のポート番号を外へそのまま出す場合（ポート維持）だけである。ポートを付け替えるルーターの内側では、相手は存在しないポートへ送り、穴は開かない。ポート開放が要らないという設計の前提を、実装が保証していなかった。

## Decision

1. **STUN の問い合わせは音声ソケットそのものから出す。** `gather_candidates` は音声ソケットを受け取り、STUN が返した IP とポートをそのまま `ServerReflexive` 候補として公開する。ローカルポートで置き換えない。
2. **ソケットのアドレスファミリーに合う候補だけを返す。** 音声ソケットは `0.0.0.0` に bind した IPv4 専用なので、IPv6 の STUN は行わず、IPv6 のホスト候補も返さない。別ソケットの IPv6 マッピングにローカルポートを付けた候補は、音声ソケットが受信できないアドレスだった。デュアルスタックの音声ソケットを導入したら、そのソケットから v6 の STUN サーバーへ問い合わせる。
3. **STUN の応答は音声ソケットに届く。** 問い合わせは受信ループが始まる前（`Connection::connect` の前 / `streaming_start` の前）に行う。応答待ちの間に届いた STUN 以外のデータグラムは読み捨てて待ち続ける。
4. **GUI は準備済みのソケットを複製して問い合わせる。** `streaming_prepare` が bind したソケットの複製（同じ記述子。ポートも NAT の対応も同じ）で STUN を行い、その間は `streaming_start` がソケットを取り出せないようロックを保つ。取り出されたあとで publish が呼ばれた場合は、ホスト候補だけを公開する。別ソケットの対応から推測した公開アドレスは載せない。

## Consequences

- ポートを付け替える NAT の内側でも、公開したアドレスがそのまま音声ソケットに届く。
- STUN に応答が無いときは ServerReflexive 候補が出ない（以前はローカルポートを付けた推測の候補が出る場合があった）。STUN が使えない環境では、ホスト候補（同一 LAN）だけになる。
- 検証は `tests/stun_nat_test.rs`。ループバック上に、ポートを必ず付け替える NAT と STUN サーバーを立てる。実機の家庭用ルーターでの確認は別に必要。
- NAT の種類によっては、宛先ごとに別のポートを割り当てる（宛先依存マッピング）。その場合、STUN サーバーに見えたポートは相手には使えない。この ADR は解決しない。直すには TURN のようなリレーが要るが、低遅延の方針（[architecture.md](../architecture.md) 5.3）でリレーは使わない。
