# ADR-119: 相手が聞こえないリンクは、両端で黙ってから順番に先に送り直す

## Status

Accepted

## Context

Room check（[ADR-117](./ADR-117-check-many-peers-on-hosted-runners.md)・[ADR-118](./ADR-118-mix-systems-in-the-room-check.md)）で、
macOS の runner の一部が、アプリを使わない UDP の確認では通る相手とも、アプリでは受信が 0 のままになった。
最初のパケットを出した時刻を組ごとに比べると、悪い側が相手とつながったのは 0.78 秒以上先に出した組だけで、失敗した組の差は 46〜257 ms だった。

仮説は次のとおり。NAT が、こちらの側からそのアドレスへ送るより前に届いた相手のパケットを、答えの来ていない流れとして覚える（Linux の conntrack）。
覚えたあとにこちらが同じアドレスへ最初に送ると、その流れの返りの組が覚えた組と重なり、NAT は別の外のポートを割り当てる。
相手は伝えられた元のポートへ送り続けるので記録は延命され、送り続けても抜けない。

Linux の NAT 2 台（コンテナ、`tests/nat/run.sh`）で再現した。

- 片側の NAT だけが覚えるとき、**覚える側の後ろの端が先に送れば**つながり、**相手が先に送ると**どれだけ続けても受信は 0（先に送る側の差が 1 秒でも）。
- 両側が覚えるときは、順番では抜けない。
- 両端が黙って記録が消えるのを待っても、30 秒（UDP の既定の期限）では足りない。期限を過ぎた記録も、カーネルが消す（1 分以内）まで、同じ内側ポートから出る新しい流れに同じ外のポートを使わせる。
  期限 8 秒の環境で黙る時間を 10 秒にすると抜けず、75 秒にすると抜けた。期限 30 秒の既定の環境では、35 秒では抜けず、100 秒で抜けた。

## Decision

- **確認に答えがなく、相手の通信を 1 つも受けていないリンク**は、5 秒たったら 100 秒のあいだ、両端が同時に何も送らない（keep-alive・他の候補への送出・ポートの予測を含む）。
  そのあと、先に送る側が全候補へ確認のパケットを送り直し、あとから送る側は 2 秒待ってから送る。送り直しは 6 秒ほど続け、再び黙る。
  先に送る側は、相手の鍵と自分の鍵の並びで決め（両端が同じ答えを得る）、試すたびに入れ替える。1 回の長さは両端で揃える
  （先に送る側は、待ちの分だけ長く送る）。相手の通信を 1 つでも受けたら、この動作は止まる（REQ-CON-173）
- 聞こえているリンクの送出・遅延・音には触らない。止めるのは、相手の通信を 1 つも受けていないあいだだけ
- 確認に答えがなかったとき、リンクの行き先は、送れる候補のうち最初の公開アドレスにする（無ければ送れる最初の候補）。
  私的なアドレスは、相手が同じネットワークにいれば確認で答えるので、答えなかったものは相手への道ではない（REQ-CON-172）
- リンクごとに、経路を選んだ理由・最初の送出と受信の時刻・相手の候補の種類ごとの数・他のアドレスへの送出の数・送り直した回数と順番を持ち、
  CLI の `--report-json` と Room check の結果に出す（REQ-CLI-015・REQ-CON-174）。利用者の情報の送信（テレメトリ）には足さない。
  アドレスそのものは書かない
- 検討して採らなかったもの
  - 最初のパケットだけ TTL を小さくして先に NAT を開く: 音声と同じソケットで 1 パケットごとに TTL を変える必要があり、OS ごとに挙動が違い、
    この環境では途中の 1 段が無くて試せない
  - 中継（TURN 相当）: 作らない方針
  - 受信が無いリンクの STUN のやり直しと、新しいポートの公開（`UpdatePeerInfo`）: より確実だが、セッション中に音声のソケットで STUN を引く道がまだ無い。
    ここで解けなかった場合の次の手として残す

## Consequences

- 受信が 1 つも無いまま 5 秒たったリンクだけが 100 秒黙る。そのリンクは音が出ていないので、遅延や音質は変わらない。つながるまでの時間は、
  抜けるリンクで 100〜220 秒増える（Linux の実験で 216 秒。試す順が当たらなかった場合は 2 回目で抜ける）。以前は抜けなかった
- 両側の NAT が覚える組は、順番では抜けない。この動作の対象外
- 実際の macOS の runner の NAT が Linux の conntrack と同じ振る舞いかは確かめられていない（ポートを ±100 ずらして送る総当たりは抜けなかった）。
  Room check の結果（`first packet gap`・`sent again`）で確かめる
- 100 秒は、Linux の期限 30 秒とカーネルの掃除の間隔（60 秒まで）に合わせた値。別の実装の NAT で足りないときは `PunchSchedule` で変えられる
