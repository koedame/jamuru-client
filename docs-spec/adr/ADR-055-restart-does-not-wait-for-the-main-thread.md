# ADR-055: 再起動は、主スレッドの終了を待ち続けない

## Status

Accepted

## Context

Mac 実機のベータ版で、`debug.update_apply` が `installed` と `restarting: true` を返したあと、アプリが二度と応答しないことが 2 回起きた（beta.25 と beta.32）。中継には端末が「接続中」と出るのに、操作する側の `hello` は届かず、人が端末で jamjam を起動し直すまで戻らなかった。

beta.25 の端末のログ（`jamjam.log`）は、`Release … is out; downloading` を最後に、人が起動し直すまで 79 分間なにも書いていない。再起動されていれば新しい版の `starting` が書かれるはずで、書かれていない。**再起動を頼んだのに、新しいプロセスが立たなかった。**

Tauri は、主スレッド以外から `restart()` を呼ぶと、主スレッドのイベントループに終了を頼み、ループが終わったところで新しいプロセスを起動する。呼んだスレッドは戻らずに待つ。つまり再起動は主スレッドが終了の要求を処理することに全部を預けている。macOS の主スレッドは、オーディオドライバの呼び出しで止まりうる（[ADR-050](./ADR-050-device-calls-are-bounded.md)）。止まっていれば要求は処理されず、古いプロセスは残り、新しいものは立たない。

同じ Mac で、セッションを抜けて音声が止まった状態で入れた beta.22 は 2 秒で再起動できていた。beta.25 は、接続が失敗したまま音声のストリームが開いたままの状態で入れていた。**音声が開いている状態と主スレッドの停止の関係は、この記録からは確かめられていない**（止まった瞬間のスタックを取れていない）。

## Decision

1. **再起動の前に音声を止める。** 開いている音声のストリームを、上限 3 秒で止めてから再起動する。上限を超えても再起動は進める。
2. **再起動に時間を与え、来なければ主スレッドを待たずに再起動する。** 主スレッドの終了に 10 秒たっても再起動されなければ、専用のスレッドから新しいインスタンスを起動し、古いプロセスを `_exit` で終わらせる（終了ハンドラも主スレッドと同じものを待ちうるので、起動から 3 秒たっても終わらなければ強制する）。タイマーはランタイムのタスクでなく専用のスレッドにする。止まっているのがランタイムのワーカーでも動くため。
3. **終了の要求が主スレッドに届いたかをログに残す。** 次に同じことが起きたとき、要求が処理されたか（ログに `Exit requested`）と、10 秒後の強制（`The restart did not happen`）のどちらで再起動したかが、端末のログから分かる。

更新の後の再起動（自動更新）・`debug.restart`・`debug.update_apply` の 3 つは同じ経路を通す。

## Consequences

- 主スレッドが止まっていても、再起動を頼めば最長でおよそ 10 秒で新しいプロセスが立つ。遠隔デバッグの端末が、更新のあとで戻らなくなることはなくなる。
- 10 秒のあいだ、主スレッドが動いていて単に終了が遅い場合に、強制と通常の再起動が重なりうる。通常の再起動は新しいプロセスを起動してから終わるので、まれに 2 つ立ちうるが、10 秒以内に終わらない終了は異常と見なす。

### 追記: 主スレッドが止まる原因の一つを特定・解消

実機のスタックサンプルで、主スレッドは終了処理の中で利用状況（usage）の最後の送信を待つ
`block_on` の condvar で止まっていた。その送信の周りに置いた `tokio::time::timeout` は効かない:
timeout とその中身は同じ `poll` 呼び出しでまとめて進むので、送信側が一度も `.await` に
戻らずブロックしたままだと（reqwest のクライアント構築が OS のシステム構成呼び出しに
潜り込む場合など。Windows の実機では再現していない）、timeout 側の経過を確かめる機会自体が
来ない。

`UsageState::app_exiting`（`src-tauri/src/usage.rs`）を、送信を専用スレッドで走らせ、
主スレッドは OS のタイマーに基づく `recv_timeout` で待つ形に直した。送信側が本当に
戻らなくても、詰まるのはその専用スレッドだけになり、主スレッドは時間どおりに進む。
このアプリ内で分かっている「主スレッドが止まる原因」はこれで塞いだが、**この ADR の
watchdog（時間で別スレッドから起動し直す仕組み）は残す**。まだ分かっていない・
オーディオドライバ起因（ADR-050）などの他の詰まりに対する最後の砦であり、
二重の仕組みではなく別の層の備え。

- 主スレッドが止まった別の原因（未知のもの）は、まだ直していない。ログに
  `The restart did not happen` が出たら、原因は別に調べる（同じ版で `debug.crashes` と
  `debug.logs` を見る）。
