# ADR-117: 多人数の部屋の確認を、GitHub-hosted runner からステージングにつないで回す

## Status

Accepted

## Context

最大 16 人の部屋（REQ-CON-020）で全員が全員の音を聞けているかは、16 台の参加者を同時に動かさないと確かめられない。
手元の機材には、相手役 15 台を載せられる有線の機器が無い。公開リポジトリの GitHub-hosted runner は無料で、
画面なしの `jamuru`（`--input-tone` と `--output-file` で音の出入りを置き換えたもの）を何台も立てられる。

サーバーの実装は別の非公開リポジトリにあり、このリポジトリに置かない・サブモジュールで持たない・ここのジョブで動かさない。
テストの中だけで立てる小さなシグナリングも同じ理由で作らない。確かめる相手は、デプロイ済みのステージングのサーバーにする。

## Decision

ワークフロー `.github/workflows/room-check.yml` と `scripts/room-check.py` で、次を回す。

- 1 つの部屋に、複数の runner に分けた参加者を入れる。参加者 i は周波数 `300 + 100 × i` Hz の音を送り、聞こえた音をファイルに書く。
  音は順番に 1 人ずつ出す（ほかの参加者は `/mute`）。複数の音を足すと満杯（±1.0）で頭打ちになり、鳴っていない周波数まで
  「聞こえた」ことになるため（手元の試走で確認）。各人の番のあと、各ファイルからその人の周波数を 100 ms の窓ごとに探し、
  番の間に音が入っていた窓の割合と、他人の番に聞こえた割合（0 のはず）を出す。全員が全員の番を決めた割合以上で聞いていれば合格
- 部屋を作る runner が招待コードを他の runner に渡す。ワークフローの成果物は読めるので、接続先（secret）を鍵にして暗号化した
  ファイルで渡す
- 接続先は secret `JAMJAM_SERVER_URL_BETA` で渡し、ソースにもログにも書かない（[ADR-030](./ADR-030-signaling-url-by-build-profile.md)）
- 起動は `schedule`（夜間に 1 回）と `workflow_dispatch` だけ。fork からの pull request には secret が渡らない。
  公開リポジトリに self-hosted runner を付けない
- ログに出すのは合否と、参加者ごとの数値（音が入っていた窓の割合・聞こえた相手の数・音が欠けた割合・往復の時間・CPU の使用率）だけ。
  サーバーの応答・`jamuru` の出力・接続元のアドレスは出さず、成果物にも入れない
- 遠隔デバッグのトークンや管理用の資格情報は使わない。ふつうのアプリと同じ入口だけを使う
- ステージングは試用の利用者と共用なので、人数はアプリの上限まで、測る時間は短く、夜間に 1 回にする。
  無料枠の通知が来たら頻度を下げる
- runner の CPU は共有なので、性能の実測には使わない

## Consequences

- 手動の実行で、16 人（4 台の runner に 4 人ずつ、2 台に 8 人ずつ）が全員の番を 93〜100 % の窓で聞き、他人の番に聞こえたことは無かった
  （2026-11-07）。1 台の runner に載せられるのは、相手 15 人を受ける参加者で 8 人くらいまで（1 人あたり CPU 31〜38 %、4 コアのうち約 3 コア）

- 機材を足さずに、16 人の部屋と、runner どうし（別のデータセンターの回線）の P2P を毎晩確かめられる
- 確かめられるのは、いまステージングに出ているサーバーとの組み合わせだけ。まだ出していないサーバーの変更は、
  サーバー側のリポジトリのテストで見る
- 夜間の実行は、ステージングのサーバーが止まっていても落ちる。落ちた理由がサーバー側かアプリ側かは、
  ログの数値（誰が誰の音を聞けなかったか）から読む
