# ADR-023: 「Phase」を識別子として使わない

## Status

Accepted

## Context

「Phase N」が独立した 6 系統で使われており、同じ表記が文書ごとに別のものを指している。

| 出所 | Phase 1 が指すもの | Phase 5 が指すもの |
|------|------------------|------------------|
| Plans.md（作業グループ） | Storybook UI 統一 | 診断結果ダッシュボードUI |
| architecture.md / ADR-007（対応プラットフォーム） | Windows/macOS/Linux | iOS/Android（Flutter） |
| docs-site/docs/intro.md（実装履歴） | コア機能 | エフェクト・プラグインホスト |
| ADR-012（コード署名） | 署名なし配布 | （なし） |
| sync-spec スキル（手順） | 仕様スキャン | テスト確認 |

読み手はどの系統の「Phase 5」かを判別できない。ADR-007 の「モバイル: Flutter（Phase 5）」は architecture.md 系統だが、Plans.md にも Phase 5 が存在していた。

### Plans.md の番号が機能していない

| 事実 | 影響 |
|------|------|
| Phase 12 の実行順は 12.1→12.7→12.2→12.8→12.3→12.4→12.5→12.9→12.6 だった | 番号が順序を表していない |
| Phase 2・3・8 が消滅している | 記録としても不完全 |
| Phase 7（2026-01-24）と Phase 9（2026-01-26）が半年開いたまま | 「一区切り」の単位として機能していない |
| Phase 13 は「Phase 12 をアーカイブすると 3 件が消える」問題を避けるためだけに作った | 概念の欠陥に対する回避策 |

さらに ADR-018 で要求 ID とトレーサビリティを導入した結果、**残作業は `docs-spec/traceability.md` から自動生成される**ようになった。Plans.md に残る役割は「なぜ未達か・何が必要か」の記述だけであり、番号という第二の識別子は冗長になった。

## Decision

### 1. Plans.md は番号を持たず、要求 ID を主キーにする

作業項目の識別子は `REQ-*` とする。要求に紐づかない項目（開発環境の整備など）は見出しの文言で識別する。

グループ分けは進行順ではなく**何を待っているか**で行う。半年開いた項目が「進行中のフェーズ」に見える状態を避けるためである。

```
## 実環境待ち      -- 実機・実回線・別マシンが必要
## 判断待ち        -- 製品要件としての可否が未決
## 実装待ち        -- 着手すれば終わるもの
```

### 2. 文書内の段階表は「段階」と呼ぶ

ロードマップとしての段階表それ自体は有用なので残す。ただし呼称を「Phase」から変える。

| 文書 | 変更後の呼称 |
|------|------------|
| architecture.md / ADR-007（対応プラットフォーム） | 段階 |
| ADR-012（コード署名の導入） | 段階 |
| docs-site/docs/intro.md（実装履歴） | マイルストーン |
| sync-spec スキル | Step（手順であり段階ではない） |

ADR-012 の本文を書き換えることは「ADR は追加のみ」に反しない。決定内容は一切変えず、他系統との衝突を解消するための呼称変更に限る。本 ADR がその根拠となる。

## Consequences

### メリット

- 「Phase 5」がどの系統か判別できない状態が解消される
- Plans.md の識別子が要求 ID に一本化され、`traceability.md`（自動生成）と Plans.md（手書き）が同じキーで対応する
- 「待っているもの」でグループ分けするため、実機待ちの項目が着手可能な項目に見えなくなる

### デメリット・トレードオフ

- 「Phase 12 が終わった」のような会話上の便利な単位を失う。代わりに「トレーサビリティのギャップ解消が終わった」と内容で呼ぶ必要がある
- ADR-020 / ADR-021 が本文で「Plans.md Phase 12.x」を参照している。これらは要求 ID または項目名への参照に差し替える
