# ADR-064: 相手との UDP の通信を、1 本のリンクとして暗号化する

## Status

Accepted

## Context

利用者向けの文書は「音声は AES-256-GCM で暗号化済み。傍受されても解読できない」と説明し、設計文書は「DTLS 1.3、既定で ON」と書いていた。
実際には、`src/network/encryption.rs` に X25519 + AES-256-GCM の部品と単体テストがあるだけで、**送受信の経路からは一度も呼ばれていなかった**。
`Connection::send_audio` は暗号化の印が立っていない（`flags.encrypted = false`）パケットをそのまま UDP で送り、受信側も印を見ずに処理していた。
同じ LAN の人や経路上の第三者が UDP を取れば、演奏も声も聞けた。法務の点検（2026-10-01）で、説明と実装を突き合わせて見つかった。

部品は経路から呼ぶ前提で作られてもいなかった。

- 暗号化と復号に同じ鍵の文脈を使う形（`EncryptedTransport`）で、実際の 2 者では片方の送信を相手が復号できない。
- nonce は 32 bit のシーケンス番号だけから作る。音声・FEC・keep-alive・遅延の測定は番号の数え方が別で、音声と FEC は同じ番号を使うため、同じ鍵で同じ nonce が再び使われる。
  keep-alive の送信は再接続で番号が 0 に戻る。
- ヘッダを守らず、同じパケットの再送も弾かない。
- 鍵交換のメッセージを運ぶパケットが定義されていなかった。

## Decision

1. **すべての送受信が通る 1 つの口を作る。** `SecureLink`（`src/network/encryption.rs`）。1 つの相手につき 1 つで、`Connection` の送信は
   `send_sealed` を、受信は `SecureLink::open` を必ず通る。部品を足して「あとで繋ぐ」形にしない。
2. **鍵交換は、音声と同じ UDP の経路の中でする。** 接続のたびに X25519 の一時鍵を作り、公開鍵だけを載せた制御パケット（`PacketType::Control`）を、
   相手が暗号化されたものを返すまで 250ms ごとに送る。シグナリングのサーバーが中継する方式と比べ、Connection を使うものすべて
   （アプリ・CLI・echo・音質チェックのボット・テスト）が同じ手順で動く。
3. **鍵は向きごとに別。** 共有秘密から HKDF-SHA256 で、両端の公開鍵（小さいほうが先）を塩に混ぜて 2 つ作り、公開鍵が小さい側が「low→high」で送る。
   自分の鍵を送り返されても、自分が送ったパケットを返されても、復号できない。
4. **nonce は、リンク全体で 1 つの 64 bit カウンタから取り、パケットに載せる。** 種類（音声・FEC・keep-alive・ping）や送り手によらず同じ鍵で同じ nonce を使わない。
   ペイロードは `カウンタ(8) | 暗号文 | タグ(16)`。ヘッダ（バージョン・種類・シーケンス・タイムスタンプ・フラグ）は読める形のまま
   AAD として認証するので、書き換えられると復号が失敗する。
5. **受け取り済みのカウンタと、最新より 128 以上古いカウンタは受け付けない。** 揺れで順番が入れ替わった音声は受け付ける（ジッタバッファが並べ直す）。
6. **相手が鍵を持っていると示すまで、keep-alive と鍵のほかは送らない。** 自分に鍵ができたあとも、相手から暗号化されたパケットが 1 つ届くまでは、
   音声・FEC・ping・遅延の情報は出さない（鍵ができた直後に送ると、まだ鍵を持たない相手に捨てられて、入室の最初に欠けて見える）。
   keep-alive は鍵ができればすぐ暗号化して送り、それが「持っている」の合図になる。音声は符号化もしない（符号化すると、相手に損失として見えるシーケンス番号を使う）。
   待たせた「遅延の情報」は、そのあとすぐ送る。鍵が合っていれば、受け取るのは暗号化されたものだけで、平文は keep-alive も受け付けない（引き下げの防止）。
7. **暗号化できない相手（この版より前のアプリ）は、相手の住所から平文の音声・ping が届いたことで見分ける。** 鍵を受け取らず、鍵の前に平文の音声を送るのは古いアプリだけ。
   見分けたらその接続は平文で動かし、接続の統計の `security` を `unencrypted` にし、画面に「この相手との音声は暗号化されていません」と出す（REQ-SEC-006）。
   **相手の住所以外から届いたパケットと鍵は、暗号化するかどうかの判断にも鍵にも使わない**（ポートを知った誰かが 1 つの平文のパケットで暗号化をやめさせられないように）。
8. **`Session`（複数の相手へ送る）も、相手ごとに `SecureLink` を持つ。** 平文で送る経路を公開 API に残さない。
9. **確かめ方は、ソケットから出るパケット。** 2 つの `Connection` の間に中継（`tests/common` の `Tap`）を挟み、既知の信号を送って、中継を通った datagram を読む
   （`tests/wire_encryption_test.rs`）。部品の単体テストは根拠にしない。

### 選ばなかったもの

- **DTLS 1.3**: 設計文書にはあったが、実装は無かった。UDP の上に別の握手・再送・状態機械を持ち込み、Rust の実装を足すと依存が大きい。
  音声だけの 1 対 1 の経路で必要なのは鍵交換と AEAD だけで、既にある部品（X25519・HKDF・AES-GCM）で足りる。
- **シグナリングのサーバーで鍵を中継する**: 経路上の第三者による途中への割り込みには強くなる（サーバーを信じる前提になる）が、
  echo・音質チェックのボット・CLI の直接接続（サーバーを使わない）も同じ手順に載せる必要があり、Worker のプロトコル（`PeerMessage` の宛先と本文）に手を入れる。
  今回は見送り、相手の確認（下記）の一部として検討する。
- **音声と他の制御を別の鍵・別の経路にする**: 守る理由が音声と変わらず、カウンタを分けると nonce の一意性の確認が増える。1 つにした。
- **暗号化できない相手を断る**: 配布中のベータ版どうしが、更新の途中で繋がらなくなる。画面に出して繋ぐほうを選んだ（バージョン 1.0.0 を出すときに見直す）。

## Consequences

- **守れるのは、通信の途中で音声を聞かれること。** 鍵交換は署名していないので、**相手が本人かどうかは確かめていない**。接続を始める瞬間に、
  経路上でパケットを書き換えられる者が割り込めば、両端と別々に鍵を作って間に入れる。これは Wiki「セキュリティ要件」の JJ-01 に書き、
  相手の確認（端末識別子での署名、またはシグナリング経由の鍵の束縛）は別のチケットにする。
- **パケットは 24 bytes 大きくなる**（カウンタ 8 + タグ 16）。128 フレームのステレオ PCM（1024 bytes）で約 2.3%。帯域の見積もり（`required_bps`）の分も増やした。
- **接続の開始が、鍵が合うまで音声を待つ。** 新しいアプリどうしで 1 往復（通常は数十 ms）、古い相手では見分けるまで最長で keep-alive の間隔（1 秒）。
  接続が続いている間の遅延は、パケットごとの暗号化・復号の分だけで、測定は下記。
- **古い相手には平文で繋がる。** 画面に出る。正式版（1.0.0）を出す前に、この例外を無くすか（暗号化できない相手を断る）を決める。
- 受け取り済みのパケットの検出は 1 本のリンクごと 128 パケットの窓なので、これを超えて遅れて届いた音声は、再生には間に合わないものとして捨てる。
- 鍵が最初に届いた相手のものに決まる。ただし、その相手から暗号化されたパケットが 1 つも届いていない間は、別の鍵が届けば入れ替える（古いアプリのインスタンスが先に鍵を送ってきた場合に、リンクが相手を失わないように）。
