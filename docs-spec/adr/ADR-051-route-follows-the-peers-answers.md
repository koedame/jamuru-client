# ADR-051: 音声の送り先は、相手の応答が確認できた候補にする

## Status

Accepted

## Context

接続の確認（[REQ-CON-113](../behavior/connection.feature)）は、相手の全候補に keep-alive を送り、最初に相手の keep-alive が届いた候補を送り先にしていた。これは「相手のパケットが、その候補のアドレスからこちらに届く」ことしか示さない。**こちらのパケットがその候補の先の相手に届く**ことは確かめていなかった。

実機（macOS）と Linux の相手役で、ルームを出て入り直すたびに約半数で音が 40 秒たっても届かなかった。

- macOS は、相手の LAN アドレス宛の送信が `No route to host` で失敗した。それでも、相手が LAN アドレスへ送った確認は届くので、その候補が「最初に応答した」ことになり、送り先に選ばれた。音声・keep-alive・ping はすべて失敗する送り先へ出続けた。
- 相手役は、こちらから届いた確認が別の候補（VPN のアドレス）からだったので、そちらを選んだ。双方が別の経路を選び、2 秒後に「再接続」に入り、10 秒後に諦めた。再接続は同じ送り先に送り直すだけで、別の候補は試さなかった。

送信だけが成り立たない候補は、相手の LAN が別の場所の LAN と同じ番号帯で重なる場合や、OS が LAN への送信だけを拒む場合に現れる。

## Decision

1. **確認の応答は、こちらから送れた候補からのものだけを数える。** 確認の keep-alive を送れなかった候補（送信がエラーになった候補）から相手のパケットが届いても、その候補は選ばない。どれにも応答が無く待ちが尽きたときの既定も、先頭ではなく、送れた最初の候補にする（`is_probe_answer`）。
2. **送り先の候補は 1 つだけで固定せず、相手の応答で動かす。** 送り先 `current` のほかに、相手の他の候補を持つ（`Route`）。相手が ping に応答した（pong が届いた）ときは、こちらのパケットが相手に届いている証拠として、その時刻を覚える。
3. **応答が途絶えたら、相手の声が届いている候補へ送り先を移す。** 検出しきい値（`detect_after`、既定 2 秒）を超えて pong が無いあいだに、送り先と別の、かつこちらから送れる候補のアドレスから相手のパケットが届いたら、音声・keep-alive・ping をその候補宛に送る。相手のパケットが届いていない候補へは移らない。
4. **応答が途絶えているあいだ、相手の他の候補にも keep-alive を送る。** 相手にこちらの声が他の候補からも届くようにして、相手側が同じ規則で移れるようにする。送れたかどうかは候補ごとに毎回記録し直す。

## Consequences

- 相手の応答が確かめられない候補へ送り続けることがなくなる。上の実機の事象は、初めから送れる候補（VPN）を選ぶので起きない。
- 応答が確かめられている間は送り先を動かさない。パケット損失の多い回線で、応答が 1、2 回抜けても、相手のパケットが他の候補から届かない限り移らない。
- 送り先が移るのは、経路が実際に切れたときに限る。以前は再接続が同じ送り先に送り直すだけだった。
- keep-alive は、応答が途絶えているあいだだけ、候補の数に比例して増える。音声は増えない。
- 検証は、`connection.rs` の単体テスト（応答の判定・送り先の移動の条件・ループバック上で沈黙した候補から相手の声が届く経路への移動）で行う。実機での入り直しの確認は別に必要。
