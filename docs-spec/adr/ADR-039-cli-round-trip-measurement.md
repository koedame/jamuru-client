# ADR-039: 音声経路の往復遅延を、CLI が区切りのある信号で測って JSON に残す

## Status

Accepted

## Context

jamjam は低遅延が最優先であり（[ADR-008](./ADR-008-zero-latency-mode.md)）、アプリの変更で遅延が悪化したときは、あとからではなく変更の直後に分かりたい。ところが CLI が出せるのは終了時の文章による統計だけで、次の 3 点が足りなかった。

- **終わり方**: Ctrl+C まで走り続けるので、スクリプトから 1 回分を測って止められない
- **機械が読める出力**: 統計は人が読む文章で、比べたり貯めたりできない
- **アプリ全体の往復時間**: `rtt_ms` は keep-alive の往復で、ネットワークだけの値である。取り込み・送信・デコード・ジッタバッファ・再生まで含めた「音を出してから、その音が返ってくるまで」は測れていなかった。`--input-tone` の連続した正弦波では、どの音がどの音に対応するかも分からない

もう一つ、CLI は再生遅延の自動調整（[ADR-031](./ADR-031-live-playout-delay.md)）を呼んでいなかった。GUI は 1 秒ごとに呼ぶので、CLI で測った遅延は GUI の実際の挙動を表さない。

## Decision

### 1. 区切りの分かる信号で、送信と再生の時刻を対にする

`--input-bursts` は、入力デバイスの代わりに 500 ms ごとに 10 ms の 1 kHz のバースト（間は無音）を送る。バーストは、

- 送信側: 送信直前のフレームで最初に検出した時刻
- 受信側: プレイアウトバッファが出力へ渡したフレームで最初に検出した時刻

をそれぞれ記録し、**受信した時刻より前で最も新しい送信**と対にする。個数で数えて対にしない。バーストが 1 つ失われても、以降が 1 つずつずれて誤った遅延を報告することがないようにするためである。

対にできるのは 500 ms 未満の往復に限る（次のバーストと取り違えないため）。同じバーストへの 2 つ目の音は数えない。分解能は 1 フレームである。

### 2. 相手が音を保持して返す場合は、その分を引く

エコーサーバーのように、受けた音を一定時間保持してから返す相手では、返ってきた音を自分の音と区別できる。その保持時間は `--echo-delay-ms` で渡し、往復から引く。既定は 0。

**測れるのは、相手が自分の音を返すときだけである。** 返さない相手（双方が `--input-bursts` の `host` と `join` など）では、聞こえるのは相手自身のバーストで、その位相差がもっともらしい遅延として報告される。ローカルモニタリング（`--monitor`）は自分の入力を出力へ直接混ぜるので、検出はその前の、プレイアウトバッファが出したフレームで行う。

### 3. `--duration` で終わり、`--report-json` で残す

`host` / `join` に追加する。`--duration <秒>` は接続してからの秒数で、経過すると通常どおり切断して終了する。`--report-json <PATH>` は終了時に 1 つの JSON オブジェクトをファイルへ書く。標準出力は進行表示とログが混ざるので、機械が読む出力は別の経路にした。

レポートの内容: 版・終了時刻・相手・接続秒数・音声設定・ネットワーク（RTT・ジッタ・ロス・パケット数）・プレイアウト（遅延フレーム数・再生・補間・遅れ・再同期）・往復（送信数・戻るはずだった数・戻った数・最小・平均・中央値・95 パーセンタイル・最大）。往復は `--input-bursts` のときだけ入る。「戻るはずだった数」は、往復の時間が過ぎる前に終わった直近のバーストを除いた数で、終了間際のバーストがロスに見えないようにする。

### 4. CLI も再生遅延を自動調整する

CLI のセッションも `ReceivePath::adapt` を GUI と同じ周期（`ADAPT_INTERVAL`）で呼ぶ。周期の定数は GUI と CLI で同じものを使うため、コアライブラリに置いた。

## Consequences

### 良い影響

- アプリを変えたあとの往復遅延を、サウンドカードもウィンドウも無い環境で 1 コマンドで測り、数値で比べられる
- 遅延の内訳（往復 − `rtt_ms`）が、アプリが足している分として読める

### 悪い影響・残る制約

- 測るのは CLI 経路である。GUI の取り込み経路（実デバイス）は含まない
- `--output-file` の代わりに実デバイスを使うと、デバイスの出力バッファの遅延は往復に含まれない（プレイアウトバッファから出力へ渡した時点を測るため）
- 分解能が 1 フレームなので、フレームの大きいプリセットでは値が粗い
- 送信側の時刻は、取り込みの時刻ではなく、送信タスクがフレームを受け取った時刻である
