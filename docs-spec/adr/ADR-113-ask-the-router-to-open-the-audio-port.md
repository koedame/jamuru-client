# ADR-113: ルーターに音声のポートを開けてもらう（UPnP）

## Status

Accepted。

## Context

家庭のルーターは、中から外へ出た通信の戻りだけを通す。相手のアプリが先に送ってこない限り、外からのパケットは落とされる。
いまの jamuru は、STUN で自分の公開アドレスを知り、お互いに同時に送り合って穴をあける（ADR-035）。
ルーターの種類によっては、宛先ごとに別の外側のポートを割り当てる（宛先依存のマッピング）ため、STUN で知ったアドレスが相手には使えず、つながらないことがある。

ルーターに「このポートへ外から来た UDP は、この端末の音声ソケットへ渡す」と頼めれば（UPnP IGD の AddPortMapping）、相手の宛先に関係なく同じ外側のアドレスが使える。
頼めるルーターは家庭用に多いが、無いルーターも、設定で切ってあるルーターもある。頼みごとが通らなくても、これまでどおり STUN だけでつなぐ。

## Decision

### 1. 音声の IPv4 ソケットについて、UPnP IGD でルーターにポートを開けてもらう

- 開けるのは音声の UDP ソケット 1 本のポート 1 つだけ。説明は `jamuru`。
- 外側のポートは、まず手元のポートと同じ番号を頼み、使用中なら 49152〜49202 から無作為に最大 3 回試す。
- 応答したルーターの IP アドレスが私設（10/8・172.16/12・192.168/16）かリンクローカルでなければ、同じネットワークのルーターではないので使わない（インターネット側から偽の応答を送り込まれる経路をふさぐ）。応答元と、機器の説明・操作先の URL の宛先が同じであることは、クレート（`igd-next`）が確かめる。
- ルーターが返した外側の IP アドレスが公開アドレスでない（私設・CGNAT の 100.64.0.0/10・リンクローカル・ループバックなど）ときは、二重の NAT なので使わず、ただちに閉じる。
- 取れた外側のアドレスは、候補の種類は反射型（server reflexive）のまま、優先度を STUN の結果より高くして（type_pref 110。ホスト 126 より下）渡す。ワイヤ形式（シグナリングの候補）は変えない。

### 2. 貸し出し期間（リース）は 1 時間、半分ごとに更新する

- 無期限（0）にしない。アプリが落ちても、残ったものは 1 時間以内にルーター側で消える。
- 更新が失敗しても音声は止めない。リース付きを断るルーター（エラー 725。無期限の転送しか受けない）には頼まない。無期限にすると、アプリが強制終了されたとき転送が残り、そのポートを後から使う別のアプリに外の通信が届いてしまうため。そのルーターでは STUN だけで続ける。
- 退室（`streaming_stop`）・アプリの終了・CLI の終了で、ポートを閉じる（削除は 2 秒で打ち切る）。閉じ忘れた `Drop` でも、更新を止めて削除を試みる。

### 3. STUN と並行して頼み、待たせない

- 候補を集めるとき、STUN への問い合わせと、ルーターの探索・依頼を同時に走らせる。探索は 1.5 秒、依頼全体は 4 秒で打ち切る。
- ルーターが見つからなかったときは 5 分間は探し直さない（音声の入室のたびに 1.5 秒待たせない）。
- ルーターが無い・断った・時間切れのいずれでも、STUN だけの候補で続ける。失敗は入室を妨げない。

### 4. 使うクレート

`igd-next` 0.18（MIT。tokio 版。依存に新しいライセンスは増えない）。許可リストのライセンスだけで足りるので、GPL 系などの判断は要らなかった。

### 5. 既定はオン。設定で切れる

- 設定「ルーターのポートを自動で開く」（`open_router_port`）。既定はオン。一般タブの「接続」に置く。次に入室するときから効く。
- オンにする理由: つながらない原因の多くは利用者には見えず、オフが既定だと気づかないまま「つながらない」で終わる。開くのは入室中の 1 ポートだけで、そのポートで受けるのは、すでに P2P で相手に見せているアドレスと同じ。受けた UDP は暗号化の鍵を持たない相手には復号できず、捨てられる。
- 追加で見える情報はない（公開アドレスはすでに STUN で相手に見える）。ただし**ルーターのポートが入室中、外のだれからでも届く状態になる**ため、プライバシーの文書とセキュリティ要件に書く。

### 6. NAT-PMP / PCP は入れない

miniupnpd のようにどちらも話すルーターがあるが、NAT-PMP / PCP は、ルーターの宛先（既定のゲートウェイ）を OS ごとに調べる処理が要る。UPnP と違い SSDP で見つけられない。費用に見合わないので入れない。別の案件で必要性を見る。

### 7. 外から届くかの確認はしない

「開いたポートに本当に外から届くか」を確かめるには、外側で UDP を受けるサーバーが要る。いまのシグナリングサーバーは UDP を受けられない。ルーターが返した外側のアドレスを信じ、実際に届くかは、相手との接続の試行（ホールパンチ）が確かめる。専用のサーバーは費用が発生するので、ここでは作らない。

### 8. 同じネットワークの偽のルーターは防がない（受け入れる）

SSDP に答える機器が本物の既定ゲートウェイかどうかは確かめない（確かめるには OS ごとの既定ゲートウェイの調べ方が要り、6 の NAT-PMP / PCP と同じ費用がかかる）。同じネットワークの機器が偽のルーターを名乗ると、任意の公開 IP を候補として相手に渡させられる。その機器は、ARP の偽装など、同じネットワークにいればできる他の手段でも、このアプリの通信を横取りしようとできる。渡した候補に音声が流れても、相手は鍵交換で本人を署名で確かめる（JJ-16）ので、偽の宛先とは接続が成立せず、暗号化された音声も読めない。他の候補（STUN・ホスト・IPv6）には影響しない。

## Consequences

- STUN だけではつながらないルーターの組み合わせでも、つながる場合が増える。
- 入室中は、ルーターのポートが 1 つ外に向けて開く。届いたパケットは音声のセッションの暗号化で守られ、鍵を持たない送り手は復号できない。セキュリティ要件の Wiki に、届くものを書く。
- ルーターを探すための SSDP（239.255.255.250 への UDP マルチキャスト）と、ルーターへの HTTP（LAN 内）が増える。LAN の外には出ない。
- UPnP を無効にしている利用者のルーターには、何も起きない。

## 検証

- 偽のルーター（SSDP と SOAP を話す）を使った統合テスト（`tests/port_mapping_test.rs`）: 依頼が通る・断られる・同じ番号が使用中・恒久のみ・二重の NAT・ルーター無し・設定オフ・更新・退室・`Drop`。
- 本物のルーター（miniupnpd 2.3.7）を動かすコンテナの実験環境（`tests/upnp/run.sh`）: ルーターの公開アドレスで候補が出ること、DNAT の規則ができること、外側の端末から送ったデータグラムが音声のソケットに届くこと、退室で規則が消えること、UPnP の無いルーターでは STUN だけで 1.5 秒ほどで続くこと、設定オフでは何もしないこと。
