# ADR-120: 上りと下りの片道の遅れを、時計のずれを添えて測る

## Status

Accepted

## Context

接続ごとの `rtt_ms` は往復で、上り（自分→相手）と下り（相手→自分）が別々には分からない。
経路は行きと帰りで違うことがあり、夜間の部屋の確認（ADR-117・ADR-118）の台どうしの遅れを読むには、片道ずつ要る。

片道は、送った側の時刻をパケットに入れ、受けた側の時刻との差を取って測る。これは 2 台の時計の差なので、時計がそろっていることが前提になる。
往復から時計のずれを割り出す方法（NTP の式）は、行きと帰りが同じだと仮定するので、片道の差を出すのには使えない。

## Decision

- 往復の測定の ping に送った側の時計の時刻（Unix 時間のマイクロ秒）を、pong に ping の送信時刻・ping を受けた時刻・pong を送る時刻を載せる（REQ-LAT-132）。
  固定部分のあとに足すので、載せない相手の ping と pong は固定部分だけで読まれ、載せる相手の末尾は載せない相手に無視される。
  プロトコルの版は上げない（1.0.0 までは検証ユーザーだけで、古い版のための読み替えは残さない方針だが、これは読み替えが要らない形で足せる）
- 接続の統計に上りと下りの片道を入れる（REQ-LAT-133）。往復と同じ係数で平滑化する。上りはずれの分だけ大きく、下りは小さく出て、**和は往復になる**
- `--report-json` に相手ごとの `one_way_spread_ms`（`up` と `down`、それぞれ最小・中央値・p95・最大・標準偏差）を足す（REQ-CLI-016）。アプリは時計のずれを知らないので、補正はしない
- 夜間の確認（`room-check.py`）は、台ごとに時計の状態を記録する。Linux は chrony の `chronyc tracking`（時計の進み・遅れと、root dispersion + root delay / 2 の誤差の幅）、
  取れない台（macOS・Windows・chrony が無い台）は公開の時刻サーバーへの SNTP を数回問い合わせて、誤差の幅が最小の答え（往復の半分）を使う。
  番の前と後の 2 回測り、進み・遅れの平均を時計のずれとし、誤差の幅は 2 回の大きい方に、動いた量の半分を足す
- 片道は、2 つの台の時計のずれの差で補正する（上りから引き、下りに足す）。補正後の値は、2 つの台の誤差の幅の和の範囲で正しい。
  上りと下りの**差**にはずれが 2 回入るので、その誤差の幅は 2 倍になる。**差の大きさが差の誤差の幅以下なら「差は分からない」と扱う**（差が無いとも、逆向きとも言えない）。
  同じ台の参加者は同じ時計を使うので、補正も誤差も無い
- 時計の状態が取れなかった台とのつながりは、往復だけにする（片道は出さない）。補正しない片道は、時計が大きくずれた台では遅れそのものより大きな嘘になる。
  2026-11-08 の手動の回では、GitHub の macOS の台は時刻サーバーへの UDP（123 番）が通らず（8 回とも時間切れ）、時計は他の台から約 1 秒ずれていて（上りが −940 ms、下りが +976 ms と出た）、
  この取り方では測れない。Linux は chrony で誤差の幅が 0.2 ms 未満、Windows は SNTP で 3〜4 ms だった。
  Windows の Python の時計は 15 ms 刻みなので、アプリと同じ呼び出し（`GetSystemTimePreciseAsFileTime`）で読む
- 結果の `links` に `one_way_spread_ms`、台ごとの `runner_facts` に `clock`（番の前）と `clock_end`（番の後）を足す。アドレスは入れない
- Verdict に、台の組ごとの上り・下り（補正後の中央値、誤差の幅、差が分かるか）を出す

## Consequences

- 台をまたぐ組の片道は、時計の誤差の幅（chrony なら 1 ms 未満、SNTP なら数 ms）と同じ程度までしか読めない。差がそれより小さい組は「差は分からない」と出る
- 時計の状態の取得は公開の時刻サーバーへ UDP 123 で問い合わせる。通らない台は往復だけになる
- ping が 8 バイト、pong が 24 バイト大きくなる。1 秒に 1 往復なので帯域は無視できる
