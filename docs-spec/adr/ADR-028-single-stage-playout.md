# ADR-028: 受信音声を単段バッファにし、出力コールバックが直接引く

## Status

Accepted

## Context

受信経路は音声を **2 か所**に溜めていた。

```
ソケット → ジッタバッファ → ポーリングループ → 再生FIFO(8フレーム) → 出力コールバック
```

ループの取り出し条件は「再生 FIFO に 1 フレーム分の空きがあれば取り出す」だった（[ADR-026](./ADR-026-gui-audio-path.md)）。FIFO は 8 フレーム分あるので、**ジッタバッファに溜まったフレームは再生時刻より前に次々と吸い出される**。

結果として 2 つの問題があった。

1. **設定した段数が実行時に存在しない。** `balanced` の 4 フレームは、並べ替えのできないただの FIFO へ移っていた。遅れて届いた・順序が入れ替わったパケットは、自分の枠が既に無い状態で到着する。ADR-020 と REQ-LAT-025 が「段数＝保護量」と定めているのに、実際の保護はそこになかった
2. **FIFO の遅延が遅延表示に入っていない。** `LocalLatencyInfo::from_audio_config` は再生バッファを **1 フレーム**として計上する（`src/network/latency.rs`）。実装は最大 8 フレーム保持する。32 サンプル時で 5.33ms、`zero-latency` のアプリ遅延バジェット 2.0ms（ADR-019）を超える

さらにループは 250µs のポーリングで回っており、再生の刻みはオーディオクロックではなくタイマーに従っていた。

## Decision

**溜める場所を 1 つにし、出力コールバックがそこから直接引く。**

```
ソケット → デコード（+リサンプル） → 再生バッファ → 出力コールバック
```

### 1. `PlayoutBuffer`（`src/audio/playout.rs`）

- フレームはシーケンス番号が指すスロットで自分の順番を待つ。**遅延到着・順序入れ替わりが自分の位置に収まる**
- 後段のキューが無いので、**保持している遅延＝聞こえる遅延**。遅延表示の前提（再生 1 フレーム）と実装が一致する
- 起動条件は従来と同じ「設定段数 + 1 フレーム」（REQ-LAT-025 / 026）
- 損失は最後の正常フレームからフェードして隠蔽し、**置き換える対象と同じ長さ**を出す。長さが固定だと損失のたびに後続の時間軸がずれる

### 2. リアルタイム規律

`read_into` はアロケートせずブロックしない。スロットは事前確保され、隠蔽は呼び出し側のバッファへ書く。共有は mutex だが、**読み側は `try_lock` で、競合したら 1 フレーム隠蔽する**。待たないので優先度逆転が起きない。書き側の臨界区間は 1 フレームの memcpy である。

デコードとリサンプルは**パケットが届いたところ**（ネットワーク側）で行う。コールバックが行うのは、コピーとミキサーのゲイン適用だけである。

### 3. フレーム長は可変

ピアが別のサンプルレートなら受信側で変換する（[ADR-013](./ADR-013-sample-rate-strategy.md)）。**レート変換はフレーム数の整数倍にならない**（44.1k→48k は 1.088 フレーム分、44.1k→96k は 2.18 フレーム分）。

固定長スロットに収めるには詰め物か切り捨てが要るが、それはサンプルを増減させる操作であり、**ピッチを変える**。したがってフレームは到着した長さのまま保持し、読み出しが書いた長さを返す。スロットは最も広い変換（44.1k→96k）を見込んで公称フレームの 3 倍で確保する。

### 4. シーケンス番号の振り直しに再同期する

スロット容量を超える距離のシーケンスが届いたら、同一ストリームの欠落ではありえないので再同期する。ADR-026 で「実ストリームで検証できないまま推測で入れるのを避ける」として残した穴が、ここでは**容量という明確な判定条件**で塞げる。

### 5. ミキサーのゲインは再生時に適用する

音量・パンは書き込み時ではなく**再生するフレームに**適用する。書き込み時だと変更が効くまで段数分（数 ms）遅れる。コールバックはアトミックを読むだけなのでリアルタイム安全である。

## Consequences

### 良い影響

- プリセットが約束する遅延が実際の遅延になる。ADR-008 の最優先要件に直接効く
- 遅延到着・順序入れ替わりの保護が、仕様が言うとおりの量だけ存在する
- 250µs のポーリングが消えた。再生の刻みはオーディオクロックそのものになった
- 音量・パンの変更が次のフレームで聞こえる
- セッション中の段数変更が、バッファ破棄による音切れを伴わなくなった（目標値を動かすだけ）

### 悪い影響・残る作業

- **CLI はまだ旧来の直接再生のままである。** ジッタバッファも PLC も無く、受信フレームをそのまま鳴らす。同じ経路に寄せるのは別作業として Plans.md に残す（[ADR-027](./ADR-027-cli-scope.md) が記録した既知の差分）
- **`JitterBuffer`（`src/network/jitter_buffer.rs`）は製品コードから使われなくなった。** 現在の利用者は `tests/latency_test.rs` と E2E のソフトウェアパイプラインのみである。テストが死んだコードを検証している状態なので、退役（REQ-LAT-108〜111 の検証を `PlayoutBuffer` 側へ移す）を Plans.md に残す
- 読み側が `try_lock` に失敗した場合は 1 フレーム隠蔽になる。競合窓は 1 フレームの memcpy であり実測上は稀だが、ゼロではない

### 検証

| 要求 | 検証 |
|------|------|
| REQ-LAT-025 / 026 | `src/audio/playout.rs` の起動条件テスト（段数どおりに保持・パススルーは即時） |
| REQ-LAT-108 / 109 | 同ファイルの適応テスト（上限・下限で止まる） |
| REQ-LAT-106 | `src-tauri/src/streaming.rs` のプリセット→遅延テスト |
| REQ-GUI-013 / 014 | GUI E2E の実音声シナリオ（トーンが 2 台の間を流れ、受信側のメーターが追従する） |
| ピッチ保存 | `frames_keep_the_length_they_arrived_with`（4/5/4 サンプルのフレームが増減なく再生される） |
