# ADR-033: ローカルモニタリングを、出力コールバックへ入力を直接混ぜて実現する

## Status

Accepted

## Context

REQ-AUD-111（ローカルモニタリングを ON にすると、自分の音声がネットワーク遅延なしで聞こえる）と REQ-AUD-112（OFF なら聞こえない）は `must` で、検証済みと表示されていた。実際には音が出ていなかった。

- `AudioEngine::set_local_monitoring` は真偽値のフラグを立てるだけで、そのフラグを読む処理がどこにも無かった（`local_monitor_flag()` の呼び出し元は 0 件）
- GUI にも CLI にも、モニタリングを操作する経路が無かった
- 検証していたテストは、フラグの読み書きだけを見ていた。音が出ることは見ていない
- 仕様書 `audio_engine.md` §6 は「キャプチャした音声を遅延なしで出力にミックスする」と書いていて、実態と食い違っていた

[ADR-028](./ADR-028-single-stage-playout.md) で再生リングバッファの旧経路を消したとき、旧経路の `playback_producer()`（コメントは「ローカルモニタリング用」）が唯一の接続点だったが、呼び出し元は無かった。**モニタリングは最初から動いていなかった。**

選択肢は 2 つあった。

| 案 | 内容 |
|----|------|
| 実装する | 出力コールバックへ、キャプチャした入力を直接混ぜる |
| 要求ごと外す | 楽器の直接モニタリングはオーディオインターフェースのハードウェアモニターに任せる前提へ変える |

実装を選んだ。ハードウェアモニターを持たない構成（内蔵マイク・USB マイク・ヘッドセット）でも自分の音が聞こえることが、この要求の目的だからである。

## Decision

### 1. 経路: キャプチャ → リング → 出力コールバック

```
キャプチャコールバック ──▶ MonitorTap ──▶ rtrb ──▶ LocalMonitor::mix_into ──▶ 出力バッファへ加算
                                                            ▲
                                            再生バッファ（相手の音声）を書いた後
```

- `LocalMonitor`（`src/audio/monitor.rs`）が ON/OFF・音量・リングを持つ。キャプチャ側は `MonitorTap::push`、出力側は `LocalMonitor::mix_into` を呼ぶ
- 混ぜる位置は、出力コールバックが**再生バッファから引いて音量・パンを掛けた後**である。相手の音声がまだ無い（`Priming` / `Starved`）ときも、自分の音は聞こえる。相手と繋がる前に自分の音を確かめられる
- ネットワーク・再生バッファ・ジッタバッファのどれも通らない。遅延はプリセットの段数にも接続にも依存しない
- 出力バッファの**加算**で、相手の音声を置き換えない（REQ-AUD-111 の「他の参加者の音声も同時に聞こえる」）
- モノラルの入力を両チャンネルへ同じ大きさで足す。パンは掛けない（ローカルチャンネルのパンは相手へ送る音の定位であって、自分が聞く音のものではない）
- ミュートは「相手へ送らない」であり、モニタリングとは独立である。ミュート中も自分の音は聞こえる

音声処理はしない（[ADR-005](./ADR-005-no-audio-processing.md)）。入力を 1.0 倍（既定）で足すだけで、リミッターも掛けない。

### 2. 遅延: キャプチャ 1 フレーム + 余裕 1 フレーム + 再生 1 フレーム

入力と出力は別のデバイスのクロックで動くので、2 つのコールバックの位相は揃わない。出力が入力より先に来ると、出す音が無い。**余裕**（`MONITOR_MARGIN_FRAMES` = 1 フレーム）は、この位相のずれとコールバックの遅れを吸収する量である。

```
モニタリングの遅延 = フレーム長 × (1 + 余裕 1 + 1)
```

| プリセット | フレーム長 | モニタリングの遅延 |
|-----------|-----------|------------------|
| zero-latency | 0.67ms | 2.00ms |
| ultra-low-latency | 1.33ms | 4.00ms |
| balanced | 2.67ms | 8.00ms |
| high-quality | 5.33ms | 16.00ms |

（48kHz、デバイスとドライバ自体のバッファは含まない。ADR-019 の片道遅延とは別の経路で、足し合わせない。）

余裕を 0 にすれば 2 フレーム分短くなるが、位相次第で毎フレーム途切れる。1 フレームは、ドライバが「セーフティオフセット」として持つ量と同じ考え方である。

### 3. 2 つのクロックのずれ: 溜めない、途切れたら満たし直す

- **起動**: リングに「出力が求める量 + 余裕」が溜まるまで何も足さない
- **溜まりすぎ**: 求める量 + 余裕を超えて、さらに 1 フレーム以上溜まったら、余裕まで古い方を捨てる。キャプチャのクロックが速い場合に、遅延が増え続けない（REQ-AUD-032）
- **足りない**: 出力が求める量に届かなければ、あるだけ足して満たし直しに戻る。出力のクロックが速い場合、途切れが起きる

デバイスが 2 つ（内蔵マイク + 別の出力など）でクロックが独立しているとき、ずれは周期的な捨て・途切れとして聞こえる。50ppm のずれで 64 サンプルなら約 27 秒に 1 回である。入力と出力が同じオーディオインターフェースなら、クロックは 1 つでこれは起きない。

**選ばなかった案**: クロックのずれを追従するリサンプラを入れる。音は連続するが、ずれが実際に問題になると分かる前に、計算量と位相の検証を持ち込むことになる。周期的な途切れが問題として報告されたら再検討する。

### 4. ON/OFF は「聞こえ方」の操作であり、明示的な操作でのみ ON になる

- **既定は OFF**。セッションの開始ごとに OFF へ戻す。スピーカーとマイクの組み合わせでは、モニタリングがハウリングを起こしうる。自分の音を聞くのは、利用者が求めたときだけにする
- **OFF の間は何も溜めない**（`MonitorTap::push` は捨てる）。OFF にした時点で溜まっていた分は、次の出力コールバックで捨てる。再び ON にしたとき、古い音が鳴らない
- 入力デバイスを切り替えたら、新しい `MonitorTap` を作る（リングは作り直す）。出力側は同じ `LocalMonitor` のまま続ける
- 出力側は `try_lock` で、キャプチャ側がリングを差し替えている間は、そのフレームだけモニタリングなしで出す（デバイスを待たせない）

### 5. 操作の経路

| 面 | 操作 |
|----|------|
| GUI | ミキサーの「自分」のチャンネルにあるヘッドホンのボタン（`streaming_set_monitoring`）。状態は `StreamingStatus::is_monitoring` で UI へ戻る |
| CLI | `--monitor`（開始時に ON）、セッション中の `/monitor` / `/unmonitor`。[ADR-027](./ADR-027-cli-scope.md) の「GUI で操作できる機能は CLI からも」に従う |

`AudioEngine` の `set_local_monitoring` / `is_local_monitoring_enabled` / `local_monitor_flag` は、何も読まれないフラグだったので削除する。音量は `LocalMonitor::set_volume`（0.0〜1.0）で持つが、GUI・CLI に操作は設けない（`audio_engine.md` §6 の API は残す。要らないことが分かるまで UI を増やさない）。

## Consequences

### 良い影響

- REQ-AUD-111 / 112 が、フラグではなく**出力に音が載る**ことで検証される（単体は `LocalMonitor` の出力、結合は CLI プロセスの `--output-file`）
- 相手と繋がる前でも、入力デバイスとレベルを聞いて確かめられる
- 遅延がプリセットの式で表せ、ネットワークにもジッタバッファにも依存しない

### 悪い影響・残る作業

- 内蔵マイクなど、入力と出力が別クロックの構成では、周期的な捨て・途切れが出る（上の 3）。追従リサンプラは入れていない
- モニタリングの遅延はプリセットのフレーム長に比例する。`high-quality`（16ms）は演奏中の自己モニタには長い。低遅延が要るなら `zero-latency` / `ultra-low-latency` を選ぶ
- 「遅延がこの式どおり」であることを、実機のループバックで測っていない。単体は、クロックが揃った理想の下で溜まる量（余裕 1 フレーム）を測っている。実機の遅延は、ドライバのバッファが加わる

### 検証

| 要求 | 検証 |
|------|------|
| REQ-AUD-111 | `src/audio/monitor.rs` の単体テスト（入力が順序どおり・欠落なく出る、相手の音声に加算される、音量が掛かる）、`tests/audio_quality_test.rs`、`tests/cli_test.rs`（`--monitor` の CLI が、相手のいない状態で自分のトーンを音高・音量どおり出力する） |
| REQ-AUD-112 | 同（OFF の間は出力が相手の音声のみ。OFF にした時点で溜まっていた音は、再び ON にしても鳴らない。CLI は `--monitor` 無しで無音） |
| REQ-AUD-032 | `src/audio/monitor.rs` の単体テスト（クロックが揃っていれば溜まる量は余裕の 1 フレームで一定、キャプチャが速くても溜まり続けない、途切れの後に再開する） |
| REQ-CLI-006 | `src/main.rs` の単体テスト（`/monitor` `/unmonitor` が `LocalMonitor` を切り替える）、`tests/cli_test.rs` |

GUI のボタンは、型検査・ビルド・実描画（スクリーンショット）までを検証した。実デバイスで自分の音が聞こえることは、手動で確認する。
