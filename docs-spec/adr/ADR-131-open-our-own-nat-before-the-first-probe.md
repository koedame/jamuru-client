# ADR-131: 最初の確認の前に、相手の NAT まで届かない keep-alive で自分の NAT を開けておく

## Status

Accepted

## Context

[ADR-119](./ADR-119-send-in-turns-after-a-quiet.md) の「macOS のホストランナーでの実測」で、次のことが分かった。

- macOS のホストランナーの一部（19 台中 7 台）の NAT は、相手のパケットが**こちらの最初の送出より前に**届くと、そのソケットから相手への送出を相手に届けなくなる。外のポートは付け替わらない
- 黙っても抜けない（100 秒〜300 秒、STUN を引いても引かなくても）。ADR-119 の静かな時間は、この NAT には効かない
- 両端を ±10 ms で同時に始めても、両方がこの NAT の組は通らないことがある
- 相手のパケットが届く前に、TTL 3 のパケット（自分の NAT は通り、相手の NAT までは届かない）を送っておくと壊れない。両端がこれを先に出して、本物の送出を 0.4 秒あとにすると、両端の始まりの差が 0.25 秒までは試した組が全部通った

Room check で、アプリを使わない UDP では通るのにアプリで聞こえない組は、ほぼ macOS 同士に限られていた（生の UDP が通った macOS 同士の組の約 17%）。

アプリは 1 つのソケットで部屋の全員と音声をやり取りする（[ADR-093](./ADR-093-one-dual-stack-audio-socket.md)・`UdpMux`）。hop limit（IPv4 の TTL）はソケットの設定なので、1 つのリンクのためにソケットの hop limit を下げると、そのあいだに出たほかのリンクの音声も途中で捨てられる。

## Decision

- **リンクが相手の候補の確認を始めるとき、最初の確認より前に、各候補へ hop limit 3 の keep-alive を 50 ms おきに 3 つ送る。最初の確認はその 0.4 秒あとに送る**（REQ-CON-181）。候補が 1 つの場合も同じ（確認の代わりの最初の keep-alive を 0.4 秒あとに送る）
  - 3 は、自分の NAT と、その外の事業者の NAT（CGNAT）を通り、相手の NAT までは届かない数。実測で 1・2 は効かず、3・5 は効いた
  - 0.4 秒のあいだに相手の確認が届いたら、これまでどおりすぐ答える（自分の NAT は最初の keep-alive で開いている）
- **hop limit を変えて送るあいだ、同じソケットのほかの送出を待たせる。** 送出は全部 `send_datagram` を通り、プロセスに 1 つの読み書きロックを読みで取る。hop limit を変えて送る側は書きで取り、
  hop limit を下げる → 送る → 元に戻す、までを数十マイクロ秒で終える。ロックを取るのは送出のシステムコールのあいだだけで、待つあいだに非同期の処理をはさまない
- **IPv6 のソケット（IPv4 も受ける）では、IPv4 の TTL と IPv6 の hop limit の両方を下げる。** IPv4 の相手への送出にどちらが効くかは OS によって違う。下げられないときは送らずに警告を出す（相手の NAT まで届く keep-alive を先に出すと、ちょうどこの NAT を壊す側になる）
- 鍵交換・確認・音声・Room check の判定は変えない
- 検討して採らなかったもの
  - 最初の確認の前に、相手と開始時刻をそろえる: 両方がこの NAT の組は、±10 ms でそろえても通らなかった
  - 静かな時間を短くする・再 STUN の結果を相手に伝える: この NAT は黙っても抜けず、外のポートも変わらないので、どちらも効かない
  - 送出ごとに hop limit を付ける（`sendmsg` の補助データ）: 付けられる種類が OS ごとに違う（IPv4 を受ける IPv6 ソケットからの IPv4 の送出を含む）。ソケットの設定を短いあいだ変える形なら、3 つの OS で同じ作りになる
  - hop limit を下げた別のソケットを同じポートに開く: 同じポートを 2 つのソケットが持つと、受信は後から開いたほうに渡る（`bind_std` の注記）

## Consequences

- 新しいリンクがつながるまでの時間が 0.4 秒増える。つながったリンクの送出・遅延・音質は変わらない（keep-alive は 3 つ × 候補の数で、確認より前にしか出ない）
- 両端の始まりの差が 0.4 秒を超える組は、この方法では救えない（遅く始めた側の NAT に、先に始めた側の確認が先に届く）。部屋は両端に同時に相手を知らせるので、差は普通その範囲に収まる
- ほかのリンクの送出は、hop limit を変えて送るあいだ（新しいリンクの始まりに 3 回、各回数十マイクロ秒）だけ待つ
- 途中の経路で hop limit が 3 より早く尽きる（自分の側に NAT が 3 段以上ある）場合は、keep-alive が自分の NAT を開けきれず、これまでと同じになる
- `tests/nat/run.sh` のルーターは、外から TTL 2 以下で届いたパケットを捨てる（2 つの家のあいだに事業者のルーターが 2 段以上あることを表す）。これで `record-b-same-time`・`record-both-same-time` が聞こえるようになった
