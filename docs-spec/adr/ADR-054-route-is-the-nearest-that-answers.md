# ADR-054: 送り先は、応答した候補のうち近い経路にする

## Status

Accepted

## Context

接続の確認（[ADR-051](./ADR-051-route-follows-the-peers-answers.md)）は、相手の全候補に keep-alive を送り、最初に相手の keep-alive が届いた候補を送り先にしていた。この「最初に届いた」は経路の良し悪しを表さない。

- 相手は私たちが publish した候補に、50 ms ずつずらして順に確認を送る。どの候補からの応答が先に着くかは、私たちの候補の並びで決まる。
- 並びは優先度の降順だが、ホストの候補（インターフェースのアドレス）は全部同じ優先度で、安定ソートのため、OS がインターフェースを並べた順のままになる。macOS では Tailscale が LAN より前に並び、LAN は 5 番目だった。応答は Tailscale のアドレスが 200 ms 早く着き、送り先に選ばれた。
- 送り先を選ぶ側は、受信を始めるのが自分の確認を全部送り終えたあと（候補の数 × 50 ms）なので、届いた応答はカーネルのバッファに順に溜まっており、その先頭が選ばれる。

有線の Mac と同じ LAN の相手役で測ると、LAN 直に振り分けた側のほうが Tailscale 経由より無音が少なかった（12 窓の無音の個数 4 対 10、再生バッファへの衝突 0 対 8。往復 500 バイト 3000 回の p99 0.36 ms 対 1.38 ms、最大 2.08 ms 対 9.15 ms）。標本は小さいが方向は同じだった。

## Decision

1. **確認の keep-alive に応答を求め、候補ごとの往復時間を測る。** 確認の keep-alive は、5 バイトの payload（種類 1 バイト + 番号 4 バイト）を載せて「同じ番号を載せた keep-alive を返して」と頼む。番号の上位 16 ビットが何回目の確認か、下位 16 ビットが候補の番号。受け取った側は同じ番号を載せた keep-alive を送り元へ返す。返ってきたものは、その候補宛に送ってから返るまでの往復を表す（LAN 0.2 ms、Tailscale の直接 0.6 ms、中継なら 43〜187 ms と、実測どおりの差が出る）。待ちのあいだに溜まった相手の確認も、応答を返せるよう確認の最中に読み続ける（読まずに溜めると、相手は溜まっていた時間を往復時間として測ってしまう）。鍵が合う前でも送れる（遅延の測定用の ping は鍵が合うまで送れない）。接続したあとも、確認の最中の相手から頼まれたら返す。
2. **各候補を 5 回ずつ測り、往復時間の中央値が最も短い候補を選ぶ。** 確認は 80 ms おきに 5 周し、1 周のなかでは候補に 50 ms ずつずらして送る（全部送り終えるのは、候補が 2 つで約 370 ms 後）。1 回の往復時間は、揺れる経路では当てにならない（中継の Tailscale は 43〜187 ms の間で振れる）ので、返ってきた分の中央値で経路を比べる。1 回だけ運良く速く返った経路が選ばれることはなく、返事が半分に満たない経路（取りこぼしの多い経路）は、ほかに返事のある経路があるかぎり選ばれない。種類（LAN・公開・Tailscale）による順位は、中央値が 2 ms 以内で並んだときの決め手にだけ使う（LAN、その他、Tailscale の順）。まだ返っていない確認は、送ってから最短の中央値 + 2 ms が過ぎるまで待つ（それまでに返らなければ、最短より速くはなれない）。全部送り終えたあとの待ちは、通常ほとんど無い。
3. **返事を返さない相手とは繋がらない。** どの候補からも確認の返事が届かなければ、送れた最初の候補に繋ぎに行く（これまでどおり）。相手の keep-alive が届いたことは経路の証拠にしない。1.0.0 までは互換性を保たないと決めている（検証ユーザーだけが使う）ので、返事を返せない古いアプリのために種類の順位で選ぶ道は残さない。publish する候補の優先度は、LAN、その他、Tailscale の順に付ける（IPv6 が IPv4 より少し高いのは同じ近さの中だけ）ので、相手は近い候補宛の確認を先に送る。
4. **開発・調査用に経路を指定できる。** 環境変数 `JAMJAM_ROUTE`（`lan` / `public` / `tailscale` / IP アドレス）を付けて起動すると、その種類（またはそのホスト）の候補だけで接続する。該当する候補が無ければ繋がらず、書き方が間違っていれば（`wifi` など）エラーにする。測定の結果を確かめるときや、別の経路を強いて比べるときに使う。

## 経緯: 順位から測定へ

最初は、LAN、Tailscale、その他の順に候補の優先度を付け、応答した候補のうち最も近い種類を選んでいた（往復時間は測れないと見ていた）。Tailscale が同じ LAN の中で直接繋がる前提で、LAN の次に近いと見たため。両端が別の回線にいて Tailscale が中継（DERP）になると、この前提が崩れた。Mac をスマホのテザリングに繋ぎ、別の回線の相手と繋いだ検証（2026-10-03）では、公開アドレスの応答が先に届いたのに、待つあいだに届いた Tailscale の候補が「近い」として選ばれた。Tailscale は直接の経路を張れておらず、中継経由（`tailscale ping` が 43〜187 ms）で、直接届く公開アドレスより遠回りだった。

種類で順位を付ける限り、この種の例外が続く（LAN のアドレスが別のネットワークと重なる、VPN が直接でなく中継になる）。そこで往復時間を測ることにした。種類の順位は、測った往復時間が並んだときの決め手と、publish する候補の並びに残した。その順では、応答した公開アドレスは直接届く経路の証拠で、Tailscale はそれより良くならない（直接でも同じ道を暗号化して通るだけ、中継なら遅い）ので、公開アドレスを Tailscale の上にした。Tailscale しか応答しない相手とは、どちらの場合も Tailscale で繋がる。

最初の測定は 1 候補 1 回だった。「複数回測ったほうがよい」という指摘（2026-10-03）で 5 回の中央値にした。返事を返せない古いアプリのために種類の順位で選ぶ道も最初は残したが、1.0.0 までは互換性を保たなくてよいので消した。

## Consequences

- 候補の種類に関わらず、最も往復時間が短い経路で繋がる。同じ LAN の相手とは LAN 直、別の回線どうしで Tailscale が中継なら公開アドレス、Tailscale が直接で公開アドレスより速ければ Tailscale になる。
- 確認が終わるのは、5 周の確認を送り終えた直後（候補が 2 つで約 370 ms、10 候補で約 770 ms）。ルームに入るときの 1 回だけで、音声には影響しない。
- 双方が往復時間で選ぶので、片方が LAN、片方が Tailscale という非対称な経路が減る。
- LAN のアドレスが同じ番号帯の別のネットワークと重なる場合でも、そのアドレスから応答が届かない限り選ばれない（ADR-051 の、送れた候補からの応答だけを数える規則はそのまま）。応答は、その候補宛の確認に対する返事としてだけ往復時間に数える。
- 1 候補につき 5 回測り、中央値で選ぶので、1 回の外れた測定では選択が変わらない。ただし測るのは接続の確認の約 0.4 秒のあいだだけで、そのあとで経路の良し悪しが変わっても選び直さない（繋いだあとの往復時間は、これまでどおり ping で測り続ける）。
- Tailscale 以外の重ね合わせ網（WireGuard を直に使う VPN など）は、その他の扱いになる（公開アドレスと同じ順）。同じ番号帯が LAN のプライベートアドレスなら LAN 扱い。
