# ADR-054: 送り先は、応答した候補のうち近い経路にする

## Status

Accepted

## Context

接続の確認（[ADR-051](./ADR-051-route-follows-the-peers-answers.md)）は、相手の全候補に keep-alive を送り、最初に相手の keep-alive が届いた候補を送り先にしていた。この「最初に届いた」は経路の良し悪しを表さない。

- 相手は私たちが publish した候補に、50 ms ずつずらして順に確認を送る。どの候補からの応答が先に着くかは、私たちの候補の並びで決まる。
- 並びは優先度の降順だが、ホストの候補（インターフェースのアドレス）は全部同じ優先度で、安定ソートのため、OS がインターフェースを並べた順のままになる。macOS では Tailscale が LAN より前に並び、LAN は 5 番目だった。応答は Tailscale のアドレスが 200 ms 早く着き、送り先に選ばれた。
- 送り先を選ぶ側は、受信を始めるのが自分の確認を全部送り終えたあと（候補の数 × 50 ms）なので、届いた応答はカーネルのバッファに順に溜まっており、その先頭が選ばれる。

有線の Mac と同じ LAN の相手役で測ると、LAN 直に振り分けた側のほうが Tailscale 経由より無音が少なかった（12 窓の無音の個数 4 対 10、再生バッファへの衝突 0 対 8。往復 500 バイト 3000 回の p99 0.36 ms 対 1.38 ms、最大 2.08 ms 対 9.15 ms）。標本は小さいが方向は同じだった。

## Decision

1. **候補の優先度に経路の近さを入れる。** ホストの候補は、LAN（プライベート・リンクローカル・ユニークローカル・ループバック）、Tailscale の範囲（100.64.0.0/10 と fd7a:115c:a1e0::/48）、その他の順に高くする。IPv6 が IPv4 より少し高いのは同じ近さの中だけ。publish する候補が LAN を先頭にして並ぶので、相手は LAN 宛の確認を先に送る。相手が古い版でも、優先度を見て並べ直すのでこの並びになる。
2. **最初の応答が LAN でなければ、近い経路の応答を少し待つ。** 最初の応答から 500 ms（10 候補に 50 ms ずつ送る相手の、最後の確認が着くまで）のあいだ応答を集め、最も近い経路のものを選ぶ。LAN の応答が届いた時点で待ちをやめる。同じ近さなら先に届いたほうを選ぶ。最初の応答が LAN のときは待たない。待ちの上限は、LAN が無い相手（別の家）との接続が 500 ms 遅くなること。
3. **応答の往復時間は使わない。** 確認の keep-alive に応答の仕組みは無く、相手が自分の確認を私たちの候補に送っているだけなので、この段階で往復時間は測れない。近さの順（LAN 0.2 ms、Tailscale 0.6 ms）は上の実測と合っており、確認のパケットの形を変えて往復時間を測る必要は今は無い。

## Consequences

- 同じ LAN の相手とは、並びやタイミングによらず LAN 直で繋がる。応答が LAN から届かなければ、これまでどおり届いた候補が選ばれる。
- LAN が無い相手との接続は、最大 500 ms 遅くなる。ルームに入るときの 1 回だけで、音声には影響しない。
- 双方が同じ基準で選ぶので、片方が LAN、片方が Tailscale という非対称な経路が減る。
- LAN のアドレスが同じ番号帯の別のネットワークと重なる場合でも、そのアドレスから応答が届かない限り選ばれない（ADR-051 の、送れた候補からの応答だけを数える規則はそのまま）。
- Tailscale 以外の重ね合わせ網（WireGuard を直に使う VPN など）は、その他の扱いになる。同じ番号帯が LAN のプライベートアドレスなら LAN 扱い。
