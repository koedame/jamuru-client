# ADR-054: 送り先は、応答した候補のうち近い経路にする

## Status

Accepted

## Context

接続の確認（[ADR-051](./ADR-051-route-follows-the-peers-answers.md)）は、相手の全候補に keep-alive を送り、最初に相手の keep-alive が届いた候補を送り先にしていた。この「最初に届いた」は経路の良し悪しを表さない。

- 相手は私たちが publish した候補に、50 ms ずつずらして順に確認を送る。どの候補からの応答が先に着くかは、私たちの候補の並びで決まる。
- 並びは優先度の降順だが、ホストの候補（インターフェースのアドレス）は全部同じ優先度で、安定ソートのため、OS がインターフェースを並べた順のままになる。macOS では Tailscale が LAN より前に並び、LAN は 5 番目だった。応答は Tailscale のアドレスが 200 ms 早く着き、送り先に選ばれた。
- 送り先を選ぶ側は、受信を始めるのが自分の確認を全部送り終えたあと（候補の数 × 50 ms）なので、届いた応答はカーネルのバッファに順に溜まっており、その先頭が選ばれる。

有線の Mac と同じ LAN の相手役で測ると、LAN 直に振り分けた側のほうが Tailscale 経由より無音が少なかった（12 窓の無音の個数 4 対 10、再生バッファへの衝突 0 対 8。往復 500 バイト 3000 回の p99 0.36 ms 対 1.38 ms、最大 2.08 ms 対 9.15 ms）。標本は小さいが方向は同じだった。

## Decision

1. **確認の keep-alive に応答を求め、候補ごとの往復時間を測る。** 確認の keep-alive は、5 バイトの payload（種類 1 バイト + 候補の番号 4 バイト）を載せて「同じ番号を載せた keep-alive を返して」と頼む。受け取った側は同じ番号を載せた keep-alive を送り元へ返す。返ってきたものは、その候補宛に送ってから返るまでの往復を表す（LAN 0.2 ms、Tailscale の直接 0.6 ms、中継なら 43〜187 ms と、実測どおりの差が出る）。待ちのあいだに溜まった相手の確認も、応答を返せるよう確認の最中に読み続ける（読まずに溜めると、相手は溜まっていた時間を往復時間として測ってしまう）。keep-alive の形のまま（payload が増えるだけ）なので、古いアプリは普通の keep-alive として読み、何も返さない。鍵が合う前でも送れる（遅延の測定用の ping は鍵が合うまで送れない）。接続したあとも、確認の最中の相手から頼まれたら返す。
2. **往復時間が最も短い候補を選ぶ。** 種類（LAN・公開・Tailscale）による順位は使わない。ただし 2 ms 以内の差は 1 回の測定の揺れなので、その範囲では近い種類（LAN、その他、Tailscale の順）を取る。まだ返っていない候補は、その候補に確認を送ってから、最短の往復時間 + 2 ms が過ぎるまで待つ（それまでに返らなければ、最短より速くはなれない）。全候補への確認を送り終えてから待つので、通常はほとんど待たない。
3. **相手が応答を返さないとき（古いアプリ）は、近い種類の経路を選ぶ。** 相手が自分の確認を私たちの候補に送ってくるので、それが届いた候補のうち、LAN、その他、Tailscale の順に近いものを選ぶ。最初に届いたのが LAN でなければ、500 ms（10 候補に 50 ms ずつ送る相手の、最後の確認が着くまで）近い経路を待つ。Tailscale を公開アドレスの下にした理由は下の「経緯」。publish する候補の優先度も同じ順にする（IPv6 が IPv4 より少し高いのは同じ近さの中だけ）ので、相手は近い候補宛の確認を先に送る。
4. **開発・調査用に経路を指定できる。** 環境変数 `JAMJAM_ROUTE`（`lan` / `public` / `tailscale` / IP アドレス）を付けて起動すると、その種類（またはそのホスト）の候補だけで接続する。該当する候補が無ければ繋がらず、書き方が間違っていれば（`wifi` など）エラーにする。測定の結果を確かめるときや、別の経路を強いて比べるときに使う。

## 経緯: 順位から測定へ

最初は、LAN、Tailscale、その他の順に候補の優先度を付け、応答した候補のうち最も近い種類を選んでいた（往復時間は測れないと見ていた）。Tailscale が同じ LAN の中で直接繋がる前提で、LAN の次に近いと見たため。両端が別の回線にいて Tailscale が中継（DERP）になると、この前提が崩れた。Mac をスマホのテザリングに繋ぎ、別の回線の相手と繋いだ検証（2026-10-03）では、公開アドレスの応答が先に届いたのに、待つあいだに届いた Tailscale の候補が「近い」として選ばれた。Tailscale は直接の経路を張れておらず、中継経由（`tailscale ping` が 43〜187 ms）で、直接届く公開アドレスより遠回りだった。

種類で順位を付ける限り、この種の例外が続く（LAN のアドレスが別のネットワークと重なる、VPN が直接でなく中継になる）。そこで往復時間を測ることにした。種類の順位は、測れない相手（古いアプリ）のための代わりに残す。その順では、応答した公開アドレスは直接届く経路の証拠で、Tailscale はそれより良くならない（直接でも同じ道を暗号化して通るだけ、中継なら遅い）ので、公開アドレスを Tailscale の上にした。Tailscale しか応答しない相手とは、どちらの場合も Tailscale で繋がる。

## Consequences

- 候補の種類に関わらず、最も往復時間が短い経路で繋がる。同じ LAN の相手とは LAN 直、別の回線どうしで Tailscale が中継なら公開アドレス、Tailscale が直接で公開アドレスより速ければ Tailscale になる。
- 新しいアプリどうしでは、確認が終わるのは全候補に確認を送り終えた直後（候補の数 × 50 ms）。LAN だけを待つ 500 ms の上乗せは無い。古いアプリが相手のときだけ、最初に届いたのが LAN でなければ最大 500 ms 遅くなる。ルームに入るときの 1 回だけで、音声には影響しない。
- 双方が往復時間で選ぶので、片方が LAN、片方が Tailscale という非対称な経路が減る。
- LAN のアドレスが同じ番号帯の別のネットワークと重なる場合でも、そのアドレスから応答が届かない限り選ばれない（ADR-051 の、送れた候補からの応答だけを数える規則はそのまま）。応答は、その候補宛の確認に対する返事としてだけ往復時間に数える。
- 1 候補につき測るのは 1 回。揺れは 2 ms の幅で吸収し、それより大きく外れた 1 回の測定が選択を変える恐れは残る。繋いだあとの往復時間は、これまでどおり ping で測り続ける。
- Tailscale 以外の重ね合わせ網（WireGuard を直に使う VPN など）は、その他の扱いになる（公開アドレスと同じ順）。同じ番号帯が LAN のプライベートアドレスなら LAN 扱い。
