# ADR-050: 固まったオーディオドライバへの呼び出しには上限を付け、待ちが他の操作を止めないようにする

## Status

Accepted

## Context

Mac 実機（beta.20）で、ルームに入った直後に AG06 を開く呼び出しが macOS の中で止まり、11 分のあいだ音声の設定がほぼ操作できなくなった。AG06 は繋がったままで、最初に止まったのは macOS 側（`coreaudiod` かドライバ）だった。jamjam の問題は、**止まった呼び出しの後ろに、無関係な操作まで並んだこと**にある。

1. セッションのスレッドがデバイスを開く呼び出しで止まった。このスレッドは、コマンドの受付（設定の変更・停止）と、ネットワークの受信・keep-alive も運ぶので、停止するとコマンドが溜まり、接続も切れる。
2. 設定の読み書きは、デバイスの一覧を読んでいるあいだ、変更を順番に通すロックを握っていた。一覧の読み出しも同じドライバに聞くので 1 回 60 秒かかり（入力・出力で 2 回）、設定の変更が 2 分おきに 1 件ずつしか通らず、`settings_get` は返らなかった。
3. デバイスを開く待ちに上限がなく、利用者は別の機材に切り替えて逃げることもできなかった。

## Decision

1. **ドライバを呼ぶ処理は、専用のスレッドで行い、待つ時間に上限を付ける。** ストリームは作ったスレッドから動かせないので、そのスレッドがストリームを持ち続ける（`StreamHost`）。上限は開くのが 8 秒、一覧を読むのが 3 秒。超えたら `DeviceUnresponsive` を返す。戻らない呼び出しは止められないので、専用のスレッドに残し、戻ってきたら結果を捨てる。
2. **セッションのスレッドは、デバイスを開く処理を待たない。** 開き直しは別のスレッドに任せ、セッションのスレッドは毎周、終わったかを見るだけにする（`DeviceSlot`）。開いている途中で別のデバイスを選ぶと、途中のものは見捨てて、新しいエンジンですぐ開く。
3. **設定の読み書きは、一覧の読み出しを待たない。** 一覧は変更の順番待ち（`changing`）の外で、非同期ランタイムのスレッドを塞がずに読む。一覧が固まっている間は最後に読めた一覧を出し、固まった呼び出しが戻るまで同じ一覧を重ねて読まない。
4. **待ちが尽きたら、画面に出す。** 開けなかったデバイスを `streaming_status` の `device_problems` で返し、画面が「このデバイスが応答しません」と知らせる。握りつぶして黙らない。
5. **固まりを再現する口を、テストとデバッグの版にだけ置く。** `jamjam::audio::fault` が、ドライバへの呼び出し（一覧・開く）を指定の秒数だけ返さなくする。フィーチャー `fault-injection` の外では、コードごと存在しない。デバッグの口からは `debug.device_hang`（[ADR-044](./ADR-044-portals-and-permissions.md)）で呼ぶ。

## Consequences

- REQ-AUD-123 の検証は、単体テスト（上限・見捨てて別のデバイスを開く・最後の一覧）と、`debug.device_hang` を使った動作確認で行う。
- 開き直しを別のスレッドに任せたので、取り込みのデバイスを切り替えたときの「開けたか」の反映は、開き終わった周に遅れる。無音の長さは変わらない。
- macOS 側で固まる原因そのもの（`coreaudiod`・ドライバ）は jamjam では直せない。ここでは、固まっても他の操作を巻き込まないことだけを保証する。
- 上限（8 秒）は、マイクの許可を求める表示が出ている間に超えないよう、開くのに通常かかる時間より十分長くしてある。
