# ADR-114: 入室前に回線と機器を確かめる

## Status

Accepted。

## Context

つながらない・音が出ない原因の多くは、利用者には見えない（ルーターのポートの割り当て、IPv6 が外に出られるか、UPnP、マイクの許可）。
入室して初めて「つながらない」と分かるのでは遅く、何を直せばよいかも分からない。
設定の「診断とサポート」タブには診断が既にあるが、次の欠陥があった。

- NAT の種類を、STUN サーバーごとに**別のソケット**から測っていた。ソケットが違えばポートも違うので、どのルーターでも「相手ごとに変わる」に見えた。「制限コーン」は一度も出なかった
- IPv6 は、`[::]` に束縛したソケットで測っていた。デュアルスタックのソケットでは IPv6 の答えが返らず、IPv6 があっても「無い」と出た
- UPnP を確かめていなかった
- 結果が「NAT 種別」のような内部の言葉で、何をすればよいかが出なかった

## Decision

### 1. 新しい仕組みは作らず、既存の診断を直して広げる

診断タブ・`diagnostics_run_*` コマンド・`src/diagnostics/*` をそのまま使う。入り口を足す（5）。

### 2. NAT は、音声と同じソケット 1 本から、複数の STUN へ同じ回に問い合わせて測る

- 見えたアドレスとポートがすべて同じなら `Stable`、サーバーによって違えば `PerDestination`、答えが 2 台未満なら `Unknown`。この家のアドレスがそのまま公開アドレスなら `NoNat`
- 測れるのは**ポートの割り当て（マッピング）だけ**で、相手のパケットを通すか（フィルタリング）は、手元の STUN サーバーでは区別できない。そのため、実際には測れていない「フルコーン」「制限コーン」「ポート制限コーン」「対称型」の名前は使わない（`Symmetric` は `PerDestination` に置き換えた）
- `PerDestination` のルーターは、UPnP が応えない限り「繋がりにくい相手がいる」（`PeerReach::Narrow`）。相手側にも同じルーターがあるとき、IPv4 では繋がりにくい

### 3. IPv6 と UPnP は、実際に確かめる

- IPv6: 公開できるアドレス（`2000::/3`）があり、かつ音声と同じソケットで STUN から IPv6 の答えが返ったときだけ `Usable`。アドレスはあるが答えが無ければ `NoRoute`
- UPnP: ルーターを探して外側のアドレスを尋ねるだけ。**ポートは開けない**（最小権限。診断のたびにルーターの状態を変えない）。結果は `Answers` / `Off` / `NoRouter` / `Refused` / `DoubleNat`。設定「ルーターのポートを自動で開く」がオフなら、診断でも尋ねない（`Off`）。探す処理は ADR-113 と同じものを共有し、尋ねる部分だけを別の関数（`port_mapping::probe`）にした

### 4. 機器は開かない

診断はマイクやスピーカーのストリームを開かない。開くと、(a) macOS のマイクの許可を求める画面が出る、(b) 機器全体のバッファサイズを書き換える機器（ASIO など）がある、(c) 入室中なら音声のセッションと機器を取り合う、の副作用が出るため。

- 機器が使えるかは、一覧・48 kHz への対応・macOS のマイクの許可の状態（`許可されていない` / `まだ決まっていない`）で判断する。許可されていなければ直し方を出す
- 最小バッファは、OS ごとの目安（`src/environment.rs`）であって実測ではない。画面に「目安」と書く
- 実際に開けるかは、入室して音声のセッションが始まったときに分かる。**この限界は、診断が「開ける」と保証しないこととして受け入れる**

### 5. 入り口は入室前の画面。結果は「繋がりやすさ」と直し方で出す

- 接続パネルに「回線と機器を確かめる」のリンクを置き、押すと設定ウィンドウを「診断とサポート」タブで開く（`window_open_settings` に任意の `tab` を足した）。診断は、そのタブの「診断を実行」で始まる。自動では始めない
- ネットワークのカードの先頭に「繋がりやすさ」を出し、続けて IP・NAT・IPv6・UPnP を並べる
- 問題は「何が起きているか」と「何をすればよいか」の 1 組で、`ProblemCode` に追加した（`PerDestinationNat`・`UpnpOff`・`UpnpNoRouter`・`UpnpRefused`・`UpnpDoubleNat`・`Ipv6Unreachable`・`StunUnanswered`・`MicrophoneRefused`・`MicrophoneUndecided`）。文言は日本語・英語の両方

### 6. 同意の前に外へ出さない

診断は、これまでと同じく、利用規約に同意するまでサーバーにも STUN にも問い合わせない（REQ-TRM-003。`signaling_client` が拒む）。診断の結果は画面に出るだけで、サーバーには送らない。公開の `privacy.md` に、診断でも STUN に問い合わせること・UPnP は尋ねるだけであることを足した。

## Consequences

- `NatType` の値が変わる。1.0.0 前なので、互換は保たない（ADR 以前の値を読む場所は UI だけで、同じ変更で直した）
- 診断が STUN に出す問い合わせが、複数サーバーへ 1 回ずつ増える（音声やアドレス以外は含まない）
- 機器を開かないので、診断の結果だけでは「その機器で音が出る」とは言い切れない

## 検証

- 純粋な判定（`nat_type_of`・`ipv6_status`・`upnp_status`・`PeerReach::of`・`reach_problems`）と、マイクの許可の問題の単体テスト（`src/diagnostics/`）
- 偽のルーターと偽の STUN を使った統合テスト（`tests/port_mapping_test.rs`）: UPnP を探しても何も転送されない・二重 NAT・ルーター無し・複数サーバーの同回測定
- 画面は、日本語・英語の全ての問題コードで翻訳漏れが無いこと（`ui/src/i18n/translated-components.test.tsx`）と、実画面のスクリーンショット
