# ADR-110: 音声のパケットに優先の印を付ける

## Status

Accepted。

## Context

IP のパケットの見出しには、優先度を書く 6 ビットの欄がある（DSCP。IPv4 では ToS、IPv6 では Traffic Class の上位 6 ビット）。送る側がソケットに値を設定すると、そのソケットから出るパケットすべてに付く。
家庭の Wi-Fi のアクセスポイントと、送る側の PC の Wi-Fi は、この値を見て WMM の 4 つの待ち行列（音声・映像・普通・背景。RFC 8325）のどれで送るかを決める。
音声の印（EF = 46）が付いていれば、同じ Wi-Fi で動画やダウンロードが流れていても、音声のパケットが先に送られ、揺れと欠けが減る見込みがある。
インターネットの途中では消されることが多いので、効くのは主に家の中の区間になる。jamuru は低い遅延が最優先で、この印は遅延を増やさずに揺れを減らす手段になる。

これまで音声の UDP ソケットには何も付けていなかった。

## Decision

### 1. 音声のソケットに EF（46）を付ける

付けるのはセッションの音声のソケット 1 本（全員のリンクが共有するソケット。ADR-093）。シグナリング（WebSocket）や更新の確認には付けない。
値は WebRTC の音声の推奨（RFC 8837）と同じ EF（46。ToS / Traffic Class のバイトでは 0xB8）にする。

OS ごとの付け方:

| OS | 付け方 | 理由 |
|----|--------|------|
| Linux | `IP_TOS` と `IPV6_TCLASS` を 0xB8、`SO_PRIORITY` を 6 | IPv6 のソケットは IPv4 の相手へ IPv4 の見出しで送るので、両方に付ける。`SO_PRIORITY` は手元の Wi-Fi ドライバの待ち行列に載せる（0〜6 は特権が要らない） |
| macOS | 付けない | `IP_TOS` / `IPV6_TCLASS` は、両用ソケットでは見出しに載らなかった。Apple の `SO_NET_SERVICE_TYPE`（`NET_SERVICE_TYPE_VO`）は、付けると Mac から送る音声に無音区間が出た（下の「測定」） |
| Windows | `IP_TOS` と `IPV6_TCLASS` を 0xB8 | Windows 11（ビルド 26200）で、レジストリの `DisableUserTOSSetting` が無い既定のまま、`IP_TOS` を付けた UDP のパケットが 0xB8 で届くことを測った（下の「測定」）。管理者の権限は要らない |

Windows で qWAVE（`QOSCreateHandle` → `QOSAddSocketToFlow` に `QOSTrafficTypeVoice`）を使わない理由:

- 音声のソケットは IPv4 と IPv6 の両用の 1 本（ADR-093）。qWAVE は、IPv6 のソケットから IPv4 の宛先へのフローを作れない（`ERROR_INVALID_PARAMETER`）。IPv4-mapped の宛先も作れない（`ERROR_NOT_FOUND`）。IPv4 の相手には印を付けられない。
- フローは宛先ごとに作るため、最初のパケットが印なしで出て、宛先が変わるたびに足す仕組みが要る。
- 音声に付く値が 56（CS7）で、46 ではない。46 を指定する `QOSSetOutgoingDSCPValue` は管理者の権限が要る。

古い Windows で `IP_TOS` が無視されるかは測っていない。無視される場合は印なしで動く（害は無い）。

付けられなかったとき（OS が対応しない・拒まれた）は、ログに理由を残し、印なしで音声を送り続ける。印は要望であって、音声の送受信の条件にしない。

### 2. 設定で切り替える。既定はオン

設定 `voice_priority`（一般タブの「音声を優先して送る」）で切り替える。既定はオン。

最初は既定をオフにしていた。印の付け方（Windows と Linux）が見出しに載ることは測れたが、Wi-Fi で音声が良くなるか悪くなるかは測れておらず、効果を測れる送り手だった Mac では、音声の待ち行列（macOS の `NET_SERVICE_TYPE_VO`）を使うと無音区間が出たため。
その後、Windows を Wi-Fi だけにして、混雑のある回線で設定のオン・オフを交互に 12 回ずつ測った（下の「Wi-Fi での測定」）。オンの方が着信の隙間が短く、受信の欠けが少なく、往復の遅延も短かった。混雑の無い回線では差が読み取れず、悪くなる向きの差は見つからなかった。低い遅延と音質を犠牲にしないという方針は守れるので、既定をオンにした。
macOS は今も付けない（下の「macOS」）ので、既定がオンでも Mac の動きは変わらない。

設定ファイルに `voice_priority = false` が書かれている端末（設定を一度保存した端末）は、オフのまま変わらない。セッションの開始時にソケットへ付けるので、変更は次のセッションから効く。

### 3. 利用者の情報の送信は変わらない

パケットの中身も宛先も変えず、見出しの優先度の欄だけを変える。利用者の情報の送信・保存・見え方は変わらないので、プライバシーの説明（`docs/getting-started/privacy.md`）は直さない。

## Consequences

- Windows と Linux では、既定で音声に印が付く。同じ Wi-Fi で他の通信が流れていても、音声が先に送られる（Windows の Wi-Fi で効果を測った。Linux の Wi-Fi は未測定）。パケットの中身は変わらない。
- 設定をオフにすると何も変わらない。macOS は設定によらず印を付けない。
- 印を消す・落とすネットワークでは、付けても付けなくても同じ。
- 付けるのはソケットのオプション 1 つで、依存の追加は無い。パケットごとの処理も増えない。

## 検証

Linux では、印を付けたソケットから送ったデータグラムを、受け取る側が `IP_RECVTOS` / `IPV6_RECVTCLASS` で読み、IPv4・IPv6 のどちらも 0xB8（EF）であること、付けないソケットでは 0 であることをテストにした（`src/network/priority.rs`）。
Windows・macOS では、ベータ版を入れた端末から LAN の Linux へ音声を送り、受け取る側の見出しの値を測る。結果は下の「測定」に残す。

## 測定

### Windows でどの付け方が効くか（IPv4）

Windows 11（ビルド 26200、`DisableUserTOSSetting` は未設定）の PC から、同じ LAN の Linux へ UDP を 30 個ずつ送り、受ける側が `IP_RECVTOS` で IPv4 の見出しの ToS を読んだ。

| 送る側のソケットと付け方 | 受けた ToS（30 個中） |
|---|---|
| IPv4 ソケット、付けない | 0x00 |
| IPv4 ソケット、`IP_TOS` = 0xB8 | 0xB8（30） |
| 両用ソケット、`IP_TOS` = 0xB8、IPv4 の宛先 | 0xB8（30） |
| IPv4 ソケット、qWAVE の音声フロー（IPv4 の宛先） | 0xE0 = 56（30） |
| 両用ソケット、qWAVE（IPv4 の宛先） | フローを作れず（`ERROR_INVALID_PARAMETER`）、0x00 |
| 両用ソケット、qWAVE（IPv4-mapped の宛先） | フローを作れず（`ERROR_NOT_FOUND`）、0x00 |
| 両用ソケット、qWAVE（宛先なし） | フローを作れず（`ERROR_INVALID_PARAMETER`）、0x00 |

`IPV6_TCLASS` を Windows で付けるところまでは通った（エラーなし）が、受ける側で読む IPv6 の経路が手元に無く、届いた値は測っていない。

### オン・オフの比較（Windows、有線）

Windows 11 の PC（有線）を相手役（Linux、有線）のルームに入れ、設定をオン・オフにして入り直し、相手役の側で `tcpdump -v` を取った。

| 設定 | PC から届いたパケットの ToS（400 個） |
|---|---|
| オン | 0xB8（400） |
| オフ | 0x00（400） |

同じ条件で、実機の確認の道具（無音区間・遅延・負荷）を回した。どちらも NG なし。往復の遅延は 21.7ms で同じ、無音区間は 0 か所で同じ、underrun は +0 で同じ。有線の静かな回線なので、差が出ないのが期待どおり。

### macOS

ベータ版 beta.209（`SO_NET_SERVICE_TYPE` を `NET_SERVICE_TYPE_VO` にした版）を入れた Mac M4 Max と、有線の Linux の相手役で、同じ確認を交互に回した。

| 設定 | 実行 | Mac から相手役へ送る音の無音区間（8 サンプル以上） |
|---|---|---|
| オン | 1 回目 | 1 か所 |
| オフ | 1 回目 | 0 か所 |
| オン | 2 回目 | 2 か所 |
| オフ | 2 回目 | 0 か所 |
| オン | 3 回目 | 1 か所 |
| オフ | 3 回目 | 0 か所 |

オンのときだけ、3 回とも Mac から送る音に無音区間が出た（逆向きは 0 か所）。このとき Mac から出るパケットの ToS は、Tailscale の中の見出しでも 0x00 だった。つまり `NET_SERVICE_TYPE_VO` は見出しの印としては効かず、オンのときだけ無音区間が出た。欠ける理由（Mac の無線の待ち行列の扱い）までは測っていない。

beta.210（`IP_TOS` / `IPV6_TCLASS` を付ける版）では、Mac の両用ソケットから LAN の相手役へ送るパケットの見出しが 0x00 のままだった（相手役から Mac へは 0xB8）。macOS は見出しに印を載せられないので、付けないことにした。

### 最終のベータ版（beta.212）

- Windows（有線）: 既定のオフで、相手役に届いたパケット 400 個は `tos 0x0`。オンにして入り直すと 400 個すべてが `tos 0xb8`、ログに `Audio packets are marked as voice (IP_TOS and IPV6_TCLASS)`。
- Mac: オンにしても印は付かず、ログに `Audio packets are not marked as voice: macOS does not carry the mark …` が出る。この版でオンのまま 3 回測り、Mac から相手役へ送る音の無音区間は 3 回とも 0 か所（beta.209 では 3 回中 3 回）。このとき Mac の入出力は仮想デバイスだったので、逆向きの無音区間と underrun は別の要因（仮想デバイスの時計）で揺れた。

### Wi-Fi での測定（Windows、混雑あり・なし）

Windows 11 の PC（Realtek 8852BE の Wi-Fi。有線は測定のあいだ無効にして、Wi-Fi だけで繋いだ）から、有線の Linux の相手役へ 1000Hz の音を送り続けた。設定のオン・オフを交互に切り替えて入り直し、1 回あたり入室の 8 秒後から 30 秒を測った。
測ったのは、相手役の出力の 3 秒の録音 3 回の無音区間（8 サンプル以上）、相手役の受信の欠け（`starved`）、相手役の NIC に着いたパケットの間隔、端末の往復の遅延と Jitter buffer。端末が選んだ経路は全回 LAN の Wi-Fi。相手役自身の詰まり（`thread_stall`）は全回 0。
混雑は、同じ Wi-Fi の別の機械から有線の機械へ、TCP を上り・下りに 60 Mbit/s ずつ流して作った（この Wi-Fi の上限は上下合わせて約 260 Mbit/s）。

| | 混雑あり オン | 混雑あり オフ | 混雑なし オン | 混雑なし オフ |
|---|---|---|---|---|
| 回数 | 12 | 12 | 4 | 4 |
| 無音区間の出た回 | 0 | 3（計 6 か所） | 0 | 0 |
| 約 0.5 秒の長い停止の回 | 1 | 1 | 1 | 1 |
| 長い停止を除く: 受信の欠けが 10 以上の回 | 0 / 11 | 4 / 11 | 1 / 3 | 0 / 3 |
| 長い停止を除く: 着信の最大の隙間（中央値） | 27 ms | 84 ms | 22 ms | 22 ms |
| 長い停止を除く: 往復の遅延（中央値） | 24.2 ms | 26.9 ms | 27.8 ms | 24.9 ms |
| 長い停止を除く: Jitter buffer（中央値） | 1.3 ms | 4.0 ms | 2.7 ms | 2.7 ms |

- 混雑のある Wi-Fi では、オフにすると 50〜100ms の着信の隙間が毎回のように出て、受信バッファが 4ms に増え、12 回中 3 回で無音区間が出た。オンでは 50ms を超える隙間が出なかった。順序の偏りを消すため、12 回のうち 6 回はオフを先に回した。
- 約 0.5 秒の長い停止は、オンにもオフにも同じ回数出た。印の有無と関係のない Wi-Fi の停止に見える（原因までは測っていない）。
- 混雑の無い Wi-Fi は 4 回ずつで、差は読み取れない（長い停止を除く 3 回ずつ。オンで受信の欠けが 31 出た回が 1 回、オフで 3 以下）。
- 限界: 送り手は Windows 1 台、アクセスポイントは 1 台、混雑は 1 種類。Linux の Wi-Fi は測っていない。
