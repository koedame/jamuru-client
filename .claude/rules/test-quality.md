# テスト品質ルール

## 絶対禁止

1. **テストの削除・無効化禁止**
   - 既存テストを削除してはならない
   - `#[ignore]` で無効化してはならない
   - テストが失敗する場合は、テストではなく実装を修正する

2. **テストの形骸化禁止**
   - `assert!(true)` のような意味のないアサーション禁止
   - テスト対象の動作を実際に検証すること

3. **テストカバレッジの低下禁止**
   - 新機能追加時は対応するテストも追加
   - 公開 API には必ずテストを書く

## E2E はアプリの挙動を変えない

GUI E2E・結合テストは、**配布するアプリと同じ挙動のまま**確かめる。テストを通すために、アプリの設定・ビルドの最適化・音質や遅延の設定・
負荷を軽くする経路を、テストの中だけ変えない（テストが通っても、使う人の環境で起きることを確かめたことにならない）。

- 満員のルームのように、今のマシンで捌ける数を超える構成は、E2E を通すためにアプリを軽くして置かない。**今のマシンで捌ける上限までをテストにし**、
  それより上は「理論値 N、検証済み M」と事実として持つ（`docs/development/testing.md`「ルームの人数」）。上限は
  `how_many_peers_the_app_takes`（`tests/e2e/tests/gui.rs`）で測る
- 上限が低いのはアプリの軽量化・高速化の課題。E2E 側で隠さず、数字として残して改善の前後で比べる
- 低い遅延・良い音質というアプリの本質的な要件を、テストを楽にするために落とさない
- E2E が拾うのは、実環境でしか見つからない課題（実機・実回線・実際のデバイスの癖）

## 推奨事項

- テストは独立して実行可能であること
- テスト名は動作を説明する名前にする
- エッジケースもテストする

## 例外

- 測定の道具として手で回すものは `#[ignore = "理由"]` を付けてよい（検査を無効にしているのではなく、通る・通らないを持たない）

- 明らかに不要になったテスト（削除された機能のテスト）は削除可能
- ただし、削除理由をコミットメッセージに明記すること
