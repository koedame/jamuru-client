# テスト

jamuruのテストを実行する方法を説明します。

## テストの実行

### 全テスト実行

```bash
cargo test --all-targets
```

### 特定のテストを実行

```bash
# テスト名で絞り込み
cargo test test_name

# 特定のモジュールのテスト
cargo test audio::
cargo test network::
```

### テストの詳細出力

```bash
cargo test -- --nocapture
```

## テスト構成

テストは [docs-spec/behavior/](../../docs-spec/behavior) の BDD 仕様に基づいています。

| テストファイル | 対応仕様 |
|--------------|---------|
| `tests/connection_test.rs` | `docs-spec/behavior/connection.feature` |
| `tests/audio_quality_test.rs` | `docs-spec/behavior/audio-quality.feature` |
| `tests/latency_test.rs` | `docs-spec/behavior/latency.feature` |
| `tests/i18n_test.rs` | `docs-spec/behavior/i18n.feature` |
| `tests/port_mapping_test.rs` | ルーターへのポート開放（UPnP）。偽のルーター（SSDP と SOAP）に対する統合テスト |
| `tests/port_prediction_test.rs` | 宛先ごとにポートを変える NAT の模型（ループバック）が、候補に複数のポートを並べること |
| `tests/bad_line_test.rs` | 悪い回線の模擬が、設定した欠け・遅延・帯域・順番・全断のとおりに働くこと（ADR-124） |
| `tests/line_trial.rs` | 悪い回線に通したアプリの往復・受信バッファ・欠けの補いを表にする道具。引数なしは短い組を回す（ADR-124） |

## ルーターのポート開放（UPnP）

ルーターにポートを開けてもらう機能（ADR-113）は、2 通りで確かめます。

- `cargo test --test port_mapping_test`: 手元のループバックに立てた偽のルーターに対して、頼みが通る・断られる・同じ番号が使用中・二重の NAT・ルーター無し・更新・閉じる、を確かめます。毎回回ります。
- `tests/upnp/run.sh`: 本物のルーター（miniupnpd）をコンテナで動かし、ルーターの先の端末から送ったデータグラムが音声のソケットに届くか、閉じると転送の規則が消えるか、UPnP の無いルーターでも STUN だけで続くか、設定オフでルーターに触れないかを確かめます。docker と、コンテナに `NET_ADMIN` を渡せる権限が要ります。CI では回しません。

## 宛先ごとにポートを変える NAT（ポートの予測）

相手の NAT が宛先ごとにポートを変えるとき、相手の送り出すポートを予測して送る機能（ADR-115）は、3 通りで確かめます。

- `cargo test --lib port_prediction` と `cargo test --lib network::connection`: ポートの並びごとの予測・送る量の上限・応答だけを受け入れること・NAT の模型（ループバック）で経路が相手の実際のポートへ移ること。毎回回ります。
- `cargo test --test port_prediction_test`: 宛先ごとにポートを変える NAT が候補に複数のポートを並べ、1 つのポートを使う NAT は並べないこと。毎回回ります。
- `tests/nat/run.sh [ケース名 ...]`: 2 つのルーター（カーネルの iptables）の内側のアプリが、STUN サーバーを介して接続できるかを、NAT の組み合わせごとに確かめます（cone・random・宛先アドレスごとに順に割り当てる sequential・ポートセットの portset）。`NAT_LAB_AUDIO_SECS=10` を付けると、経路が決まったあとに音声を送り、遅延と欠落も出します。`NAT_LAB_PEER=<バイナリ>` で別の版のアプリと比べられます。ルーターが「こちらが送るより前に届いた相手のパケット」を覚える組（`record-*`）と、両端が黙って順番に先に送り直して抜ける組（`patient-*`、1 ケース 5 分前後。ADR-119）もあります。docker と、コンテナに `NET_ADMIN` を渡せる権限が要ります。CI では回しません。

## ルームの人数

ルームは最大 16 人（相手 15 人）。1 台のアプリは相手 15 人ぶんの音声（毎秒 11250 パケット）を受けて送る。
16 人ぶんのアプリを 1 台のマシンで動かすと、相互 240 本の接続を 1 台で捌くことになるので、**理想の確かめは人数ぶんのマシン**。
いまのマシンで確かめられた範囲を、理論値と分けて表に持つ（測った日・マシン・ビルドを必ず添える）。

| 確かめ方 | 理論値 | 検証済み | 測った日・条件 |
|---|---|---|---|
| コアの結合テスト（`tests/mesh_connection_test.rs`） | 16 人 | 16 人（全員が全員の音を受ける） | 毎回 |
| 実アプリ 1 台と軽い相手 9 個（最適化ビルド） | 相手 15 人 | 相手 9 人（全パケット受信・空読み 0・往復 4.0 ms・受信スレッド約 25%） | 10/13、16 スレッド |
| 実アプリを 1 台のホストに N 個立てる（`jamjam-room-check.py`、最適化ビルド） | 16 人 | 6 人は全員が全員の音を聞いた。10 人は 1 回目は聞こえたが、続けると欠けた（ホストが飽和、load 30 超）ので品質の結論にしない | 10/13、16 スレッド |
| 実アプリを GitHub-hosted runner に分けて立てる（`room-check.yml`、最適化ビルド。ADR-117） | 16 人 | 16 人（4 台×4 人・2 台×8 人のどちらも、全員が全員の番を 93〜100 % の窓で聞いた。他人の番に聞こえたことは無い）。runner の CPU は共有なので性能の結論にはしない | 11/7、毎晩 |
| 同じ確認に Windows と macOS の runner を混ぜる（`room-check.yml`、ADR-118） | 16 人 | 10 人（Linux 4 人・Windows 4 人・macOS 2 人。6 台）。ランナーどうしが直接 UDP を送り合えるかを、アプリを使わずに 16 本の流れで先に確かめ、通らなかった組は「環境のせいで測れなかった」として不合格に数えない（通ったのにアプリで聞こえない組は不合格）。直近 4 回のうち 3 回は全員が全員の番を聞けた。残る 1 回は、macOS の参加者 1 人が 7 人との LAN 経路を確定できないままで、アプリ側の不具合として調べている。GitHub-hosted の macOS ランナーは直接 UDP が通らないことがあり、これはアプリでは直せない | 11/8、手動 |
| GUI E2E（デバッグビルド、`tests/e2e/tests/gui.rs`） | 相手 15 人 | 相手 2 人（3 人のルーム） | 10/14、16 スレッド、ホストの load 17〜21 |
| 人数ぶんの別々のマシン | 16 人 | 未検証 | — |

デバッグビルドは、相手 2 人で空読み 26・往復 5.3 ms だが、相手 3 人から空読みが数千に増え往復が 16.0 ms に張り付く（暗号と PCM の変換が間に合わない）。
同じ負荷でも最適化ビルドは相手 9 人を捌くので、必要な性能はビルドで桁が違う。測り直すとき:

```bash
JAMJAM_CAPACITY_PEERS=2,3,4,5,6,7,8,9 cargo test --features gui --test gui -- --ignored --nocapture --test-threads=1 how_many_peers_the_app_takes
```

人数ごとに、相手の数・1 本あたりの受信と送られた数・空読み・補間・往復の遅延・アプリの CPU・ホストの load が 1 行ずつ出る。結果の表は

## 悪い回線に通して、途切れの変更を前後で比べる

受信バッファ・欠けた音の補い・再生の速さの調整など、途切れに効く変更の効き目は、同じ悪い回線にアプリを通して、変更の前後の表を並べて見ます（ADR-124）。
アプリの中は変えません。相手の手前に、遅延・揺れ・欠け・順番の入れ替わり・重複・帯域・全断をかける UDP の中継（`tests/common/line.rs` の `BadLine`）を置くだけです。
乱数の種を固定するので、同じ種なら同じデータグラムが落ち、同じように遅れます。権限も実機も docker も要りません。

```bash
# 条件の名前を引数に取る。表が出て、終了コードは 0 = 全部測れた / 1 = 測れない条件があった / 2 = 引数が分からない
cargo test --release --test line_trial -- 4g-busy burst-loss
cargo test --release --test line_trial -- all --duration 30 --quality    # 全条件。--quality は 1 kHz の音も通して音の傷みを足す
cargo test --release --test line_trial -- --list                         # 条件の一覧
cargo test --release --test line_trial -- all --app /path/to/jamuru-before --json before.json   # 別の版のアプリを測る
```

変更の前後で比べるには、変更前のコミットで `cargo build --release` したバイナリを `--app` で渡し、同じ条件・同じ `--seed`・同じ `--duration` で 2 回回して表を並べます。
数字の良し悪しでは終了コードを変えません（アプリがレポートまで走らなかった・回線を何も通らなかった・往復が回線の最短より短く回線が効いていない、のときだけ 1）。
引数なしは `fiber` と `4g-busy` を 6 秒ずつ（約 20 秒）で、毎回の `cargo test --all-targets` が回します。

条件は片道の値です（往復は 2 倍）。実機で回線の品質をかける道具と数字をそろえてあるので、実機での測定と並べられます。

| 名前 | 片道の遅延 | 揺れ（正規） | 欠け | 帯域 |
|---|---|---|---|---|
| `fiber` | 3 ms | 1 ms | なし | 制限なし |
| `4g-good` | 35 ms | 8 ms | 0.2 % | 20 Mbit/s |
| `4g-busy` | 90 ms | 25 ms | 1 % | 5 Mbit/s |
| `burst-loss` | 40 ms | 10 ms | 平均 20 パケット続く欠けが全体の約 2 %（Gilbert-Elliott 0.1 %・5 %・100 %・0 %） | 制限なし |
| `narrow` | 40 ms | 10 ms | なし | 1 Mbit/s |
| `queue-bloat` | 30 ms | 10 ms | なし | 4 Mbit/s（待ち行列 600 ms） |
| `loss-5` / `loss-20` | 20 ms | 2 ms | 5 % / 20 %（ランダム） | 制限なし |
| `wifi` | 0.1 ms | 3.0 ms（Pareto） | なし | 制限なし |
| `wired` | 0.2 ms | 0.3 ms | なし | 制限なし |

表の読み方: `heard/expected` は返ってきた/返るはずだったバースト数（返るはずだった数は、往復が済む前に終わった直近のバーストを除く。ADR-039）。
`buffer` は終了時の受信バッファの段数、`played`・`concealed`・`late` は再生・補った・遅れたフレーム数、`lost` は回線が落とした割合（欠け・待ち行列あふれ・全断の合計）、
`sent` はアプリが回線に送った量。**`sent` が帯域の条件の上限に届いていなければ、その条件の帯域はアプリに効いていない**（下の注）。
`--quality` の `tone gone` は 1 kHz の音が消えていた 10 ms の窓の割合、`tone damaged` は音のある窓のうち音以外のエネルギーが 0.1 %（約 30 dB）以上の窓の割合。

### 今の develop での基準（理論値と検証済みを分ける）

| 確かめること | 理論値 | 検証済み | 測った日・条件 |
|---|---|---|---|
| 模擬の欠けの割合 | 設定どおり（`loss-5` は 5 %） | 計算で 10 万個に対し 4.65〜5.35 % に収まる（`bad_line_test.rs`）。アプリを通した `loss-5` は上り 4.9 %・下り 5.3 %、`loss-20` は 21.0 %・20.9 % | 11/12、30 秒 |
| 模擬の続く欠け | 平均 20 個続き、全体の 1.96 % | 300 万個に対し 17〜23 個・1.67〜2.25 %（計算）。アプリを通した `burst-loss` は上り 2.2 %・下り 1.6 % | 11/12 |
| 模擬の遅延・揺れ・帯域・順番・重複・全断 | 設定どおり | `bad_line_test.rs` が計算と実際のソケットの両方で確かめる。短い遅れは長い遅れの後ろで待たない | 毎回 |
| 同じ種で同じ結果 | 同じ | 計算と、中継を 2 回立てて落ちたデータグラムを比べるテストで確認 | 毎回 |
| 実際のカーネルの `netem` との一致 | 同じ数字 | **未検証**（この環境では docker の `NET_ADMIN` が使えない。実機の測定と並べる） | — |
| 2 台のアプリを回線の両側に置く | 可能 | **未検証**。今は相手が受けた音を返す相手か `Connection`（`BadLine::start(Some(a), b, ..)`）で、偽のシグナリングが両方の候補を中継の口に向ける仕組みは無い | — |
| 帯域の条件がアプリに効く | `narrow`（1 Mbit/s）・`queue-bloat`（4 Mbit/s） | `narrow` は 1 kHz の音では上り 17.7 % 落ちて効く。バーストでは効かない。`queue-bloat` はどちらでも効かない（下の注） | 11/12 |

`fiber` の往復は、ホストが空いているとき 18.7 ms（中央値）、混んでいると 32 ms まで増える。**表の値は台の負荷で動くので、前後を比べるときは同じ台で続けて回す。**

| `4g-busy` | 31/59 | 181.7 / 218.9 / 248.4 / 248.4 | 10 | 3795 | 2291 | 1365 | 1.0 / 1.1 | 524 / 519 | 39.0 | 37.8 |
| `burst-loss` | 57/59 | 98.8 / 117.2 / 131.1 / 151.8 | 10 | 10696 | 355 | 202 | 2.2 / 1.6 | 528 / 516 | 0.6 | 2.1 |
| `narrow` | 60/59 | 96.0 / 112.0 / 113.7 / 114.4 | 10 | 10976 | 229 | 666 | 0.0 / 0.0 | 529 / 529 | 0.1 | 3.4 |

（11/12、`cargo test --release --test line_trial -- all --duration 30 --quality`。往復・再生・補った・遅れた・送った量はバーストの回、音の 2 列は 1 kHz の音の回。）

この表を見て気づいたことは、直さずに別のチケットに切った。要点:

- `4g-busy`（揺れ 25 ms）は 1 kHz の音の 39 % が消え、バーストも 59 個中 31 個しか返らない。受信バッファは上限の 10 段（約 27 ms）で、再生が間に合わない
- 欠けだけで揺れの小さい `loss-5`（揺れ 2 ms）でも、受信バッファは 10 段に張り付き、往復が回線の最短（40 ms）より約 27 ms 長い。揺れが大きいときの値と同じ上限に達している
- **帯域の条件は、CLI の入力ではほとんど効かない。** バーストの回でアプリが送る量は約 530 kbit/s、1 kHz の音でも約 1.2 Mbit/s で、無音や単純な音は詰めて送られる（ADR-111）。`narrow`（1 Mbit/s）が音で効くだけで、`queue-bloat`（4 Mbit/s）は待ち行列が 5 ms しか溜まらない。
  実際の楽器の音（約 4 Mbit/s 以上）で帯域の条件を効かせるには、詰めにくい入力（雑音など）が CLI に要る
